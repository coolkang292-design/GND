### 2-2. 사다리 회차의 「남은 일정 다시 잡기」 — ✅ **고쳤다 (2회차)**

문제였던 것: 공용 `buildMissedSessionProposal`은 **요일 슬롯**으로 다시 잡는데
사다리는 요일이 아니라 6일 주기다. 사다리의 `preferredSlots`는 첫 주기 5일의
요일일 뿐이라(RPC가 요구해서 채워 보내는 값 — §2-3), 그것으로 다시 잡으면 7일
주기로 근사돼 5일 훈련 뒤 **2일**을 쉬게 됐다. 그리고 **RPC가 통과시켰다** —
모든 회차가 같은 시각이고 날짜도 오름차순이라 아무 검사에도 안 걸린다.
**오류 없이 틀린 날짜가 깔리는** 종류였다.

고친 방법:

| | 무엇 |
|---|---|
| `ladder-schedule.ts` | `buildLadderMissedSessionProposal` 추가 — 남은 회차를 `오늘`과 `마지막으로 마친 날+1` 중 **나중**부터 5일 훈련·1일 휴식으로 다시 깐다 |
| `calendar-view.tsx` | `isLadderPlan(plan)`이면 그쪽을 부른다. 나머지는 그대로 공용 함수 |
| `ladder-schedule.test.ts` | 9건 — 간격이 `1,1,1,1,2`로 반복되는지 **직접 센다** |
| `calendar-view.test.tsx` | 3건 — **배선**을 고정한다. 함수만 있고 안 불리면 안 고친 것이고, 그 경우 오류가 안 난다 |

⚠️ 두 테스트 묶음 다 **변이 테스트로 확인했다.** 휴식일을 없애면 도메인 테스트
   1건이, 배선을 끊으면 컴포넌트 테스트 2건이 실패한다(근력 회귀는 통과).

⚠️ 공용 함수와 달리 `occupiedDates`를 **안 받는다.** 0102로 같은 날 계획을 여러
   개 담을 수 있게 되어 남의 계획을 피할 이유가 사라졌고, 피하려 들면 그 순간
   주기가 깨진다. 주기가 이 프로그램의 전부다.

⚠️ 남은 한계: 뒤 회차를 먼저 마치고 앞 회차를 건너뛴 경우(4회차 미완 · 5회차 완료)는
   못 고친다 — 마친 회차는 안 옮기는데 앞 회차를 오늘 이후로 밀면 순서가 역행한다.

   제안 날짜의 간격이 `1·1·1·1·2`인지. **이틀이 비면 배선이 안 걸린 것이다.**

### 2-3. 사다리 프로그램의 `preferredSlots`는 **날짜를 정하지 않는다**

RPC가 서로 다른 요일 2~5개를 요구해서 첫 주기 5일의 요일로 채워 보낼 뿐이다.
그 값을 읽어 무언가를 하려는 코드를 새로 쓰지 마라 — 2회차 이후와 요일이 다르다.

### 2-4. 회귀 스크립트 3종을 되살렸다 — ✅ (2회차)

0102는 **동작을 바꾼** 마이그레이션이라, 옛 동작을 지키던 단언들이 **정상 동작을
회귀로 신고**하기 시작했다. 실제로 돌려 보고 갈랐다.

| 스크립트 | 실패 | 원인 |
|---|---|---|
| `workout-plan-test` | 3건 | 전부 0102 (같은 날 중복 차단 · 이동 차단 ×2) |
| `program-enrollment-test` | 4건 | 0102 (등록 충돌 · 재배치 충돌 ×2 · 일반계획 이동 차단) |
| `program-enrollment-test` | 2건 | **0069(2026-08-12)부터 썩어 있었다** |
| `program-interval-enrollment-test` | 0건 | — |

0069 쪽 2건: `program_recovery_gap`이 `program_plan_date_order`로 바뀐 것과,
**48시간 회복 간격 규칙 자체가 삭제된 것**. 3주 넘게 실패 상태였는데 아무도 몰랐다.

> ⚠️⚠️ **왜 안 드러났나 — `source: "derived"`는 "통과한다"가 아니라
> "한 번도 안 돌렸다"는 뜻이다.** 셋 다 derived였고, `program-enrollment-test`는
> 기준선 **13**인데 실제 단언이 **27**개였다. 정적 추정이 절반이나 틀려 있었는데도
> 아무 경고가 없었다. `--list`에서 derived를 보면 **그건 미검증 표시다.**

고친 방향은 전부 같다 — **"막히는가"를 "몇 개가 남는가"로 뒤집었다.**
"201이 왔는가"는 저장이 통째로 죽어도 통과하지만 "그날 계획이 2개인가"는 안 통과한다.
같은 이유로, 0102가 **없애지 않은** 규칙(같은 프로그램의 두 회차가 같은 날 서는 것,
프로그램 회차 자신은 전용 RPC로만 이동)에는 단언을 **새로 넣었다** — 좁힌 것을
없앤 것으로 오해하면 "주 3회"가 조용히 "하루에 몰아서"가 된다.

## 3. ⚠️ 이 세션에서 물린 함정 — 같은 자리에 다시 빠지지 마라

### 3-1. 마이그레이션이 **아직 안 낸 마이그레이션을 되돌린다**

이 저장소는 같은 함수를 여러 마이그레이션이 `create or replace`로 덮어쓴다.
0102를 **0100·0101 적용 전** 스냅샷에서 떠 놨었고, 그대로 Run했으면 사다리 24회
지원과 주차 1~8이 **통째로 사라질** 참이었다.

> **규칙: 마이그레이션을 하나 적용할 때마다 `pnpm db:snapshot`을 다시 돌리고,
> 아직 안 낸 마이그레이션의 함수 본문을 다시 떠라.**

0102의 확인 쿼리 **4번**이 이 회귀를 잡는다.

### 3-2. `pg_catalog.coalesce`는 없다

`SET search_path TO ''` 때문에 이름을 전부 스키마로 묶다가 `coalesce`에도 붙였다.
**COALESCE는 함수가 아니라 SQL 문법 구조다**(CASE·NULLIF·GREATEST와 같은 부류).
붙이면 42883으로 죽는다.

⚠️ **CREATE 시점에는 안 잡힌다.** plpgsql 본문은 파싱만 하고 이름 해석은 실행할 때
한다 — 0100은 아무 경고 없이 "성공"으로 끝났고, 등록을 눌러야 드러났다.

### 3-3. **테스트도 빌드도 SQL을 안 읽는다**

게이트가 전부 초록인 채로 깨진 마이그레이션(안 닫힌 `/*`)이 나갔다.
`src/lib/domain/migration-sql.test.ts`가 이제 마이그레이션 102개에 대해
블록 주석 짝 · `$function$` 짝 · begin/commit 짝을 본다. **그물이지 문법 검사가
아니다** — "Run해 봐야 아는 것"이 여전히 남아 있다.

### 3-4. 테이블 CHECK 제약은 스냅샷에 **안 담긴다**

`pnpm db:snapshot`은 함수·정책·인덱스만 뜬다. 0101에서 `program_week` 제약을
바꿔야 했는데 **이름을 몰랐다**(0066이 인라인으로 붙였고 저장소에 기록이 없다).
이름을 찍었다가 틀리면 `drop ... if exists`가 **조용히 넘어가고** 옛 제약이 남는다.
→ **이름 대신 정의로 찾아 지우는 DO 블록**을 썼다. 같은 상황이면 그 패턴을 써라.

### 3-5. 개발 서버는 **운영 DB**를 본다

별도 dev DB가 없다. 개발 서버에서 프로그램을 등록하면 **사장님 계정에 진짜 회차가
생긴다.** 확인 뒤 「이 프로그램 그만두기」로 지워야 한다.

### 3-6. Vercel 배포는 `--scope gnd4`가 필요하다

`.git` 없는 복사본에서 배포하는 것(`git archive HEAD`)은 기존 규칙 그대로인데,
`vercel --prod --yes`만 쓰면 **"Not authorized"** 가 난다. 프로젝트가 팀 소유라
`--scope gnd4`를 붙여야 한다.

```bash
git archive HEAD | tar -x -C <임시폴더>
cp -r .vercel <임시폴더>/.vercel
cd <임시폴더> && npx vercel --prod --yes --scope gnd4
```

## 4. 설계 메모 — 왜 이렇게 했나

### 4-1. 회차 수가 18이었던 이유, 24로 바꾼 이유

처음에 18회로 냈다. **18은 원문이 아니라 등록 RPC가 `p_plans` 길이를 18로 못 박고
있어서** 나온 숫자였다. 사장님이 *"18회가 맞음?"* 이라고 물었고, 원문을 세어 보니
"5일 훈련 1일 휴식 × 4주"의 훈련일은 **24**였다. 제약이 프로그램을 줄이고 있었던
것이라 제약을 고쳤다(0101).

> **교훈: 제약에 맞춰 요구사항을 줄이기 전에, 제약을 고칠 수 있는지 먼저 보라.**

### 4-2. 사다리만 요일이 아니라 주기로 일정을 잡는 이유

요일 목록은 **7일마다 반복**해서 6일 주기를 표현할 수 없다. 월~금으로 근사하면
5일 훈련 뒤 **2일**을 쉬게 되어 원문의 루틴이 아니다.
`ladder-schedule.ts`가 `buildProgramSchedule`과 **따로** 있는 이유가 이것이다.
합치지 마라 — 날짜를 정하는 방식이 근본부터 다르다.

### 4-3. 0102만 배포 순서가 반대인 이유

옛 앱이 `upsert(onConflict: "user_id,plan_date")`를 쓴다. 제약을 없애는 순간
42P10으로 **계획 저장이 통째로 죽는다.** 그래서 0100·0101은 배포 전, **0102는
배포 후**다. 0102 머리말에 크게 적어 뒀다.

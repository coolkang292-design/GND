## 2. 문제의 본질

**핵심:** "이전 등수"를 기억하는 곳이 없어서, 지금 등수가 바뀌었는지 아무도 모른다.
**성공 기준:**
1. 등수가 실제로 바뀐 사람에게만, 바뀐 직후 1번 알림이 간다.
2. 알림의 등수가 챌린지 화면의 등수와 **항상 같다**(다른 숫자를 말하면 신뢰가 깨진다).
3. 순위를 비공개로 둔 방에서는 알림으로 순위가 새지 않는다.
4. 운동 한 번에 알림 폭탄이 나가지 않는다.

## 3. 가정 점검

| 가정 | 판정 |
|---|---|
| "순위는 DB에서 계산해야 한다" | **버린다.** 점수식이 TS에 있고 5단 타이브레이크·보너스까지 얽혀 있다. SQL로 복제하면 두 벌이 갈라진다(`scoreParticipant` 주석이 경고하는 바로 그 사고). TS 한 벌을 서버에서 부른다 |
| "클라이언트가 운동 완료 때 호출하면 된다" | **수정.** 앱을 닫거나 네트워크가 끊기면 누락. 트리거 신호는 DB에서 와야 한다 (0016과 같은 `pg_net` 패턴) |
| "모든 방에 보낸다" | **버린다.** `live_ranking=false` 방은 순위가 진행 중 비공개다. 알림이 순위를 말하면 그 약속을 깬다 |
| "등수가 바뀔 때마다 보낸다" | **수정.** 동점 흔들림·연속 완료 때 폭탄. 쿨다운·묶음 필요 |
| "종목별 랭킹(횟수·시간·거리·볼륨)도 포함" | **이번엔 제외.** 종합점수 하나만(시상대·`내 순위 N위`와 같은 자). 종목별은 2차 |

## 4. 그라운드 트루스

- 점수가 변하는 사건은 **운동 완료 · 운동 삭제/취소 · 목표 수정(0090 목표 상향)** 뿐이다. 날짜가 지나는 것만으로는 순위가 안 바뀐다(참여율 분모는 기간 고정).
- 순위 계산은 TS 한 벌이다. 서버가 쓰려면 TS를 서버에서 돌려야 한다.
- 알림 1행 = 푸시 1회. 푸시는 이미 배관이 있다 — **새로 만들 것은 "감지"뿐**이다.
- 비교하려면 직전 순위를 저장해야 한다. 이게 유일하게 빠진 부품이다.

## 5. 설계 (위에서 아래로 쌓기)

```
workout_sessions 완료(status→completed) ──(0016식 pg_net)──▶ POST /api/challenge/rank-check {session_id}
    └ 서버(service_role): 그 사람이 joined 인 active + live_ranking=true 챌린지만 골라
        └ 방마다: getPeriodStatsByUser → buildParticipantInput → rankParticipants   ← 화면과 같은 TS 한 벌
        └ challenge_rank_snapshots 와 비교 → 달라진 사람에게 notify('rank_change') → 스냅샷 갱신
```

### 5-1. DB (0139) — 비파괴만
- `challenge_rank_snapshots(challenge_id, user_id, rank, notified_at, updated_at)` PK(challenge_id, user_id). RLS 켜고 **정책 없음**(service_role만 접근).
- `workout_sessions` AFTER UPDATE 트리거: `status`가 `completed`로 바뀔 때만 `net.http_post(/api/challenge/rank-check)`. 실패해도 운동 완료를 막지 않는다(`exception when others then null`).
- `rank_change`는 허용목록에 이미 있으므로 제약 변경 불필요.
- ⚠️ 트리거 함수는 `set search_path = ''` + 스키마 한정자(0092 관례), `grant`/`revoke`는 만들 때 명시.

### 5-2. 서버 `/api/challenge/rank-check`
- 입력은 `session_id`만. **DB 재조회가 진실**(`/api/push/notify`와 같은 방식 — 위조 호출은 아무것도 못 한다). 공유 시크릿 헤더를 추가로 걸지는 §6 결정 4.
- 순수 로직은 `src/lib/domain/rank-change.ts`로 분리(I/O 없음, TDD): `diffRanks(prev, next) → [{userId, from, to}]`, `rankChangeMessage(...)`.
- 첫 계산(스냅샷 없음)은 **알림 없이 기준선만 저장**. 방 참가·시작 직후 허위 알림 방지.

### 5-3. 알림 문구 (초안, 확정은 §6)
- 상승: `📈 5만원빵 · 2위로 올랐어요` / `3위 → 2위`
- 하락: `📉 5만원빵 · 3위로 밀렸어요` / `오늘 운동하면 다시 올라갈 수 있어요`
- 동점(공동): `2위 (공동)` 표기, 공동끼리 자리 이동은 알림 없음.
- 아이콘은 기존 `rank_change: 📈` 재사용. 하락도 같은 유형이므로 제목 이모지로 구분.

### 5-4. 폭탄 방지
- 같은 (챌린지, 사용자)에게 **쿨다운 N분**(안) 안에는 합쳐서 마지막 등수 1건만. 스냅샷은 항상 최신으로 갱신하되 `notified_at`으로 발송만 제한.
- 한 요청에서 한 방당 알림 ≤ 참가자 수.

## 6. 사용자 결정 필요 (구현 전)

1. **누구에게?** ✅ **확정 2026-11-15: (a) 등수가 바뀐 모두**(올라간 사람 + 밀린 사람).
2. **추월자 이름을 알림에 쓸까?** "○○님이 나를 추월" — 재미는 크지만 TOP3 밖 닉네임이 노출된다. 지금 화면은 TOP3 + 내 순위만 공개. 추천: **이름 없이** 등수만.
3. **쿨다운 길이** — 추천 30분.
4. **서버 호출 보호** — pg_net 요청에 공유 시크릿을 걸지(안전) vs `/api/push/notify`처럼 DB 재조회만 믿을지(단순). 이 경로는 알림을 *만들* 수 있으므로 시크릿 추천.

### 6-1. 구현 중 확정된 것 (2026-11-15)
- **수신 범위:** 순위가 한 명이라도 바뀌면 **참가자 전원**(joined)에게 1건. 올라감 📈 / 밀림 📉 / 그대로 📊.
- **밀린 사람에게 추월 제안(사용자 추가 요청):** 내 미달성 목표 중 "끝까지 채우면 실제로 바로 위 순위를 넘는" 것을 `scoreParticipant`로 시뮬레이션해 고른다 → `유산소 거리 4km만 더 채우면 다시 앞설 수 있어요`. 안 되면 `목표 + 운동 하루 더`, 그래도 안 되면 일반 문구. 위 사람의 닉네임·점수는 문구에 넣지 않는다.
- **~~이름 없이 등수만~~ → 닉네임 노출로 변경(사용자 결정 2026-11-15):** 제목 `○○님이 N위 됐어요`(○○ = 이번에 가장 크게 오른 사람), 본문 `지금 나는 M위예요 + 한마디 · (제안) 하면 다시 N위를 탈환할 수 있어요`. 올라간 본인은 `N위로 올랐어요`. 쿨다운 30분은 추천안 채택.
- **"탈환"은 시뮬레이션으로 보증한다:** 제안대로 했을 때 `rankParticipants`로 실제로 이전 순위가 되는 경우만 "탈환"이라 말한다. 안 되면 되찾을 수 있는 가장 높은 순위까지만("N위까지 올라갈 수 있어요"), 공동 순위로 걸치는 건 탈환으로 치지 않는다.
- **위트:** 본문 변형 여러 개를 시각 기반 씨앗으로 번갈아 보낸다. 사실 어구(`지금 나는 M위예요`·`N위 → M위`·`N위 그대로`·`탈환`)는 모든 변형에 고정, 위트는 이모지·한마디에만 얹는다.
- **설정 존중:** `notification_settings.ranks`를 끈 사람은 제외(행 없음 = 켜짐). 설정 화면 문구도 "챌린지 순위 변동·종료·시상대"로 갱신.
- **알림함 표시:** `rank_drop`은 본문을 3줄까지 보여 준다(한 줄이면 탈환 제안이 잘린다).
- **공유 시크릿은 쓰지 않았다(추천과 다름).** 시크릿을 SQL 트리거 본문에 박아야 해서 오히려 위험하다. 대신 `/api/push/notify`와 같은 신뢰 모델 — DB 재조회 + 실제로 순위가 바뀐 때만 발송 + 스냅샷 선점 원자성(`claim_rank_snapshot`, challenges 행 FOR UPDATE).

### 6-3. 추월 제안 → 운동 세팅 (사용자 추가 요청 2026-11-15, **설계만**)
요청: 계획이 있으면 세팅하지 않고, 없으면 제안한 대로 운동을 담아 준다.
**이미 있는 장치를 재사용한다** — `workout_suggestion`(0078, 설계 `2026-08-16-empty-day-workout-suggestion-design.md`):
알림 → `/record?suggest=1` → 화면이 `pickSuggestionKind`를 다시 돌려 **계획이 없고 draft가 비었을 때만** 종목을 담는다.
DB에 계획을 심지 않고(달력에 안 남음), 자동 시작도 안 한다(사용자 결정 유지).
- **대상은 순위가 내려간 사람뿐이다**(사용자 확인 2026-11-15). 올라간 사람·그대로인 사람 알림은 기존 `/challenge` 이동 그대로, 운동 세팅 없음.
- 계획 있는 날: `hasPlanToday → null`이라 **세팅 안 함**(기존 계획이 자동으로 담기는 현행 동작 그대로). 알림 문구는 그대로 간다.
- 계획 없는 날: 제안 목표에 맞는 운동을 draft에 담고 `운동 시작`은 사람이 누른다.
- 필요한 것: ① 밀림 알림 전용 목적지 `/record?suggest=overtake` (알림 유형 `rank_drop` 분리 → 0078식 허용목록 전체 재작성 + `TYPE_ICON`·`PUSH_URL_BY_TYPE`) ② 제안한 목표 종류를 화면에 전달 — `notifications`에 URL·payload 컬럼이 없어서 nullable `meta jsonb` 컬럼 추가(비파괴) ③ 목표→담을 운동 매핑(아래) ④ `record/page.tsx` 쿼리 처리 + `workout-suggestion.ts`에 `overtake` kind.
- 목표 → 담는 것(1차): `tabata_count` → 4분 인터벌 시트 · `cardio_*` → 유산소(걷기/러닝) 종목 · 그 외(`*_days`·`weight_reps`·`volume`·`bodyweight_*`) → 지난 운동 그대로. **목표량(예: 4km)까지 세트에 미리 채우는 것은 2차.**
- ⚠️ 서버가 종목을 싣지 않는다(옛 제안이 남는 문제 — 0078 설계 §3). 목표 종류만 싣고 종목은 화면이 정한다.

1. 순수 함수 단위 테스트: 동점·공동 순위·첫 계산·쿨다운·상승/하락 문구.

3. **화면 확인 — 픽스처 A·B 두 계정 필수**(사회적 기능): `dev-fixture.mjs challenge` 후 A·B 중 B가 운동 완료 → **A 화면의 알림 벨 배지·문구·아이콘**, 푸시 클릭 시 `/challenge` 이동. 라이브 랭킹 꺼진 방에서 알림이 **안 오는지**도 본다.
4. 하락 알림은 점수 역전이 필요하므로 픽스처에 목표/운동 시드를 넣어 재현한다(구체 시드는 구현 때 확정).

## 9. 알려진 위험

- 트리거가 `workout_sessions`에 걸리므로 운동 완료 경로 성능·실패 격리가 핵심 → 비동기(`pg_net`) + 예외 삼킴.

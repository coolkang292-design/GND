# 배포 저장공간 절감 — 구현계획 (2026-11-19)

## 0. 문제의 본질

**핵심 문제:** Vercel Deployment Storage 10GB 중 75%(7.5GB) 알림선(11/18)에 닿았거나 가깝다. 앱 동작을 바꾸지 않고 **배포 1건당 올라가는 바이트**와 **보관되는 배포 수**를 줄인다.

**성공 기준 (측정 가능해야 한다)**
1. 현재 Deployment Storage / Functions Storage 수치가 이 문서에 **숫자로** 기록돼 있다
2. 첫 변경 후 새 배포의 정적 자산 합계가 **기존 운영 배포보다 ≥45MB 작다** (MP3 56MB → 8MB)
3. 타이머·음성 신호·화면 카운트다운 싱크 어긋남 **0** (iPhone PWA 실기)
4. 정리한 프리뷰 중 공유 링크·롤백 후보가 **0건** 포함

## 1. 실측으로 확인된 사실 (저장소, main 기준)

| 사실 | 값 |
|---|---|
| `public/audio` MP3 6개 | 16분×2 = 32.0MB · 8분×2 = 16.0MB · 4분×2 = 8.0MB → **합계 56MB** |
| 현재 비트레이트 | **이미 128kbps CBR** (10/24 `-v3`에서 256→128 완료, GND#22) |
| 그다음 큰 파일 | `splash/*.png` 2.6MB×2, `characters/char-7.png` 0.5MB … 전부 3MB 이하 |
| `vercel.json` | crons만 있음. `ignoreCommand`·`.vercelignore` **없음** |
| 6개 파일 사용처 | 기본 3개(`total-body-v3`) + Dynamite 3개(특정 계정만). 둘 다 `tabata.ts` |

> ⚠️ 이 작업 브랜치(`feat/posthog-funnel`)의 `public/audio`는 **v2 옛 3개(56MB)**다. 작업은 **`main`에서 갈라야** 한다. 이 브랜치에서 하면 안 된다.

**결론:** 정적 자산 용량의 **약 75%가 MP3**, 그중 **16분 2개가 57%**. 한 번 더 줄일 수 있는 거의 유일한 큰 덩어리다.

### 1-1. 재검토 (2026-11-19) — "MP3가 가장 크다"의 범위

`main` 추적 파일 86.3MB(`git ls-tree`) 기준 **실측**:

| 덩어리 | 크기 | 비중 |
|---|---|---|
| `public/audio` (MP3 6개) | 56.0MB | **65%** |
| 그 외 `public`(이미지류 png 7.6·webp 6.2·jpg 0.5) | ~14MB | 16% |
| 소스·문서·데이터(`src`·`docs`·`data`·`supabase`·`scripts`) | ~16MB | 19% |

- **"저장소 안에서 가장 큰 덩어리"는 맞다.** 정적 자산(`public` 약 70MB + 빌드 `static` 수 MB)으로 좁히면 약 80%다.
- **그러나 "Deployment Storage를 가장 많이 차지한다"는 아직 증명되지 않았다.** 측정하지 못한 것이 둘 있다.
  1. **프로덕션 빌드 산출물** — 로컬 `.next`는 dev 빌드(818MB 중 dev 783MB, `BUILD_ID` 없음)라 기준이 못 된다. 서버 함수 번들(로컬 server 31MB·소스맵 72.6MB는 dev 값)이 실제 배포에 얼마인지 모름.
  2. **Vercel의 용량 계산 방식** — MP3는 10/24 `-v3` 이후 **내용이 안 바뀌었다**. 같은 해시를 배포 간 중복 제거로 세면 MP3는 **전체에 한 번(56MB)** 만 잡혀 7.5GB의 원인일 수 없고, 매번 바뀌는 코드·함수 번들이 원인이다. 중복 제거를 안 하면 배포당 약 100MB × 보관 배포 수로 커지고 MP3는 그중 절반 안팎이다.
- 역산: 7.5GB ÷ 배포당 ~100MB ≈ **보관 배포 70여 건**일 때 설명된다. 배포 목록의 총 건수가 이 가설을 가장 싸게 검증한다.

**판정:** MP3 압축은 "가장 큰 단일 덩어리"라서 후보 1순위지만, **§A 측정 전에는 확정하지 않는다.** 측정 결과가 "배포 수 많음 + 중복 제거 없음"이면 프리뷰 정리가 MP3보다 효과가 크다.

### 1-2. 더 큰 절감 후보 — 8·16분 파일은 4분 블록의 **그대로 반복**이다 (2026-11-19)

- `interval-cue.ts`: 8·16분 = 4분 음원(250.02초)을 2·4번 이어 붙인 것. 각 블록이 **자기 준비 13초를 가진 독립 단위**이고 코드가 이미 `withinBlock`으로 블록별 계산을 한다.
- 따라서 **4분 파일 하나를 N번 반복 재생**하면 8·16분 파일이 필요 없다. 음악·구호는 그대로 둔다 (재인코딩 없음).
- 절감: 6개 56MB → 4분 2개 **8MB (−48MB, −86%)**. 16분 2개만 압축하는 §3-C(−16MB)보다 크고 음질 위험이 없다.
- 구호만 추출하는 안은 **음악을 빼지 않는 한 용량이 안 준다**. 기존 음원은 구호가 음악에 섞여 있어(10.6~14.4초 등) 분리하려면 스템 분리로 품질 손실이 생긴다. 음악을 사용자 몫으로 돌리는 "내 음악 모드"일 때만 의미가 있다.
- 위험: ① 블록 경계의 끊김(MP3 재시작 틈) ② iPhone 잠금화면에서 `ended` 후 재시작이 막히는지. `audio.loop = true` + 블록 수는 `currentTime` 되감김으로 센다. 둘 다 **[미검증]** — 실기기 확인 전엔 배포하지 않는다.
- 4분 원본은 8MB를 유지(필요시 96kbps로 6MB).

## 2. 가정 검증 (참 / 거짓 구분)

| 가정 | 판정 | 근거·확인법 |
|---|---|---|
| "MP3를 줄이면 저장공간이 준다" | **[미검증]** | Vercel이 같은 해시 파일을 배포 간에 중복 제거하는지 불확실. 줄여도 **옛 배포들은 옛 56MB를 그대로 보관**한다. → 1단계 수치와 2단계 배포 목록으로 확인 |
| "오래된 프리뷰 삭제가 효과 있다" | **[미검증]** | 배포 1건당 크기를 보기 전엔 모름 (6~10분 단계에서 정리 후보별 크기 확인) |
| "비트레이트를 더 낮춰도 싱크는 유지된다" | **조건부 참** | CBR이면 길이 동일. 단 `interval-cue.test.ts`가 **128kbps = 16,000B/s**로 박혀 있어 상수를 같이 바꿔야 함 |
| "파일 이름 그대로 덮어써도 된다" | **거짓** | `tabata.ts` 주석: 같은 이름이면 브라우저·CDN이 옛 파일을 쓴다 → 반복 재생안은 4분 파일을 **그대로** 쓰므로 해당 없음. 폴백(재인코딩) 때만 **`-v4`로 이름 올림** |
| "문서만 바꿔도 프리뷰가 필요하다" | 거짓 | 문서 전용 변경은 빌드 불필요 |

### C. 06:50–07:00 — 첫 변경: **4분 음원 반복 재생** (`main`에서 브랜치 분기)

**원리:** 8·16분 파일은 4분 블록(250.02초)을 2·4번 이어 붙인 것이고, 각 블록이 자기 준비 13초를 가진 독립 단위다. 4분 파일 하나를 N번 반복하면 된다. **재인코딩 없음 · 새 파일 이름 없음**(4분 파일을 그대로 쓰므로 캐시 문제도 없다).

**삭제:** `tabata-8min-total-body-v3` · `tabata-16min-total-body-v3` · `tabata-8min-dynamite-v1` · `tabata-16min-dynamite-v1` (4개, 48MB)
**유지:** `tabata-4min-total-body-v3` · `tabata-4min-dynamite-v1` (2개, 8MB)

**코드 변경 (먼저 읽고 정확한 위치를 확정한다)**
1. `src/lib/domain/tabata.ts` — 8·16분 트랙의 `src`를 4분 파일로 향하게 한다. 블록 수(`minutes / 4`)를 도출하고, Dynamite 경로 생성식(`tabata-${minutes}min-dynamite-v1.mp3`)도 **4분 파일 하나**로 향하게 고친다. 안 고치면 삭제한 파일을 요청한다.
2. `src/components/record/tabata-sheet.tsx` (`audio.currentTime` 사용 지점: 약 201·312·339행)
   - 마지막 블록 전까지 `audio.loop = true`, **마지막 블록에서 `loop = false`** → 끝에서 자연스럽게 `ended`(= 운동 완료)로 끝나 반복 소리가 새지 않는다
   - 누적 경과 = `블록번호 × 250 + audio.currentTime`. 블록번호는 `currentTime`이 직전 값보다 **크게 되감길 때**(예: 1초 이상 감소) +1
   - 일시정지·재개·세션 복원(`session.tabataMinutes`, 약 260행) 경로에서도 블록번호가 유지되는지 확인
3. `interval-session-overlay.tsx`는 부모가 넘기는 누적 경과를 그대로 쓰므로 **바뀌지 않아야 한다** (바꿔야 한다면 설계가 틀린 것 → 멈추고 재검토)
4. 테스트
   - `interval-cue.test.ts`의 "음원 파일 길이가 블록 계산과 맞는다": 이제 **트랙 총 길이가 아니라 4분 파일 하나 = 블록 1개(250초)** 를 128kbps(16,000B/s) 기준으로 단언하도록 고친다 (8·16분 파일이 없으니 `statSync`가 실패한다)
   - `tabata.test.ts` 약 259~265행의 경로 단언 수정
   - **새 테스트:** 블록 되감김 감지(순수 함수로 분리해 단위 테스트) — "되감김이면 +1, 일반 진행·시크는 +0"
5. `grep`으로 삭제한 4개 파일 이름이 `src`·`docs`·`public`에 **남아 있지 않은지** 확인 (제거 검증은 없어졌는지를 본다)

**효과 예상:** 정적 자산 56MB → 8MB (**−48MB, −86%**).

**폴백 사다리 (앞이 실패하면 다음으로)**
1. `audio.loop` 속성 — 가장 단순, 백그라운드에서도 네이티브로 이어진다
2. `ended` 이벤트에서 같은 요소를 `currentTime=0; play()` — 틈이 크거나 loop가 어긋날 때. iPhone 잠금화면에서 막힐 수 있다
3. 이전 계획 — 16분 2개만 96~64kbps 재인코딩(−16MB), 파일명 `-v4`, 길이 테스트 상수를 트랙별로 분리
4. 효과가 작으면(§2 중복 제거 때문에 총 사용량이 안 줄면) 보관 배포 수·함수 번들 점검

**싱크는 사용자 폰으로 미루지 않는다.** 먼저 개발 서버에서 직접:
- [ ] `pnpm dev` → 인터벌 타이머 4·8·16분 각각 시작, **재생·일시정지·재개**
- [ ] 8분: **블록 경계(250초 부근)** 에서 화면이 "준비 13초"로 돌아가고 음악도 처음부터 시작하는지, 틈(무음)이 귀에 들리는지
- [ ] 16분: 경계 3곳(250·500·750초). 직접 기다리지 말고 **`audio.currentTime = 245` 등으로 경계 직전으로 보내** 확인
- [ ] 마지막 블록 끝에서 **반복 소리가 새지 않고** 운동 완료로 넘어가는지 (loop 해제 확인)
- [ ] 일시정지 → 재개를 경계 직전·직후에 각각 해 블록번호가 유지되는지
- [ ] Dynamite 계정(`NEXT_PUBLIC_INTERVAL_DYNAMITE_USER_IDS`)으로 같은 확인
- [ ] 삭제한 4개 파일이 요청되지 않는지 (네트워크 탭에서 404 없음)

그다음: lint · typecheck · 전체 test · build.

**iPhone PWA 실기(필수, 제가 못 한다 → 사용자 확인 표로 요청, 답을 받기 전에 배포하지 않는다)**

| 조작 | 기대 결과 |
|---|---|
| 8분 코스 시작 후 첫 경계(약 4분 10초)를 지켜본다 | 화면이 다시 "준비 13초"가 되고 음악도 처음부터. 눈에 띄는 무음 없음 |

## 7. 이 분석이 드러낸 것

- "6개 56MB"는 128kbps로 이미 한 번 줄인 값이라 비트레이트로 더 줄이면 음질 위험이 커진다. 반면 **8·16분 파일은 4분 블록의 반복**이라 중복 제거가 무손실이다 — 그래서 첫 변경을 압축에서 **반복 재생**으로 바꿨다 (−48MB vs −16MB).
- 가장 큰 불확실성은 코드가 아니라 **Vercel의 용량 계산 방식**이다. §A 수치가 이 계획 전체의 게이트다.
- 현재 작업 브랜치는 옛 음원(v2)을 들고 있어 **`main`에서 새로 분기**해야 한다.
- 위험은 음원 크기가 아니라 **경계 재시작과 iPhone 백그라운드 동작**이다. 이 둘은 로컬에서 증명되지 않으므로 실기 확인이 배포 조건이다.

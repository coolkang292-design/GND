2. **같은 파일을 둘이 고친다**: `src/app/(tabs)/record/page.tsx`, `record-empty-state.tsx`, `workout.ts`,
   `social.ts`. 원래 폴더 쪽 변경이 main에 올라올 때 충돌한다. 진화 미션 카드는 기존 파일을
   **슬롯 prop 하나**(`missionSlot`)와 상태·효과 한 묶음으로만 건드려 충돌 면적을 줄였다.
3. **마이그레이션 번호**: main은 `0145`까지다. 이 작업은 `0146`·`0147`을 쓴다(충돌 없음).
   원래 폴더의 `0118~0123`은 main의 같은 번호 파일과 **내용이 다르다** — 그 브랜치를 합칠 때 번호를 다시 매겨야 한다.
4. 원래 폴더의 미커밋 기능(PostHog 등)은 이 계획의 범위 밖이다. 건드리지 않는다.

**바로잡는 것 (이전 보고의 오류 — 원래 폴더 코드를 읽고 한 말)**
- "화면이 서버 진화 판정을 무시한다" → **틀림.** main 화면은 단계를 서버 값(`current_stage`)으로 쓴다. 레벨 숫자만 경험치로 계산한다.

## 1. 검증된 현황 (2026-11-22, 운영 DB 직접 조회)

- 레벨 = 누적 경험치(`total_xp`)로 계산. 컷은 `level_definitions.required_total_xp` (35개 레벨).
- 단계(캐릭터) = 서버 `user_progress.current_stage`. 진화 규칙이 켜져 있으면(`stage_evolution_settings.enabled`)
  경험치가 올라도 단계는 그대로이고 진화 판정(`gnd_evolution.safe_evaluate`)이 따로 올린다.
  **화면도 단계는 서버 값을 쓴다**(`getProgressSummary`의 `actualStage`). 레벨 숫자만 경험치로 계산한다.
- **레벨에 상한이 없다.** `apply_xp_and_progress`가 `required_total_xp <= 누적`인 가장 높은 레벨을 그대로 쓴다.
  진화 조건을 못 채우면 레벨(과 레벨 보상)만 계속 오르고 캐릭터는 그대로다.
- 진화의 경험치 조건은 `현재 레벨 >= 목표 단계 첫 레벨` (4단계 Lv.16 / 5단계 Lv.21 / 6단계 Lv.26 / 7단계 Lv.31).
  → **막힌 동안 쌓인 경험치가 다음 진화의 경험치 조건을 공짜로 채운다** (과대 누적).
- 한 번의 재판정에는 **한 단계만** 오른다(`evaluate_stage_evolution`, 3→ 이후). 그래서 과대 누적이 있어도
  한꺼번에 여러 단계를 건너뛰지는 않지만, 다음 단계의 경험치 조건은 이미 채워져 있다.
- 지금 과대 누적된 사람은 **없다**: 9명 전원 누적 경험치가 자기 단계의 끝(다음 단계 컷) 아래다
  (최고 오뎅끼데스까 10170 < 15000, 3단계 4명 ≤ 4460 < 6000).
- 단계 폭(경험치): 1단계 1000 · 2단계 2000 · 3단계 3000 · 4단계 4000 · 5단계 5000 · 6단계 6000,
  단계 안에서는 5레벨이 균등 간격(200·400·600·800·1000·1200·1250).
- 경험치 출처(적립 기준): 운동 완료 178건 평균 120 · 사진 108건 평균 10 · 관리자 조정 1건 1840 · 과거 보정 1건 130.

## 2. 원칙

1. 진화 전까지 **레벨은 그 단계의 마지막 레벨에서 멈춘다** (진화가 눈에 보이는 큰 변화가 되도록).
2. 경험치 조건은 "누적이 N 이상"이 아니라 **"이 단계에서 N을 채웠는가"**. 경험치는 계속 쌓이고 버려지지
   않지만, 막힌 동안 넘친 분은 다음 단계 조건을 미리 채우지 않는다(진화 시점이 새 출발점, 과대 누적 방지).
3. 누적 경험치(`total_xp`)는 평생 기록으로 계속 쌓인다(랭킹·통계용). 레벨·진화 판정만 단계 기준으로 바꾼다.
4. 1~3단계는 지금처럼 경험치만으로 진화한다. (진화가 즉시라 넘칠 틈이 없어 동작은 그대로다.)
5. 이미 진화한 사람의 단계·레벨은 바뀌지 않는다.

## 3. C — 단계별 경험치 + 레벨 상한 (설계)

### 3.1 규칙

- `stage_xp` = 현재 단계에 들어온 시각(`user_stage_history.entered_at`) 이후의 경험치 합 (원장 `xp_transactions`,
  취소(음수) 포함). 진화하면 새 `entered_at`이 생겨 **자동으로 0에서 다시 센다**.
- 단계 폭 `W(k)` = 그 단계 첫 레벨 컷과 다음 단계 첫 레벨 컷의 차 (위 §1 표). 단계 안 한 레벨 폭 `W(k)/5`.
- 레벨 = `그 단계 첫 레벨 + min(4, floor(stage_xp / (W(k)/5)))` (7단계는 최대 35).
- 진화의 경험치 조건 = `stage_xp >= W(현재 단계)`. (기존 `level >= min_level` 대체)
- 단계 첫 레벨 보상(`stage_evolve_N`)과 그 단계 안 레벨 보상은 **레벨을 지나갈 때** 지급 — 지금과 같다.
  진화하는 순간 레벨이 한 칸(마지막 레벨 → 다음 단계 첫 레벨) 오른다.

### 3.2 읽기 전용으로 확인한 것

- 새 방식으로 계산해도 **현재 사용자 전원의 레벨이 그대로**다 (예: 2d19 3단계 `stage_xp` 1550/600 → Lv.13,
  오뎅끼데스까 5단계 260/1000 → Lv.21). 원장 기준 `stage_xp`는 누적−컷과 30~130 차이가 난다(진화를 일으킨
  적립이 진입 시각 이후로 잡히는 순서 차이). 레벨 경계에 걸린 사람은 없다.
- 과대 누적 사례: 아직 없음 → 지금 적용해도 잃는 사람이 없다. **미룰수록 늦는다**(쌓이기 전에 넣는 편이 안전).

### 3.3 구현 범위

서버
1. `user_progress.stage_xp int not null default 0` 추가(비파괴) — 화면이 매번 원장을 합산하지 않도록 캐시.
   적립·취소 때 `apply_xp_and_progress`가 갱신, 진화 때 0으로. **기존 행 값 채우기는 UPDATE라 승인 필요.**
2. `apply_xp_and_progress`: 레벨 = 단계 기준 공식(위)으로 계산. 단계 평가(`safe_evaluate`) **뒤에** 최종 단계로
   레벨을 다시 계산하고 그 다음에 보상 루프를 돈다(순서가 바뀌면 보상이 틀어진다).
3. `gnd_evolution.stage_status`: `xp` 조건을 `stage_xp`(현재/필요 = 경험치)로 바꾼다.
4. `get_crew_member_profile`의 `levelUps`(원장 임계로 되감기)는 새 방식과 안 맞는다 → `user_level_history`로 교체.
5. 형제 함수 훑기: `notify_progress`, `refresh_my_stage_evolution`, 레벨을 읽는 정책·트리거
   (`enforce_routine_slot_limit`은 `current_level`을 읽는다 — 상한 아래에서도 같은 값이라 영향 없음).

앱
6. `getLevelProgress(totalXp)` 호출처(약 10곳: 홈·내 정보·크루 목록·친구판·관리자 통계·분석·챌린지 리포트)를
   서버 `current_level`/`current_stage`/`stage_xp` 읽기로 바꾼다. (예전 "캐시값 대신 다시 계산" 규칙은
   단계 기준에서는 다시 계산할 재료가 없어 뒤집는다 — 주석·문서 동시 수정.)
7. 진화 카드 모델·조건 파서: `xp` → `stage_xp` 조건(단위 경험치)을 받는다. **구버전 앱이 새 키에서 깨지지 않게
   앱을 먼저 배포한다**(`parseStageGateStatus`는 모르는 키를 실패로 처리한다).
8. 레벨이 멈춘 동안의 화면: 경험치 막대는 가득 참, 문구는 "경험치는 가득 찼어요 · 이제 진화 미션을 채워요"
   (진화 미션 카드 B와 연결). 경험치가 헛되이 사라지는 느낌을 막는 것이 이 작업의 성패다.

### 3.4 롤아웃 순서 (앞 단계가 끝나야 다음)

1. 앱: 두 조건 키를 모두 읽고, 레벨은 서버 값 우선 → 배포

### 3.5 결정 (사용자 확정 2026-11-22)

- **경험치는 운동할 때마다 계속 쌓는다.** 진화를 못 해 레벨이 멈춰 있어도 적립은 멈추지 않고
  평생 누적(`total_xp`)은 하나도 버리지 않는다.
- **각 단계는 "그 단계에서 채울 경험치 양"으로 정한다** (누적 컷이 아니라 단계별 고정량):
  1단계 1000 · 2단계 2000 · 3단계 3000 · 4단계 4000 · 5단계 5000 · 6단계 6000.
- **진화하는 순간의 누적 경험치가 새 단계의 출발점이다.** 다음 진화의 경험치 조건은
  `진화 시점 이후 쌓은 경험치 >= 그 단계의 양`. (막힌 동안 넘친 경험치는 누적 기록에는 남고, 다음 단계
  조건을 미리 채우지는 않는다 — 과대 누적 방지.)
- 구현은 §3.1의 `stage_xp`(진화 시각 이후 합계)와 같다 — 설계 변경 없음.
- 안내 문구 필수: 멈춘 동안은 "경험치는 계속 쌓여요(누적 N) · 진화하면 새 단계가 시작돼요" 식으로
  **경험치가 사라지지 않는다**는 것을 먼저 말한다. 누적 경험치(`total_xp`)를 내 정보에 계속 보여 준다.
- 남은 확인: 4·5단계는 오뎅끼데스까 기준 약 44일·약 55일치 경험치다(적립 ≈ 일 90). 습관 조건(§A)과
  겹치므로 단계 양을 더 높이면 진화가 늦어진다 → 현재 값으로 시작하고 데이터를 보고 조정.

## 4. B — 진화 미션 카드

- 서버 `get_my_stage_evolution_status` + 내 기준선(`stage_growth_baselines`)으로 못 채운 조건과 오늘 넘을
  종목별 목표를 만든다. 목표 = 기준 기록 × (1 + 요구 평균 성장률) (중량은 같은 횟수로 0.5kg 올림).
- 챌린지 목표가 있는 날은 챌린지 퀘스트가 우선이라 카드를 읽지도 않는다.
- 파일: `src/lib/domain/evolution-mission.ts`(순수 로직·시험 15건), `src/lib/evolution-mission.ts`(조회·담기),
  `src/components/record/evolution-mission-card.tsx`, 기록 화면 연결.
- 남은 일: 개발 서버 화면 확인(카드 표시·개수·담기 버튼), 이후 커밋.
- §3 적용 뒤에는 "경험치 조건" 행이 `stage_xp`(경험치 N/M) 문구로 바뀐다.

## 5. D — 앱 안 규칙 사본 정렬

`src/lib/domain/evolution-gate.ts`의 `STAGE_RULES`는 서버 규칙표와 같아야 한다고 적혀 있는데
(주석: 2026-11-13 확정값), 2026-11-22 서버 변경(0146·0147)이 반영되지 않았다.

| 목표 | 사본(옛 누적) | 서버(현재) |
|---|---|---|
| 4단계 | 운동일 36 · 대체 54 | 단계 안 운동일 20 · 대체 30 |
| 5단계 | 운동일 60 · 대체 90 | 단계 진입 후 10주 · 대체 36일 |
| 6단계 | 시작 후 40주 | 단계 진입 후 12주 |
| 7단계 | 시작 후 60주 | 단계 진입 후 20주 |

화면 판정에는 안 쓰이고(서버 값을 쓴다) 시험·미리보기에만 쓰인다. `evaluateStageGate`의 "누적" 계산과
`evolution-gate.test.ts`·`evolution-gate.simulation.test.ts`도 단계 진입 후 기준으로 같이 고친다.
같은 사실을 두 곳에 두지 않는 원칙(CLAUDE.md) 위반이므로 §3과 함께 정리한다.

## 6. E — 난이도 상향은 데이터가 쌓인 뒤

- 진화 조건이 실제 적용된 구간을 통과한 사람이 **1명**(오뎅끼데스까 4→5단계)이라 달성 비율을 구할 수 없다.
- 그 1명은 요구(4종목 평균 +5%)의 약 3배(+16.5%)를 했고, 44일 동안 비교 가능한 16종목 중 7종목만 올랐다.
  → 어려운 쪽은 "퍼센트"가 아니라 "몇 종목이 같이 오르는가"다. 최종 단계는 종목 수 요구로 난이도를 조절한다.
- 5단계에서 오뎅끼데스까의 6단계 도전 기록을 몇 주 본 뒤 6·7단계 숫자를 정한다.
- 이전 단계 운동 종류가 적을 때 요구 종목이 1개로 줄던 구멍은 하한 3으로 막았다(0146).
- 규칙 버전(`rule_version`)은 올리지 않는다 — 올리면 기존 사용자의 기준 기록이 무효 처리된다.

**원인을 아직 모른다.** 그리고 **알 수가 없다** — 이게 첫 번째 고칠 것이다.

```

    } catch {
      setSaveError("저장하지 못했어요. 일정은 그대로 두었어요.");
```

`catch {}`가 오류를 **통째로 삼킨다.** 서버가 `program_plan_date_taken`인지
`program_plan_date_order`인지 다른 무엇인지 화면에도 콘솔에도 안 남는다.

**할 일 순서**

1. **오류를 드러낸다.** `catch (error)`로 받아 `program_` 접두 오류는 사용자에게
   뜻이 통하는 문구로 구분해 보여 주고, 그 외는 콘솔에 남긴다.
   지금은 진단이 불가능하다
2. 그 다음 진짜 원인을 고친다

**의심 후보 (확인 안 됨)**
- B 계정에 기존 어깨 프로그램 계획이 **19건**(08-05 ~ 09-20) 있어

  RPC가 다시 검사한다

  날짜만 1일씩 민다. 선호 요일이 아닌 날짜가 나오면 RPC의
  `program_scheduled_time_mismatch`에 걸릴 수 있다
- 재현: B 계정, `소매를 채우는 팔`, `다음 주 시작`, 직접 선택 금·토·일

## 3. 이 작업에서 배운 것 — 다음 사람이 반복하지 않도록

**① `catch {}`는 진단을 불가능하게 만든다.** 2.1이 그 대가다. 서버 오류를
사용자 문구로 바꾸더라도 원문은 어딘가 남겨야 한다.

**② 제약은 여러 겹에 흩어져 있다.** 회복 간격은 **다섯 곳**에 있었다 —
`validateSlots`, 배치 커서, 재배치 커서, `isAvailableProgramDate`,
클라 RPC 인자 검증, 그리고 DB 함수 두 개. 네 곳을 고치고 테스트가 다섯 번째를
잡았다. 제약을 풀 때는 **먼저 전수 grep**한다.

**③ 조회 결과의 용도가 다르면 함수를 나눈다.** `getLastRecordedSets`에 체감을
실었다면 '직전 기록 불러오기'가 draft에 그대로 담아 **피드백 시트가 영영 안 떴을**
것이다. `getProgramLoadEvidence`를 따로 만든 이유가 이것이고 주석에 박아 뒀다.

**④ 화면 확인이 단위 테스트를 대신하지 못하고, 반대도 마찬가지다.** 자동 종료
버그는 1800개 테스트가 전부 초록인 상태에서 **코드 리뷰**로 잡혔고, 검증은
`window.confirm`을 계측한 **화면 조작**으로만 가능했다.

**⑤ 적용된 마이그레이션은 고치지 않는다.** 0069는 0066의 두 함수를 통째로 다시
만들었다. 본문은 파일이 아니라 `docs/db-current-schema.sql`의 현행 정의에서
옮겼다 — 같은 함수를 여러 파일이 덮어쓰기 때문이다.

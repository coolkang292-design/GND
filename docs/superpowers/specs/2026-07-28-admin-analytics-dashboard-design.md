# 관리자 분석 대시보드 실데이터 연동 — 설계

- 날짜: 2026-07-28
- 원본 목업: `docs/dashboard-source.html` (ChatGPT 생성 프로토타입, 샘플 데이터)
- 목표: 목업의 레이아웃·차트를 유지한 채 표시 데이터를 운영 Supabase 실값으로 교체하고, GND 앱 안 관리자 전용 경로에서 서빙한다.

## 1. 배경과 결정

목업은 `gnd-analytics-dashboard...chatgpt.site`에 호스팅돼 있고 하드코딩된 `periods`/`users` 배열로 그려진다. 사용자 결정 2건:

1. **운영 위치 = GND 앱 안 관리자 페이지.** chatgpt.site를 유지하고 읽기 API를 여는 안은 기각했다. 운영 데이터가 외부 호스트로 나가고, CORS·토큰이 붙은 공개 API 표면이 새로 생겨 관리 부담이 는다. 앱 안에 두면 기존 Supabase 세션을 그대로 쓰고 배포 파이프라인도 하나다.
2. **관리자 게이트 = 환경변수 허용목록.** 마이그레이션 0건, 게이트 1곳, RLS 정책 무변경.

### 1.1 반드시 알고 시작할 것 — 표본 크기

2026-07-27 계정 정리 후 운영 DB는 **실계정 4명 · 크루 1개(리얼GND, 멤버 3명)** 이다.

목업의 112명·638회·D28 31%는 전부 샘플이다. 실데이터를 붙이면 활성 사용자는 한 자리 수, D28 리텐션 코호트는 0~1명이 된다. **이 설계는 지표를 크게 보이게 만들지 않는다.** 작은 표본에서 비율을 큰 글씨로 띄우는 것은 그 자체로 거짓 정보이므로, §4.6의 표본 표기 규칙을 모든 비율에 강제한다.

## 2. 아키텍처

```
/admin  (src/app/admin/)
  page.tsx            서버 컴포넌트 — requireAdmin() → 조회 → 집계 → 렌더
  _components/*.tsx   목업 마크업 이식 (사이드바·KPI·차트·퍼널·표)
  layout.tsx          목업 CSS를 스코프해서 적용

src/lib/admin/
  auth.ts             requireAdmin() — 유일한 접근 관문
  queries.ts          service_role 원본 행 조회 (서버 전용)

src/lib/domain/
  analytics.ts        순수 집계 함수 + TDD  ← 로직의 단일 원천
```

- `(tabs)` **밖**에 둔다. 하단 네비게이션·PWA 셸이 안 붙어 목업의 사이드바 레이아웃이 그대로 산다.
- 기간 전환은 `?period=7|28|90` 서버 렌더. 클라이언트 상태·재조회가 없다.
- **원본 DB 행과 service_role 키는 브라우저에 전달하지 않는다. 화면에 필요한 집계 결과와 사용자 목록만 서버에서 계산해 전달한다.** (집계 숫자와 사용자 목록 자체는 HTML·RSC 페이로드로 브라우저에 도달한다 — 이를 막는 것이 아니라, 원본 행·비표시 필드·키가 새지 않게 하는 것이 목적이다.)

## 3. 접근 통제

### 3.1 게이트

`src/lib/admin/auth.ts`:

```
requireAdmin():
  세션 없음                     → notFound()
  ADMIN_USER_IDS 미설정/빈 값   → notFound()   (fail-closed)
  세션 uuid ∉ 허용목록          → notFound()
  통과                          → { userId }
```

- **404를 쓴다(403 아님).** 403은 "여기 관리자 페이지가 있다"를 알려준다. 존재 자체를 숨긴다.
- **환경변수 미설정 시 전원 차단(fail-closed).** 설정 누락이 전면 개방으로 이어지면 안 된다.
- uuid 비교는 공백 제거 후 정확 일치. 부분 일치·prefix 매칭 금지.

`ADMIN_USER_IDS` = 쉼표 구분 uuid. Vercel Production 환경변수. `NEXT_PUBLIC_` 접두사 없음(클라 번들 미포함).

### 3.2 게이트 뒤 데이터 접근

통과 후에만 `getSupabaseAdminClient()`(service_role)를 쓴다. **RLS 정책은 한 줄도 바꾸지 않는다** — 관리자 select 정책을 8개 테이블에 뿌리면 정책 하나만 느슨해도 사용자 앱에서 남의 데이터가 샌다. 우회 경로를 게이트 1곳으로 모은다.

게이트가 유일한 방어선이므로 다음을 강제한다:

- `/admin` 응답에 `no-store` — CDN·중간 캐시에 집계 결과가 남지 않는다.
- 클라이언트 컴포넌트(CSV)로 내려보내는 필드는 **CSV에 실제로 들어가는 항목으로 한정**한다. 화면에 안 쓰는 uuid·이메일·원본 타임스탬프는 서버에서 잘라낸다.

### 3.3 게이트 테스트 (필수)

1. 비로그인 → 404
2. 로그인했으나 허용목록 밖 → 404
3. `ADMIN_USER_IDS` 미설정 → 관리자 uuid로도 404
4. 허용목록 안 → 200

## 4. 지표 매핑

기준 시각대는 전부 **KST(`Asia/Seoul`)**, 완료 세션은 `status='completed' and deleted_at is null`.

### 4.1 KPI 4장

| 카드 | 계산 | 원천 |
|---|---|---|
| 활성 사용자 | 기간 내 완료 세션의 distinct `user_id` | `workout_sessions` |
| └ 신규 +N명 | 기간 내 `created_at` | `profiles` |

**`profiles` 기준과 `auth.users` 기준을 섞어 쓰는 이유(의도된 것)**: KPI의 "신규"는 온보딩을 실제로 끝낸 사람이 몇 명 늘었는지를 뜻하므로 `profiles`를 센다. 반면 퍼널 최상단(§4.5)은 이탈 지점을 찾는 것이 목적이므로 `auth.users`를 센다 — 그래야 온보딩을 시작만 하고 프로필을 안 만든 사람이 "프로필 설정" 단계의 이탈로 잡힌다. 두 숫자는 다를 수 있고, 다른 것이 정상이다. 화면에도 각각 무엇을 세는지 표기한다.
| 완료 운동 | 기간 내 완료 세션 수 | `workout_sessions` |
| └ 취소 N회 | 기간 내 `status='cancelled'` | `workout_sessions` |
| 운동 완료율 | `completed / (completed + cancelled + 방치)` | §4.2 |
| 1인당 운동 | 완료 세션 수 / 활성 사용자 | 파생 |
| └ 상위 25% | 사용자별 완료 수의 p75 | 파생 |
| 증감(↗x%) | 직전 동일 길이 구간 대비 | 파생 |

증감은 **직전 구간 값이 0이면 퍼센트를 표시하지 않는다**(0→5는 ∞%). `신규` 같은 절대 증감으로 대체한다.

### 4.2 "방치" 정의

`started_at`이 있고 `status in ('active','draft')`이며 시작 후 **6시간**이 지난 세션. 6시간은 피드의 "운동 중" 판정(`activeSessionIds`)과 같은 값을 쓴다 — 화면마다 다른 기준을 쓰면 어긋난다. 상수는 한 곳에서 공유한다.

### 4.3 일별 활성 사용자 / DAU·WAU·MAU

날짜별(KST dayKey) distinct 완료 사용자. DAU=1일, WAU=7일, MAU=28일, DAU/MAU 비율. 막대 라벨은 기간별로 목업과 같은 규칙(7일=요일, 28/90일=날짜 간헐 표기).

### 4.4 리텐션 — **정의 변경**

목업의 "유저 재방문 D1/D7/D28"은 **구현 불가**다. 방문·페이지뷰·로그인 이벤트를 수집하지 않는다. `auth.users.last_sign_in_at`은 마지막 1개 값뿐이라 코호트 계산에 못 쓴다.

→ **"재운동 리텐션"으로 라벨과 정의를 함께 바꾼다.** 가입일 코호트가 가입 후 D1/D7/D28 시점에 운동을 완료했는가. 원천은 `profiles.created_at` + 완료 세션. 화면 문구도 "재방문"이 아니라 "재운동"으로 쓴다 — 측정하지 않은 것을 측정한 척하지 않는다.

목업의 인사이트 문구("첫 3회 완료 유저는 D7 재방문 1.8배")는 **넣지 않는다**. 4명 표본에서 배수를 계산하면 숫자 장난이 된다.

### 4.5 활성화 퍼널 — **단계 변경**

목업 3단계 "운동 계획 생성"은 **실제 앱 흐름과 다르다.** `workout_plans`는 온보딩 단계가 아니라 선택 기능인 예정표이고, 온보딩은 `profile → crew(또는 혼자 시작) → done`이다. 대부분의 사용자는 계획을 한 번도 만들지 않고 바로 기록한다. 목업대로 두면 **이탈이 아닌 것이 거대한 이탈로** 보인다.

**퍼널을 4단계로 줄인다:**

| 단계 | 원천 |
|---|---|
| 가입 완료 | `auth.users.created_at` |
| 프로필 설정 | `profiles` 행 존재 |
| 첫 운동 완료 | 완료 세션 ≥1 |
| 3회 운동 완료 | 완료 세션 ≥3 |

가입은 `profiles`가 아니라 `auth.users` 기준이다 — 온보딩을 끝내지 않은 익명 세션(2026-07-27에 24개 정리)이 "프로필 설정" 단계의 이탈로 정확히 잡혀야 한다.

**크루 단계를 퍼널에서 뺀 이유**: 온보딩의 "혼자 시작하기"는 **DB에 아무 흔적을 남기지 않는다**(`setStep("done")`만 하고 쓰기 없음). 그래서 "혼자 온보딩을 끝낸 사람"과 "크루 단계에서 이탈한 사람"을 구분할 방법이 현재 없다. `group_members` 존재만으로 단계를 만들면 혼자모드 사용자가 크루 없이 첫 운동을 완료해 **다음 단계 수가 이전 단계보다 커지는** 비단조 퍼널이 되어 읽을 수 없게 된다.

→ **크루 참여율은 퍼널 단계가 아니라 독립 지표로** 표시한다(`group_members`가 있는 사용자 / 전체 프로필 수). 위치는 퍼널 패널 헤더 우측(목업에서 "신규 29명"이 있던 자리 옆). 퍼널의 단조성을 지키면서 크루 도입률도 볼 수 있다.

혼자 온보딩 완료를 정확히 측정하려면 온보딩 완료 시각을 기록하는 컬럼이 필요하다 — §6 범위 밖.

### 4.6 표본 표기 규칙 (모든 비율에 적용)

- 비율 옆에 모수를 항상 병기: `50% (2/4)`
- **모수 < 5면 비율을 표시하지 않고 `2/4명`만** 표시한다.
- 모수 0이면 `—`. 0%로 쓰지 않는다(측정 불가와 0은 다르다).

### 4.7 진행 중 챌린지

`challenges.status='active'`. 이름·D-day는 `name`·`end_date`. 참여 인원은 해당 `group_id`의 `group_members` 수. 달성률은 **기존 `getActiveChallengeRanking()`을 재사용**한다 — 챌린지 화면과 같은 계산을 써야 두 화면이 안 어긋난다.

### 4.8 사용자 표

| 열 | 원천 |
|---|---|
| 사용자 | `profiles.nickname` · `avatar_url` |
| 성장 단계 | `user_progress` + `level_definitions.stage_name` |
| 기간 내 운동 | 선택된 기간의 완료 세션 수 |
| 스트릭 | `domain/streak.ts`의 `currentStreak()` |
| 마지막 활동 | 최신 `completed_at` |
| 상태 | 활성 ≤7일 · 주의 8~14일 · 휴면 15일+ (마지막 완료 기준, 완료 0건은 휴면) |
| 이탈 위험 | 낮음 <5일 · 중간 5~13일 · 높음 14일+ |

표에는 완료 세션이 0건인 사용자도 포함한다(휴면 발견이 이 표의 목적이다). 목업의 열 이름은 "28일 운동"으로 고정돼 있으나, **기간 선택(7/28/90)에 따라 열의 값과 헤더 문구가 함께 바뀐다** — 90일을 골랐는데 "28일 운동"이라 쓰여 있으면 틀린 화면이다.

이탈 위험 경계 5일은 `STREAK_EXPIRY_DAYS=5`와 같다. 앱이 "불꽃 살아있음"을 보여주는 사용자가 관리자 화면에서 "위험"으로 뜨면 안 된다.

### 4.9 성장·XP 탭 (신설)

목업 사이드바의 `#levels` 링크는 **대응 섹션이 없는 죽은 링크**다. 데이터는 충분하므로 새로 만든다.

- 레벨·7단계 분포 (`user_progress`)
- XP 획득 원천 분해 — 운동·시간·기록·사진 보너스별 (`xp_transactions.reason`)
- 포인트 발행량·잔액 (`point_transactions`, `user_wallet`)
- 배지 30종 획득 분포 · 희귀도별 완료율 (`user_badges` + `badge_definitions.rarity`)

## 5. 계산 위치

원본 행은 service_role로 읽고 **집계는 `src/lib/domain/analytics.ts` 순수 함수**에서 한다. TDD로 작성한다 — 저장소의 기존 도메인 로직(`streak.ts`·`achievements.ts`·`progression.ts`)과 같은 방식이다.

**어긋나면 조용히 틀리는 지점은 기존 함수를 그대로 호출한다:**

- 스트릭 → `currentStreak()` (홈 🔥와 동일)
- 레벨·단계 → `getLevelProgress()` (내 정보와 동일)
- 챌린지 달성률 → `getActiveChallengeRanking()` (챌린지 화면과 동일)

대시보드가 자체 계산을 두면 "관리자 화면 12일 / 앱 7일"이 생긴다. 이 저장소가 `streak-parity-check.mjs`로 계속 막아온 계열의 버그다.

**성능 한계 명시**: 현재 규모(4명·수백 세션)에서 전 행을 TS로 집계하는 것은 문제없다. **완료 세션이 약 5,000건을 넘으면 SQL 집계(RPC 또는 뷰)로 옮겨야 한다.** 지금 SQL로 만들면 테스트하기 어려운 로직이 늘 뿐이다.

## 6. 범위 밖

명시적으로 하지 않는 것:

- **방문·페이지뷰 수집 배선** — 진짜 "재방문" 리텐션을 원하면 별도 스펙이 필요하다.
- **온보딩 완료 시각 기록** — "혼자 시작하기"가 DB에 흔적을 안 남기는 문제(§4.5). 고치려면 `profiles`에 컬럼 하나와 온보딩 쓰기가 필요하다. 이번 대시보드 작업에 끼워 넣지 않는다.
- 목업의 인사이트 문구(D7 1.8배 등) — 표본이 쌓인 뒤.
- 관리자 쓰기 기능(계정 정지·데이터 수정) — 이번은 **읽기 전용**이다.
- `docs/dashboard-source.html`은 참조용으로 남기고 배포에 포함하지 않는다.
- 실시간 갱신·웹소켓. 요청 시점 스냅샷이다.

## 목표

운동 기록 앱에 영구 성장 시스템을 추가한다.

```
유효 운동 완료 → 서버 XP 계산 → XP 원장 기록 → 누적 XP 증가
→ 레벨 상승(1~35) → 5레벨마다 캐릭터 단계 진화(1~7) → 레벨 보상 해금
```

핵심 4가지: ①서버 기반 XP 지급 ②35레벨/7단계 계산 ③단계별 캐릭터 전환 ④홈·내 정보·운동 완료 화면에 성장 정보 표시.

## 범위

**포함**: 캐릭터 진화, XP 내역, 주간 XP 요약, 다음 단계 미리보기, 레벨 혜택 잠금·해금 표시, 보상 지급 원장, 불꽃 보호권 재고, 성장 타임라인.

**제외**(이번 스프린트): 팀전/팀 챌린지, 캐릭터 의상·아이템·상점·꾸미기, 유료 재화, XP 배율 상품, 아이템 거래, 중량·칼로리 기반 XP, 자유 입력 시간만으로의 XP.

## 2. XP 규칙 (확정)

XP는 운동량의 절대치가 아니라 **행동**을 보상한다. 중량·속도·칼로리·종목 수는 XP에 직접 반영하지 않는다. 초보자와 숙련자가 동일 기준으로 축적할 수 있어야 한다.

### 운동 1회 XP

| 항목 | XP | 조건 |
|---|---|---|
| 기본 완료 | 100 | 유효 운동 완료(§3) |
| 시간 보너스 | 0~40 | 서버 계산 시간 구간(아래) |
| 계획 완료 | +20 | 계획의 필수 운동·세트 모두 수행(§5) |
| 기록 완성 | +10 | 필수 기록 충실(§6) |
| 인증사진 | +10 | 사진 연결(§8) |
| **운동 1회 최대** | **180** | (주간 보너스 제외) |
| 주간 목표 달성 | +100 | 별도 지급(§ 주간) |

**시간 보너스** (정비례 금지, 1분=1XP 금지):

| 시간 | 보너스 |
|---:|---:|
| 0~19분 | 0 |
| 20~39분 | 10 |
| 40~59분 | 20 |
| 60~89분 | 30 |
| 90분+ | 40 (상한) |

90/180/300분 모두 +40 고정.

## 3. 유효 운동 기준 (🔴 타바타 보완 포함)

시작 버튼만으로는 지급하지 않는다. 상태가 `completed`여야 하고 시작·완료 시각이 존재해야 한다.

- **웨이트**: 완료 세트 3+ , 각 완료 세트에 reps 기록. 중량 0kg 허용(맨몸 스쿼트·푸시업·풀업).
- **맨몸**: 완료 세트 3+ , 각 세트에 reps 또는 완료 여부 기록.
- **유산소**: 유산소 기록 시간 10분+ 또는 서버 세션 시간 10분+.
- **혼합**: 완료 세트 3+ 또는 유산소 10분+ 또는 계획 최소 완료 조건 충족.

### 🔴 3.1 타바타 운동 (신설 — 원 지시서 누락)

타바타는 이 앱의 1급 완료 경로다(음원 종료 시 자동 완료). 그러나 **타바타 세트는 실적 reps가 0으로 기록**되고 시간이 짧아(4/8/16분), 위 "3세트+reps" 기준을 통과하지 못한다. 별도 분기를 둔다.

- 타바타 세션(`workout_sessions.tabata_minutes IN (4,8,16)`)은 **완료 자체를 유효 운동으로 인정**한다(세트 reps 검사 면제).
- 시간 보너스는 **서버 세션 시간**이 아니라 `tabata_minutes`를 기준으로 §2 구간에 적용한다(예: 16분 → 0 XP 구간 아님, 20분 미만이라 0. 정책상 타바타는 짧으므로 대부분 기본 100 XP만).
- 타바타는 계획/기록 완성 보너스 대상이 아니다(구성이 고정). 인증사진 보너스는 동일 적용.
- 판정 함수는 타바타 여부를 입력으로 받아 분기한다.

## 4. 운동시간 계산 (⚠️ round/floor 보완)

클라이언트가 보낸 임의 `duration` 값을 XP에 쓰지 않는다.

**🔴 보완**: 원 지시서 §4.1은 `floor(sec/60)`을 제안하나, `complete_workout`은 이미 **`greatest(1, round(sec/60))`**로 `duration_minutes`를 저장한다. 서로 다르면 경계에서 어긋난다(예 19.7분: round=20→보너스 대상, floor=19→0 XP). **XP는 세션에 저장된 `duration_minutes`를 그대로 사용**한다. 재계산하지 않는다.

**비정상 시간**(제외 또는 검토 표시): 완료<시작, 음수, 6시간+, 시작/완료 시각 없음. 6시간+ 기록은 자동 지급하지 않고 로그만 남긴다.

원장 metadata에 `duration_minutes`, `duration_source: "server_elapsed"`, `duration_capped` 저장. 향후 일시정지 기능 대비해 계산 함수는 독립적으로 작성한다.

## 5·6·8. 보너스 판정 요약

- **계획 완료(+20)**: 계획 필수 운동·세트 전부 수행(유산소는 계획 최소 시간 충족). 계획 없이 즉흥이면 0. 계획-실행 연결을 알 수 없으면 **추측 금지, 0 반환** 함수만 둔다.
- **기록 완성(+10)**: 완료 세트에 reps 존재, 웨이트 세트는 weight ≠ null(맨몸 0 허용), 빈 종목·빈 세트 없음. 유산소는 앱 필수값(현재 시간만) 충족 시 인정.
- **인증사진(+10)**: 🟡 **진실 소스 = `workout_sessions.verification_status ≠ 'none'`** (photo_uploaded/camera_verified). 해당 운동과 연결·본인·삭제 안 됨. 완료 시 사진 없으면 사진 XP 제외 후, **완료 30분 이내** 추가 시 별도 원장 거래로 +10(§9.2). 여러 장이어도 1회만.

## 7. 레벨·단계 정의 (⚠️ 기존 level.ts와 명칭 분리)

**🔴 보완**: 이미 `src/lib/domain/level.ts`에 **챌린지 전용 5단계 임시 레벨**이 있다. 새 영구 시스템은 별도 모듈(`src/lib/domain/progression.ts` 권장)에 두고, UI·명칭에서 "챌린지 레벨"과 "성장 레벨"을 분명히 구분한다. 함수는 `getLevelFromTotalXp` 등 신규 이름 사용.

### 7단계 × 5레벨 = 35레벨

| 단계 | 레벨 | 캐릭터 파일 | 상태 설명 |
|---|---|---|---|
| 개노답 | 1~5 | `char-1.png` | 생각 많고 아직 안 움직임 |
| 눈떴개 | 6~10 | `char-2.png` | 문제 깨닫고 첫 행동 시작 |
| 일단하개 | 11~15 | `char-3.png` | 완벽하지 않아도 바로 행동 |
| 물고가개 | 16~20 | `char-4.png` | 목표 하나를 물고 놓지 않음 |
| 미쳐보개 | 21~25 | `char-5.png` | 실행에 완전히 빠져든 상태 |
| 판을짜개 | 26~30 | `char-6.png` | 결과로 새로운 판을 만듦 |
| 전설이개 | 31~35 | `char-7.png` | 실행이 정체성이 된 상태 |

누적 XP 컷: Lv.1=0, 이후 단계별로 +200(1~5)→+400(6~10)→+600(11~15)→+800(16~20)→+1000(21~25)→+1200(26~30)→+1250(31~35). Lv.35=26,000. **Lv.35 이후 XP는 계속 쌓되 레벨은 35 고정** (`min(calculated, 35)`). 전체 컷 표는 원 지시서 §11.2와 동일하며 `level_definitions` seed로 관리한다.

**진행률**은 누적이 아니라 **현재 레벨 구간 기준**으로 계산: `(총XP − 현재레벨컷) / (다음레벨컷 − 현재레벨컷)`. Lv.35는 100%.

### 단계 명칭 (확정 2026-07-23)

**놀이안으로 확정**: 개노답 / 눈떴개 / 일단하개 / 물고가개 / 미쳐보개 / 판을짜개 / 전설이개. 목업 캐러셀의 간결안(각성/실행/집중…)은 폐기. `level_definitions.stage_name`에 놀이안을 seed한다.

## 8. 데이터 모델 (0022 마이그레이션)

테이블명은 기존 규칙을 따른다. 전부 서버(RPC/service_role)에서만 변경, 클라 직접 쓰기 금지.

- **`level_definitions`** (level PK, required_total_xp UNIQUE, stage_index 1~7, stage_key, stage_name, character_path, reward_key, reward_label). 사용자 읽기 허용·수정 금지.
- **`user_progress`** (user_id PK, total_xp, current_level 1~35, current_stage 1~7, streak_shield_count, last_level_up_at, last_stage_up_at). `total_xp`는 원장 합계 캐시.
- **`xp_transactions`** (id, user_id, amount, transaction_type earn/reverse/admin_adjustment, reason, reward_group, source_type, source_id, effective_date, metadata jsonb, reversed_transaction_id). **권장: 운동 XP 전체를 1거래**(`reason=workout_completed`, 세부는 metadata)로 저장. 사진 후등록만 별도 거래.
  - 중복 방지 인덱스: `(user_id, reason, source_type, source_id) where earn` + `(user_id, effective_date, reward_group) where earn and reward_group='daily_workout'`.
- **`user_unlocks`** (user_id+unlock_key PK, source_level, status unlocked/coming_soon, metadata).
- **`streak_shield_transactions`** (지급·소비 이력 원장; 재고값만 수정하지 않는다).

## 9. 서버 함수·RPC (🔴 원자성 보완)

순수 계산 함수와 DB 실행 함수를 분리한다.

- **순수**: `calculateWorkoutXp(input): WorkoutXpBreakdown` — 시간 보너스는 `getDurationXp(min)` 계단 함수. 하루 이미 수령 시 `rejectionReason: "DAILY_XP_ALREADY_AWARDED"`로 0 반환.

### 🔴 9.1 `complete_workout_v2` — 완료+XP 원자 처리

**보완 근거**: 현재 마무리는 `completeWorkout` RPC 후 클라에서 `markRecordBeaten`를 **또** 호출한다(2회 클라 호출 = 지시서 §18이 경고한 패턴). 여기에 XP를 3번째 클라 호출로 붙이면 부분 성공 위험이 커진다.

→ **`complete_workout_v2`가 상태 완료 + XP 계산·지급 + 레벨/단계 갱신 + 보상 지급을 한 트랜잭션**으로 처리한다. 가능하면 record-beaten 판정도 같은 트랜잭션으로 흡수한다. 검증 후 기존 호출을 교체한다(기존 `complete_workout`은 남겨 안전 롤백).

처리 순서: 인증 → 소유권 → completed 확인 → 시간 조회 → 유효성(타바타 분기) → KST effective_date → 당일 수령 여부 → 보너스 계산 → `xp_transactions` insert → `user_progress` 갱신 → 전/후 레벨·단계 계산 → 보상 지급 → 주간 목표 평가 → 결과 반환(`{awarded, xpAwarded, breakdown, previous/newLevel, levelUp, stageUp, unlockedRewards}`). 중간 실패 시 전체 롤백.

### 9.2 사진 후등록 XP

`set_workout_verification` 성공 경로에서 `award_workout_photo_xp(workout_id)` 호출: 본인·완료·30분 이내·사진 존재·기존 사진 XP 미지급·**해당 운동이 당일 기본 XP 대상이었는지** 확인 후 +10. 아니면 지급 안 함.

### 9.3 하루/주간 중복 방지

- **하루**: KST 기준 하루 최초 유효 운동 1건만 기본·시간·계획·기록·사진 XP. 2번째부터 XP 0(기록·통계는 반영). 키 `user_id + KST날짜 + daily_workout`.
- **주간**: 월 00:00 ~ 일 23:59:59 KST. 주간 목표 회수만큼 유효 운동일 달성 시 +100, 주 1회. 키 `user_id + week_start + weekly_goal_achieved`. **주간 목표 스냅샷**(주 첫 운동 시 목표 고정)으로 목표 변경 악용 차단.

## 10. RLS·분석 (⚠️ 분석 스텁)

**RLS**: 사용자는 자신의 `user_progress`/`xp_transactions`/`user_unlocks`/보호권 거래 조회 + 전체 `level_definitions` 조회만. 위 4개 테이블 클라 insert/update/delete 전면 금지(개발자도구로 `total_xp=999999` 시도해도 실패). 변경은 서버 RPC/service_role만.

**🟡 분석 보완**: 분석 인프라가 없으므로 **no-op 분석 인터페이스(`track(event, props)`)만 두고** 이벤트(`xp_awarded`, `level_up`, `stage_up`, `reward_unlocked`, `xp_award_rejected` 등)를 호출부에 심되 실제 전송은 후속으로 미룬다. PII·사진 URL은 절대 이벤트에 넣지 않는다.

## 11. 화면 구성 (목업 반영 — 이번 요청의 핵심)

목업 `운동과 성장의 도전.png` = **왼쪽 홈 / 오른쪽 내 정보**. 두 화면 모두 **구현 가능**하며, 매핑은 아래와 같다.

### 11.1 홈 (왼쪽) — 기존 유지 + 카드 1개 추가

홈은 "행동 중심"을 유지한다(지시서 §22). 현재 홈 렌더 순서([home-client.tsx](../../../src/components/home/home-client.tsx))는 대부분 목업과 이미 일치한다.

| 목업 요소 | 현재 컴포넌트 | 작업 |
|---|---|---|
| 헤더 "GND / 오늘도 GND 탈출하자" + 알림종 | `NotificationBell` | 유지 |
| 오늘의 운동 "운동 시작하기" | 기존 시작 Link + `PushEnableCard` | 유지(캐릭터 삽화만 교체 가능) |
| 스트릭 카드 | `StreakCard` | 유지 |
| 이번주/목표/스트릭 3타일 | `WeeklyStats` | 유지 |
| 크루 카드 | `CrewCard` | 유지 |
| 꾸준왕 열람권 | `KingCard` | 유지 |
| **나의 캐릭터 카드** (Lv.4 · 노답 단계 · 580/700 XP · 성장 보기 >) | **없음 → 신규** | **추가** |
| 운동 기록하기 버튼 | 기존 | 유지 |
| 하단 탭 | 기존 | 유지 |

→ **홈 변경은 "나의 캐릭터 카드" 1개 추가뿐**. `KingCard` 아래, 운동 기록하기 위에 삽입. `ProgressSummary` 1회 조회로 렌더. 이미지는 Next Image + 적정 `sizes`.

### 11.2 내 정보 (오른쪽) — 성장 허브로 재구성

현재 내 정보([profile/page.tsx](../../../src/app/(tabs)/profile/page.tsx))는 알림 설정만 있다. 이를 **성장 상세 허브**로 바꾸고, 기존 알림 설정은 우상단 톱니(설정)로 이동한다.

| 목업 섹션 | 내용 | 상태 |
|---|---|---|
| "나의 캐릭터 성장" + ? | 7단계 가로 캐러셀(완료/현재 강조/잠금 실루엣) | 신규 |
| 현재 단계 | 개노답 Lv.4, 상태 설명, 구간 진행바 82%, 다음까지 120 XP, "7단계 안내 >" | 신규 |
| 레벨 혜택 | Lv.5 스트릭 기능 해금 등 잠금·해금 표시 | 신규 |
| 다음 단계 미리보기 | 각성(눈떴개) 캐릭터 + 설명 + "Lv.6 달성 시 해금" | 신규 |
| 성장 타임라인 | Lv.1 첫 가입 ~ Lv.6 진입, 날짜·완료체크·잠금 | 신규 |
| "XP 획득 방법 보기" | 탭 시 XP 규칙 설명 시트(모달) 오픈 — 기본 100·시간 구간 표·계획/기록/사진 +α·주간 100·하루 1회 제한을 사람이 읽기 쉽게 표시 | 신규 |
| (기존) 알림 설정·PushSettings | 톱니 설정 하위로 이동 | 이동 |

잠긴 단계는 완전히 숨기지 않고 **실루엣/저채도 미리보기**로 진화 욕구 자극(지시서 §23). 조회 최적화: `ProgressSummary` + 7단계 정의 + 최근 XP 내역 + 해금 목록 + 타임라인.

### 11.3 운동 완료 화면

기존 완료 화면에 XP 결과 표시: 일반 완료(항목별 +XP 합계), 레벨업 모달(Lv.n→n+1 + 보상), 단계 진화 모달(개노답→눈떴개, 캐릭터 전환 강조). 애니메이션은 300~500ms 페이드 + 약한 빛 + 짧은 햅틱, **`prefers-reduced-motion` 존중**. 과한 영상·3D 금지.

### 11.4 목업 수치 주의

목업의 580/700 XP·82% 등은 **예시값**이다. 실제 표시는 `level_definitions` 컷을 따른다(숫자는 누적 기준 표시, 진행바는 구간 기준 계산 — 지시서 §22).

## 13. 운동 삭제·소급

- **완료 운동 삭제**(soft delete `deleted_at`): 이미 지급된 XP는 **반대 거래**(`transaction_type=reverse`, `reversed_transaction_id`)로 상쇄. 기존 거래 직접 수정 금지. 후 누적·레벨·단계 재계산(하락 가능). 이미 지급된 보호권은 자동 회수 안 함, 동일 레벨 재달성 시 `user_unlocks` 복합 PK로 중복 지급 차단.
- 🟡 **소급(backfill)**: 현재 실사용 계정이 전부 2026-07-19 이후 생성이라 과거 기록이 거의 없다 → **후속으로 미룸**. 진행 시 최근 90일·하루 1건·기본 100 XP만·`reason=historical_backfill`, **반드시 dry-run 승인 후** 운영 적용.

## 14. 테스트·검증 (⚠️ E2E 보완)

- **단위**: 시간 경계(0/9/10/19/20/39/40/59/60/89/90/120/359/360), 기본 100, 45분+전보너스 160, 95분+전보너스 180, 무효 0, 당일 2번째 0, 사진 다중 10, 계획없음 0, 음수·시각없음 거부, **타바타 유효·시간 분기**.
- **레벨 계산 경계**: 0→Lv.1, 200→Lv.2, 1,000→Lv.6, 6,000→Lv.16, 21,000→Lv.31, 26,000→Lv.35, 99,999→Lv.35.
- **중복 지급**: 동일 완료 RPC 2회·병렬·재시도·사진 병렬·주간 병렬 → 각 1회만.
- **RLS**: 타인 XP 조회 불가, total_xp 직접 수정 불가, 거래 직접 insert 불가, 정의 조회 가능·수정 불가.
- **통합**: Lv.4·580 XP → 45분 완료 → 160 지급 → 740 → Lv.5 → 보호권 지급 → 내역·홈·해금 반영. 단계 진화(990→운동→1,100→Lv.6→char-2→모달→새로고침 유지).
- **🟡 E2E 보완**: Playwright 인프라가 없다. 이번 스프린트는 **실기기 수동 검수로 대체**(이 프로젝트 확립 관행: 기능 완성→검증→사용자 실기기 확인→커밋). Playwright 도입은 별도 선행 태스크로 분리한다.
- **게이트**: `pnpm lint` / `pnpm typecheck` / `pnpm test` / `pnpm build` 통과 + 모바일(320px~, safe-area) 검수.

## 16. 완료 조건

핵심 운동 기록·피드·기본 통계는 **Lv.1부터 전부 사용 가능**(레벨로 막지 않는다). 아직 없는 혜택은 거짓 "사용 가능" 대신 **"준비 중"** 표시. 팀전·상점·꾸미기 코드 추가 금지. 불꽃 보호권 자동 소비는 `FEATURE_STREAK_SHIELD_AUTO_USE=false` 뒤에 비활성(재고·지급·표시만 구현). 서버 XP 계산·시간 구간·하루 1회·주간 1회·중복 방지·35레벨·7단계 매핑·3개 화면 표시·모달·보상 원장·RLS/단위/통합 테스트·빌드·실기기 검수 전부 충족 시 완료.

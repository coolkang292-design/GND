# 배지 카탈로그 + 포인트 경제 설계

작성일: 2026-07-27
선행 설계: `2026-07-25-badge-points-item-shop-design.md` (아이템 상점·장착 — 이 문서가 배지·포인트 부분을 대체한다)
목표 화면: 홈 캐릭터 → `/profile` (사용자 목업 기준)

---

## 1. 목표

지금 배지는 3개고 전부 "기록 갱신"에만 묶여 있다. 실보유 2건. 진열대가 비어 있고
딸 이유도 없다. 배지를 **6지표 30종**으로 늘리고, 배지와 운동에 **포인트**를 붙여
아이템 상점의 수입원을 만든다.

```
운동 완료 ─┬─→ 기본 포인트 × 불꽃 배수     (매번)
           └─→ 지표 재집계 → 배지 획득 → 티어 보너스 포인트
                                    ↓
                          프로필에서 확인 → 상점에서 소비
```

이 문서는 **배지와 포인트까지**다. 아이템·상점·장착은 선행 설계 소관이며 별도 스펙으로 간다.

## 2. 현황과 격차

| 영역 | 현재 | 필요한 것 |
|---|---|---|
| 배지 카탈로그 | 3개, 클라 상수 `BADGE_CATALOG` | 30종 + DB 데이터화 |

## 3. 핵심 결정

| # | 결정 | 이유 |
|---|---|---|
| B1 | 포인트는 **운동마다 + 배지 보너스** 양쪽에서 나온다 | 배지에서만 나오면 다 따는 순간 수입이 끊기고, 목업의 ⚡배수는 곱할 대상이 없어진다 |
| B2 | 불꽃 기준은 **홈 🔥와 동일**(사슬 방식, 4일까지 쉬어도 유지) | 앱 전체(스트릭 카드·아침 브리핑·보호권)가 이미 이 숫자를 쓴다. 두 숫자가 화면에 공존하면 버그로 보인다 |
| B3 | 그래서 배지 이름은 "연속"이 아니라 **"불꽃 N일"** | 실제로 쉬는 날이 껴도 이어지므로 "연속"은 사실과 다르다 |
| B4 | 불꽃 배지는 **5일이 쌓일 때마다 1개**씩 무제한 스택 | "사슬이 끊긴 뒤 다시 달성" 방식으로 하면 **배지를 더 받으려고 5일 쉬는 게 이득**이 된다. 이어가는 쪽이 항상 빨라야 한다 |
| B5 | 누적 지표(횟수·시간·볼륨·거리·기록갱신)는 **이정표 1회성** | 줄어들지 않는 값이라 반복이 성립하지 않는다 |
| B6 | 웨이트 볼륨을 **그대로** 지표로 쓴다 | 실측 편차 6배(하체 종목 유무)는 있으나, 실제로 더 든 것은 맞다. 임계값을 넓게 잡아 완화한다 |
| B7 | 배지 이름·설명은 **사물 비유 + GND 개 말투** | 숫자만으로는 5톤이 대단한지 감이 안 온다. 비유가 성취를 즉시 이해시킨다 |
| B8 | 배지 조건을 `badge_definitions` **테이블 데이터**로 뺀다 | 30종을 SQL 함수에 하드코딩하면 유지 불가. 배지 추가 = seed 한 줄 |
| B9 | 기존 `record_beaten_1/5/10` 보유분은 **그대로 흡수** | 이미 딴 배지가 사라지면 안 된다 |
| B10 | 포인트·배지 테이블에 `authenticated` **insert/update 권한 없음** | 기존 `xp_transactions`·`user_badges`와 동일. 앱을 뜯어도 위조 불가 |

## 5. 포인트 경제

### 5.1 획득

```
운동 완료 1회 = 100 P × 불꽃 배수
배지 획득    = 티어별 보너스 (반복형 불꽃은 획득할 때마다)
```

**불꽃 배수** — 목업의 `🔥27일 · ⚡x4`에 맞춘 구간이다.

| 불꽃 | 배수 |
|---:|---:|
| 0~4일 | ×1.0 |
| 5~9일 | ×1.5 |
| 10~14일 | ×2.0 |
| 15~24일 | ×3.0 |
| 25일~ | ×4.0 |

**티어 보너스**

| 티어 | 포인트 | 개수 |
|---|---:|---:|
| 🥉 | 300 P | 8 |
| 🥈 | 800 P | 9 |
| 🥇 | 2,000 P | 7 |
| 👑 | 5,000 P | 5 |
| 🔥 반복 | 500 P | 무제한 |

1회성 배지 29종 전부 = **48,600 P**(평생).

### 5.2 규모 검증

주 4회(월 16회) 사용자 기준:

| | 계산 | 결과 |
|---|---|---:|
| 불꽃 배수 도달 | 사슬이 유지되므로 운동일마다 +1 → 25일까지 약 6주 | ×4.0 |
| 성숙기 월수입 | 16회 × 400 P | 6,400 P |
| 불꽃 반복 배지 | 연 200운동일 ÷ 5 × 500 P | 20,000 P |
| 1회성 배지 | 1년차에 절반 정도 | 약 20,000 P |
| **1년차 총 수입** | | **약 110,000 P** |

목업의 드림 아이템(람보르기니 250,000 P)이 **약 2.3년**짜리 목표가 된다. 의도한 거리다.

### 5.3 배수가 영구화되는 것에 대하여

불꽃이 사슬 방식(B2)이라 주 2회만 해도 계속 늘어난다. 즉 6주쯤 지나면 대부분
×4.0에 도달해 **사실상 영구 4배**가 된다. 이것은 결함이 아니라 의도다 —
**5일 이상 쉬면 사슬이 끊겨 ×1.0으로 추락**하고, 복귀해도 ×4.0까지 다시 25 운동일이
걸린다. 벌칙이 강력해서 이탈 방지 장치로 작동한다.

### 5.4 목업 가격표와의 충돌

목업의 상점 가격(롤렉스 1,500 P · 조던 1,200 P)은 이 수입과 맞지 않는다.
운동 15회면 롤렉스를 사고, 조던과 값이 거의 같아 **명품의 위계가 사라진다**.
**가격표는 이 수입 구조에 맞춰 다시 짜야 한다** — 아이템 스펙에서 다룬다.
이 문서는 수입만 확정한다.

## 6. 데이터 모델

### 6.1 배지 정의 (신규)

```
badge_definitions
  badge_key      text pk
  name           text        -- "🐘 코끼리 한 마리"
  description    text        -- "개가 코끼리를 이겼개"
  emoji          text
  tier           text        -- bronze | silver | gold | legend
  metric_key     text        -- §6.3 지표 6종
  threshold      numeric     -- 임계값 (거리는 m, 볼륨은 kg, 시간은 분)
  point_reward   int
  repeatable     boolean     -- true면 스택 (불꽃 5일만)
  repeat_step    numeric     -- 반복 간격 (불꽃 = 5)
  sort_order     int
  status         text        -- active | hidden
```

### 6.2 보유 배지 (기존 확장)

```
user_badges
  user_id, badge_key,
  period_key   text not null default 'lifetime'   -- 반복형은 달성일 KST 'YYYY-MM-DD'
  session_id, earned_at
  primary key (user_id, badge_key, period_key)    -- 기존 (user_id, badge_key)에서 확장
```

기존 행은 `period_key = 'lifetime'`으로 자동 편입된다(default). **데이터 손실 없음.**

**반복형 멱등 키 설계** — 불꽃 배지는 `period_key = 달성한 날(KST)`을 쓴다.
불꽃은 하루에 최대 1 늘어나므로 같은 이정표를 같은 날 두 번 밟을 수 없다.
따라서 `(user, 'streak_5', '2026-07-26')`은 유일하고, 사슬이 끊긴 뒤 다시 5일을
채우면 **다른 날짜 = 다른 행**이 되어 자연히 스택된다. 사슬 시작일을 계산할 필요가 없다.

### 6.3 지표 6종

`evaluate_badges(p_user_id)` 하나가 아래를 한 번에 집계한다.

| `metric_key` | 산출 | 단위 |
|---|---|---|
| `workout_count` | `workout_sessions` completed · `deleted_at is null` | 회 |
| `total_minutes` | 위 세션의 `sum(duration_minutes)` | 분 |
| `streak_days` | 위 세션의 KST 날짜 distinct → **간격 5일 미만이면 사슬 유지**(`domain/streak.ts`와 동일 규칙) | 일 |
| `weight_volume_kg` | 완료된 **weight** 세트의 `sum(weight_kg × reps)` | kg |
| `cardio_distance_m` | 완료된 **cardio** 세트의 `sum(distance_meters)` | m |
| `record_beaten` | `record_note is not null` 세션 수 | 회 |

### 6.4 포인트 원장·지갑 (신규)

`xp_transactions` 구조를 그대로 복제하되 **음수(사용)를 허용**한다.

```
point_transactions
  id, user_id
  amount          int      -- 양수=적립, 음수=사용
  transaction_type text    -- earn | spend | refund | admin_adjustment
  reason          text     -- workout_completed | badge_earned | item_purchase | refund | admin_adjustment
  source_type, source_id
  multiplier      numeric  -- 지급 시점 배수 (감사·설명용)
  balance_after   int      -- 감사용 스냅샷
  rule_version    text default 'point_v1'
  metadata        jsonb
  created_at
  unique (user_id, reason, source_type, source_id) where transaction_type = 'earn'

user_wallet
  user_id pk
  balance         int not null default 0 check (balance >= 0)
  lifetime_earned int not null default 0
  updated_at
```

`balance >= 0` 체크 제약 + 구매 시 행 잠금 → 동시 구매로 잔액이 마이너스가 되는 것이
**DB 레벨에서 불가능**하다. 유니크 인덱스가 중복 지급을 막는다.

## 7. 판정·지급 엔진

### 7.1 흐름

```
evaluate_badges(user)
  1. 지표 6종 집계 → jsonb metrics
  2. badge_definitions ⋈ metrics
       · 1회성: metric >= threshold  &  (user, key, 'lifetime') 미보유
       · 반복형: streak_days > 0  and  streak_days % repeat_step = 0
                 → (user, key, 오늘KST) 미보유일 때 지급
  3. user_badges insert (on conflict do nothing)
  4. 신규 배지마다 award_points(user, point_reward, 'badge_earned', badge_key)
  5. 신규가 있으면 notifications 1건 (type='badge_earned')
```

**호출 지점** — 전부 기존 정의자 RPC 끝에 한 줄 추가한다.

| 지점 | 갱신되는 지표 |
|---|---|
| `complete_workout_v2` | 횟수·시간·불꽃·볼륨·거리 |
| `mark_record_beaten` | 기록 갱신 — **기존 하드코딩 배지 블록은 제거**하고 이걸로 대체 |

`evaluate_badges`는 멱등이다. 여러 번 불려도 `on conflict do nothing`과 포인트 원장의
유니크 인덱스가 중복 지급을 막는다.

### 7.2 운동 포인트 지급

`complete_workout_v2` 안에서 XP 지급 직후:

```
불꽃 = streak_days 재계산
배수 = 구간표 조회
포인트 = 100 × 배수
award_points(user, 포인트, 'workout_completed', session_id, 배수)
```

**하루 1회 제한은 XP와 동일하게 적용**한다 — 같은 날 두 번째 운동은 포인트 0.
XP만 하루 1회고 포인트는 무제한이면 하루에 여러 번 짧게 끊어 하는 악용이 생긴다.

## 9. 보안·정합성

1. `badge_definitions`·`point_transactions`·`user_wallet`은 `authenticated`에게
   **select만**. 변경은 security definer RPC 경로뿐.
2. `user_wallet.balance`는 캐시다. 원장 `sum(amount)`로 언제든 재계산·검증 가능
   (0030에서 `user_progress`에 쓴 방식과 동일).
3. 임계값의 단일 원천은 `badge_definitions` 행이다. 클라이언트는 표시만 한다.
4. 불꽃 판정 SQL은 `domain/streak.ts`와 **같은 규칙**이어야 한다. 어긋나면 홈 🔥와
   배지가 다른 숫자를 말한다 — 실 DB 테스트로 양쪽을 대조한다.

## 10. 검증

| 층 | 방법 |
|---|---|
| 도메인 | 배수 구간·반복 배지 횟수 계산을 순수 함수로 분리해 TDD (`src/lib/domain/`) |
| SQL | 실 DB 스크립트 — 30종 각 임계값 경계, 불꽃 스택(5·10·15일 연속 달성 → 3개), 사슬 끊김 후 재달성 → 4개째, 하루 2회 운동 시 포인트 0, `evaluate_badges` 멱등 |
| 불꽃 대조 | 같은 세션 집합으로 `currentStreak()`(TS)와 SQL 집계가 **같은 값**을 내는지 |
| 마이그레이션 | `user_badges` PK 변경 후 기존 2건이 `period_key='lifetime'`으로 살아있는지 |
| 실기기 | 운동 완료 → 포인트·배지 획득 → 프로필에서 확인까지 폰에서 1회 완주 |

# 알림 시각 개인화 — 평소 운동 시작 30분 전 (2026-08-13)

> 사용자 지시: *"알림은 매일 오전 9시에 고정하는 게 아니라 이전 운동시간에 맞춰서
> 내보내는 게 더 효율적이지 않을까?"* → *"진행하자. 다만 지난 운동시간보단
> **30분 전**으로 알림 내보내게 하자."*

---

## 1. 지금 무엇이 문제인가

| 사실 | 근거 |
|---|---|
| 브리핑은 하루 1회, 전원 같은 시각 | `vercel.json` — `0 0 * * *` (UTC 0시 = KST 9시) |
| 유저별 시각 게이트가 **이미 있는데 꺼져 있다** | `buildBriefings`의 `invocationHourOverride ?? hourOfDay(...)`. 크론이 `?hour=9`를 넘겨 전원을 9시로 강제한다 |
| 코드가 그걸 스스로 경고한다 | `briefing.ts` 주석 — *"프로덕션 다중 tz 판정은 override를 생략해야 유저별 게이트가 동작한다"* |

저녁형 사용자에게 오전 9시 알림은 **결정 10시간 전**이다. 스트릭은 그날 자정에
끊기므로, 알림의 가치는 *운동하러 갈지 아직 안 정한 순간*에 있다.

⚠️ **에이전트가 제안한 방향과 다르다.** 제안은 "평소 시각이 **지났는데** 아직 안 함"
이었다 — 이미 운동하러 가는 사람에게 보내는 소음을 피하려는 것이었다. 사용자는
**30분 전**(준비를 재촉하는 쪽)으로 정했다. 사용자 결정이므로 그대로 간다.
문구는 지금도 단계별로 갈리므로(오늘 이미 했으면 `오늘 완료! 🔥 …`) 30분 전에 오는
알림이 틀린 말을 하지는 않는다.

## 2. 근거 진실

1. **크론 해상도가 알림 해상도의 상한이다.** 하루 1회 크론으로는 유저별 시각을 낼 수 없다
2. **`started_at`이 있다** (`workout_sessions`, 0006~ RPC들이 쓴다). `completed_at`으로
   추정하면 **끝난 시각**이라 알림이 이미 늦다
3. **표본이 없는 사용자가 있다.** 기록 2건에는 "평소 시각"이 없다
4. **하루 한 번은 이미 보장된다.** `dedupe_key = morning_briefing:<user>:<로컬 날짜>` —
   크론을 30분마다 돌려도 중복 발송이 안 난다. 이게 이 설계를 값싸게 만든다
5. **전량 조회는 조용히 잘린다.** 라우트 주석이 이미 경고한다 — PostgREST 기본
   상한 1000행. 하루 1회일 땐 넘어갔지만 **30분마다면 48배**로 돈다

## 3. 설계

### 3.1 슬롯 — 30분 · 알람시계는 **Supabase pg_cron** (무료)

⚠️ **Vercel 크론으로는 못 한다.** Hobby 요금제는 크론이 하루 1회다. 개인화는 각자의
슬롯(예: 18:30)에 호출이 와야 성립하므로, 하루 1회면 그 시각에 걸린 사람만 받는다.

그래서 **DB가 알람시계**를 맡는다 (`0075_briefing_cron_30min.sql`). 인프라가 늘지
않는다 — `pg_net`은 0016(푸시 트리거)이 이미 깔아 뒀고, pg_cron은 Supabase 무료
요금제에서 쓸 수 있다.

```
pg_cron(30분) → /api/briefing → notifications INSERT
                                   → 0016 트리거 → /api/push/notify → 기기 푸시
```

⚠️ **판정 로직을 SQL로 옮기지 않는다.** "누구에게 보낼지"는 TypeScript에 있고 단위
테스트가 지킨다. DB에 다시 구현하면 두 벌이 되어 갈린다 — `start_challenge`를 세 번
덮어쓰며 겪은 그 사고다. DB는 **깨우기만** 한다.

⚠️ `vercel.json`은 `0 0 * * *`(하루 1회)로 되돌렸다. 지우지 않은 이유는 안전망이다 —
pg_cron이 멈춰도 하루 한 번은 돌고, 챌린지 자동 전환(UTC 0시 슬롯)도 그때 실행된다.
중복 호출은 `dedupe_key`가 막는다.

유저의 알림 시각이 **현재 30분 슬롯**에 들어오면 보낸다.

```
알림 분 = (평소 시작 슬롯의 시작 분 − 30 + 1440) % 1440
```

30분을 뺀 값이 자정을 넘어가면(예: 00:10 시작 → 23:40) **전날로 돌아간다**. 그래서
`% 1440`으로 감싸고, dedupe는 **그 시점의 로컬 날짜**로 잡는다.

### 3.2 추정 — 최근 60일 · 최빈 슬롯 · 최소 5회

- 최근 `ESTIMATE_WINDOW_DAYS = 60`일의 `started_at`만 본다. 반년 전 습관은 지금이 아니다
- 시작 시각을 **30분 슬롯**으로 접고 **최빈 슬롯**을 고른다
  - ⚠️ 평균·중앙값을 쓰지 마라. 아침·저녁 둘 다 하는 사람의 평균은 **아무도 운동하지
    않는 낮 시간**이 된다. 최빈값은 그 함정이 없다
- 동률이면 **더 최근 세션이 있는 슬롯**. 규칙이 없으면 실행마다 알림 시각이 흔들린다
- 표본이 `MIN_SESSIONS_FOR_ESTIMATE = 5` 미만이면 `null` → 화면·발송은 **기존 09:00**으로 떨어진다

### 3.3 조회 상한 — 페이지네이션

`.range()`로 끝까지 읽는다. 상한에 걸려 **조용히 스트릭이 과소계산되는** 것이 이번
변경으로 48배 잦아지므로 먼저 고친다.

### 3.4 챌린지 전환 RPC는 하루 한 번만

`autostart_due_challenges`·`autofinalize_due_challenges`가 지금 브리핑 크론에 얹혀 있다.
멱등이라 48번 돌려도 안전하지만 값이 없다 — **UTC 0시 슬롯에서만** 부른다(옛 동작과 동일).

### 3.5 문구 — 단계마다 **다른 심리 기제** (2026-08-13 사용자 지시)

> *"알림 메시지는 손실 회피 심리를 자극하는 문구로"* → *"손실회피와 동기 부여를
> 조합하면 좋을 것 같은데 인간 본능과 심리 이론을 바탕으로 구성해줘"*

⚠️ **전부 공포로 밀면 안 된다.** 두 가지가 무너진다: ① 아직 4일 여유가 있는 단계
(`d4`)에서 "오늘 안 하면 리셋"은 **거짓말**이고, ② 매일 겁주는 알림은 꺼진다.
그래서 위험이 낮은 단계는 **접근 동기**, 높은 단계는 **회피 동기**를 쓴다.

| 단계 | 상태 | 주 기제 | 근거 |
|---|---|---|---|
| `today_done` | 오늘 완료 | 목표 구배 | Hull·Kivetz — 목표에 가까울수록 힘이 붙는다 |
| `d4` | 어제 운동 | 자이가르닉 + 목표 구배 | 미완결이 기억에 남는다 · 다음 한 칸(n+1) |
| `d3` | 2일 쉼 | 보유 효과 + 매몰 노력 | Thaler — 가진 것을 더 크게 친다 |
| `d2` | 3일 쉼 | 손실 회피 + 자기효능 | Kahneman·Tversky · Bandura |
| `d1` | 4일 쉼 | 손실 회피 + 실행 의도 | Gollwitzer — 언제·무엇을 정하면 실행률이 오른다 |
| `expired` | 소멸 | 새 출발 효과 | Dai·Milkman·Riis |

- `TODAY_DONE_MESSAGES`가 `string[]` → `((n) => string)[]`으로 바뀌었다. 칭찬만 하면
  거기서 끝나므로 **다음 숫자**를 보여준다 (`8일째, 내일이면 9일이에요`)
- ⚠️ **`expired`에는 손실 회피를 쓰지 않는다. 의도적이다.** 이미 잃은 뒤라 찌를
  손실이 없고, "N일을 잃었습니다"는 재촉이 아니라 면박이다
- ⚠️ **d2·d1은 잃을 양만 말하지 않는다.** 문턱을 낮추는 신호(`30분`·`한 번`)를 같이
  준다 — 없으면 "어차피 못 해"로 간다
- `streak-messages.test.ts`가 기제별 흔적을 단언한다. 실제로 초안 3개를 잡아냈다:
  자기효능 신호가 빠진 d2·d1 변형과, 손실 양이 빠진 d1 변형

### 3.6 범위 밖
- **사용자가 시각을 직접 고르기** — `notification_settings`에 시각 컬럼이 **없다**.
  자동 추정만으로 시작하고, 필요해지면 컬럼을 추가한다
- **알림 종류 이름** — `type`과 `dedupe_key`의 `morning_briefing`은 그대로.
  바꾸면 기존 행과 갈라진다

## 5. 검증

### 5.0 최종 동작 구성 (2026-08-14 확인 완료)

```
Supabase pg_cron  (*/30, jobname=briefing-dispatch, 0076)
   └ net.http_get  Authorization: Bearer ← vault.decrypted_secrets['briefing_cron_secret']
        └ GET https://gnd-one.vercel.app/api/briefing   → 200
             └ notifications INSERT → 0016 트리거 → /api/push/notify → 기기 푸시
```

- Vercel 크론(`0 0 * * *`)은 안전망으로 남긴다. 중복은 `dedupe_key`가 막는다
- **Vault의 값은 Vercel `CRON_SECRET`과 글자 하나까지 같아야 한다**(64자)

**고장이 세 겹이었다. 하나씩 벗겨야 보인다:**

| 증상 | 원인 | 고친 방법 |
|---|---|---|
| HTTP 흔적 자체가 없음 | pg_cron 워커 미기동 | Dashboard → Extensions에서 **껐다 켜기** |
| `405` | `/api/briefing`은 GET인데 `http_post`로 부름 | 0076에서 `http_get`으로 |
| `401` | Vault 값이 Vercel `CRON_SECRET`과 다름 | `vault.update_secret`로 덮어쓰기 |

⚠️ **Vercel의 `Sensitive` 환경변수는 값을 다시 못 읽는다.** 화면의 `sk_1…2…`를
복사하면 **잘린 값**이 복사되어 계속 401이 난다. 값이 필요하면 **로컬 `.env.local`**
에서 꺼내라 — `vercel env pull`로 받아 둔 그 파일이 운영과 같은 값을 갖고 있다
(2026-08-14에 이걸로 확인했다. 로컬 값으로 운영에 GET → 200).

### 5.0.1 ⚠️ `cron.job_run_details`를 "잡이 도는가"의 지표로 쓰지 마라

**이 Supabase 프로젝트는 실행 기록을 안 쌓는다.** 2026-08-14에 이것 때문에 오진했다:

| 관측 | 그때의 해석 | 실제 |
|---|---|---|
| `cron.job_run_details` 0건 | "워커가 죽었다" | **로그만 안 쌓인다** |
| `net._http_response`에 `02:30:00` 401 | — | **잡은 정확히 발사되고 있었다** |

`02:30:00`처럼 **`:00`/`:30` 정각에 찍힌 HTTP 응답이 유일하게 믿을 만한 증거**다.
실행 기록이 0건이라고 외부 크론으로 갈아타려다 되돌렸다.

⚠️ 다만 **처음에는 정말로 안 돌았다.** Dashboard → Database → Extensions에서
`pg_cron`을 **껐다 켠 뒤에** 발사가 시작됐다. SQL의 `create extension`만으로는
워커가 안 뜬다 — 확장을 새로 켤 때는 대시보드 토글을 거쳐야 한다.

고장은 **두 겹**이었다: ① 워커 미기동(토글로 해결) ② `http_post` → 405(0076으로 해결).
하나를 고쳐도 증상이 그대로라 계속 첫 번째를 의심하게 된다 — **응답 코드를 보면
어느 겹인지 바로 갈린다**(405=메서드, 401=비밀키, 없음=워커).

### 5.1 운영 확인 쿼리 (Supabase SQL Editor)

⚠️ **`0075` 파일 하단 주석의 확인 쿼리는 틀렸다.** `cron.job_run_details`에는
`jobname` 컬럼이 **없다**(`jobid`만 있다) — `cron.job`과 조인해야 한다.
2026-08-14에 실행하다 `42703: column "jobname" does not exist`로 드러났다.
0075는 이미 적용됐으므로 파일은 고치지 않는다(적용된 마이그레이션 불변 규약).
**아래가 올바른 쿼리다.**

```sql
-- 잡이 등록됐는가
select jobid, jobname, schedule, active from cron.job;

-- 30분마다 실제로 도는가 (start_time이 :00 / :30 간격이어야 한다)
select d.start_time, d.status, d.return_message
from cron.job_run_details d
join cron.job j on j.jobid = d.jobid
where j.jobname = 'briefing-dispatch'
order by d.start_time desc limit 12;

-- HTTP 응답 (200이어야 한다. 401 = Vault 값이 Vercel CRON_SECRET과 다름)
select id, status_code, created from net._http_response order by created desc limit 10;

-- 최종 증거: 알림이 사람마다 다른 시각에 갔는가
select user_id, title, created_at from notifications
where type = 'morning_briefing' order by created_at desc limit 20;
```

⚠️ `net._http_response`만 보면 **누가 불렀는지 알 수 없다.** 브리핑 크론 호출과
0016의 푸시 발송이 같은 표에 섞인다. 크론이 도는지는 `cron.job_run_details`로 본다.


- 순수 함수 단위 테스트 (표본 미달·최빈·동률·자정 넘김·타임존)
- `buildBriefings` 슬롯 게이트 테스트 (하루 한 번·폴백)
- ⚠️ **배포 후 실제 발송 시각을 본다.** 크론 주기가 요금제에 막히면 조용히 옛날처럼
  하루 한 번만 도는데, 코드는 정상이라 테스트로는 안 잡힌다

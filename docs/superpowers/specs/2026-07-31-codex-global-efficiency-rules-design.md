# Codex 전역 효율 작업 규칙 설계

**작성일:** 2026-07-31

**상태:** 사용자 방향 승인 완료 · 작성 문서 검토 대기

**대상:** 앞으로 Codex로 수행하는 모든 작업

## 1. 문제와 목표

현재 전역 지침은 안전성과 설명 품질은 높지만, 작업 크기와 위험을 구분하는 기준이 약하다. 그 결과 작은 문서 수정이나 한두 파일 오류 수정에도 큰 기능과 비슷한 검색·계획·검증·기록 절차가 붙을 수 있다.

목표는 안전 절차를 없애는 것이 아니라 **작업 위험에 맞는 가장 작은 충분한 절차**를 선택하는 것이다.

성공 기준은 다음과 같다.

- 작은 작업은 별도 브랜치·작업 폴더·전체 검사 없이 끝낼 수 있다.
- 전체 테스트와 build는 같은 코드 기준으로 원칙적으로 마지막 1회만 실행한다.
- 데이터베이스·인증·개인정보·삭제·결제·운영 배포는 기존의 강한 승인과 검증을 유지한다.
- 같은 파일·상태·출력을 근거 없이 반복해서 읽거나 보여주지 않는다.
- 전역 지침 자체의 길이를 줄여 모든 작업에서 드는 고정 토큰 비용도 낮춘다.

## 2. 첫 원칙 검수 결과

반드시 필요한 작업은 네 가지뿐이다.

1. 현재 상태와 요청을 정확히 이해한다.
2. 필요한 범위만 변경한다.
3. 가장 저렴하면서 충분한 증거로 결과를 확인한다.
4. 되돌리기 어렵거나 외부에 영향을 주는 일만 사용자에게 승인받는다.

다음 관행은 모든 작업에 공통으로 필요한 조건이 아니다.

- 별도 브랜치와 worktree
- 정식 설계서와 상세 계획서
- 여러 에이전트 또는 반복 리뷰
- 전체 테스트와 build의 반복 실행
- 긴 완료 보고서
- 작업 단계마다 문서 갱신과 커밋

이들은 작업 크기나 위험이 정당화할 때만 사용한다.

## 3. 전역 단일 원천과 프로젝트 규칙의 역할

### 3.1 전역 단일 원천

`C:\Users\SAMSUNG\.codex\AGENTS.md`를 모든 Codex 작업의 효율 규칙 단일 원천으로 사용한다.

전역 파일에는 다음만 둔다.

- 비개발자에게 설명하는 방식
- 작업 위험 등급
- 검색·검증·질문·보고의 반복 제한
- 안전 승인선
- 증거가 충분하면 멈추는 원칙

현재 전역 파일은 약 10.7KB다. 반복 설명과 모든 작업에 강제된 긴 양식을 줄여 **8KB 이하**를 목표로 다시 정리한다. 안전·보안·승인 규칙은 삭제하지 않는다.

### 3.2 프로젝트 지침

각 프로젝트의 `AGENTS.md`·`CLAUDE.md`에는 그 프로젝트만의 사실만 둔다.

예: GND의 운영 Supabase 연결, 로컬 `main` 기준 Vercel CLI 배포, GitHub 배포 금지, 실 DB 검증 스크립트 주의사항.

전역 효율 규칙을 프로젝트 파일에 다시 복사하지 않는다. 프로젝트 규칙과 전역 규칙이 충돌하면 더 구체적이고 더 안전한 프로젝트 규칙을 따른다.

## 4. 작업 위험 등급

파일 수는 참고 기준일 뿐이며, **위험도가 파일 수보다 우선한다.** 한 파일만 바꿔도 인증이나 데이터베이스라면 고위험 작업이다.

### 4.1 빠른 작업

대상:

- 설명·읽기·조사
- 문서·문구·설정의 작은 수정
- 1~3개 파일의 국소 오류 수정
- 데이터베이스·인증·개인정보·삭제·결제·운영 배포와 무관한 변경

절차:

- 저장소와 상태를 처음에 한 번 확인한다.
- 관련 파일만 검색한다.
- 결과를 크게 바꾸는 정보가 없지 않은 한 질문 없이 합리적으로 가정하고 진행한다.
- 별도 브랜치·worktree·하위 에이전트·정식 설계서를 기본으로 사용하지 않는다.
- 관련된 가장 작은 테스트만 실행한다.
- 화면 변경은 개발 서버에서 해당 흐름만 확인한다.
- 공용 핵심 코드를 바꾸지 않았다면 전체 테스트와 build를 생략할 수 있다.
- 완료 보고는 결론·변경·검증·남은 일만 짧게 쓴다.

### 4.2 표준 작업

대상:

- 4개 이상 파일 변경
- 여러 화면·모듈에 걸친 기능
- 새로운 사용자 행동
- 공용 계산·상태·인터페이스 변경

절차:

- 짧은 계획을 한 번 제시한다.
- 변경 중에는 관련 테스트만 실행한다.
- 마지막에 lint·typecheck·전체 test·build를 각각 한 번 실행한다.
- 화면 작업은 개발 서버에서 대표 사용자 흐름을 한 번 확인한다.
- worktree는 사용자 변경과 충돌하거나 동시 작업을 격리해야 할 때만 사용한다.
- 최종 리뷰와 문서 갱신은 각각 한 번만 한다.

### 4.3 고위험 작업

대상:

- 데이터베이스·마이그레이션
- 인증·권한·개인정보·비밀값
- 중요 데이터 삭제
- 결제·과금
- 운영 배포·실사용자 알림
- 복구하기 어려운 Git 변경

절차:

- 설계·계획·회귀 테스트·전체 검증을 유지한다.
- 실제 데이터와 외부 사용자에 미치는 영향을 먼저 확인한다.
- 실행 직전에 사용자 승인을 받는다.
- 개발 서버 또는 안전한 시험 환경에서 실제 흐름을 확인한다.
- 적용·배포 후 실물을 검증하고 미검증 항목을 분명히 기록한다.

## 5. 반복과 토큰 사용 제한

정상 경로의 기본 제한은 다음과 같다. 실패, 새로운 증거, 안전 위험이 생겼을 때만 넘을 수 있다.

- 저장소·브랜치·상태 확인: 시작 1회, 상태가 실제로 바뀐 뒤 마무리 1회
- 집중 검색: 최대 2회 후 필요할 때만 범위를 확대
- 관련 테스트: 실패 확인과 수정 후 통과 확인에 필요한 최소 횟수만 실행하고, 같은 코드에서 이유 없이 반복하지 않음
- 전체 테스트: 마지막 1회
- build: 마지막 1회
- 최종 리뷰: 1회
- 문서 갱신: 마지막 1회
- 커밋: 논리적으로 하나인 작은 작업은 1개
- 질문: 결과나 위험을 크게 바꾸는 정보가 없을 때만 질문
- 진행 보고: 시작, 중요한 중간 결과, 완료 또는 막힘에만 전달
- 긴 명령 확인: 1초 단위 반복 확인을 피하고 10~30초 단위로 기다림
- 도구 출력: 전체 원문 대신 판정에 필요한 줄·개수·오류만 추출
- 에이전트 사용: 서로 독립인 작업이 실제로 동시에 진행될 때만 사용
- 스킬 사용: 사용자가 지정했거나 작업에 반드시 필요한 최소 묶음만 사용

## 6. 충분한 증거에서 멈추기

검증은 많이 하는 것이 아니라 **원래 문제를 잡는 가장 값싼 증거를 얻는 것**이 목적이다.

증거 우선순위:

1. 문제를 직접 재현하는 작은 테스트
2. 변경된 기능의 관련 테스트
3. 화면 변경이면 대표 사용자 흐름의 로컬 확인
4. 공용 코드나 큰 작업이면 전체 검사
5. 운영 배포이면 운영 주소의 한 가지 권위 있는 신호

한 단계에서 요구사항을 직접 증명하면 같은 사실을 다른 방식으로 반복 확인하지 않는다. 서로 모순되는 신호가 있을 때만 추가 검증한다.

## 7. 배포 효율 원칙

전역 규칙은 특정 서비스나 Git 제공자를 강제하지 않고 프로젝트 배포 규칙을 우선한다.

공통 순서는 다음과 같다.

개발 서버 실제 흐름 확인 → 로컬 최종 검사와 build 1회 → 사용자 승인 → 프로젝트가 정한 방식으로 배포 → 운영 실물 확인 → 기록 1회

검증한 동일 커밋을 깨끗한 임시 폴더로 복사했다면 그 폴더에서 의존성 설치와 로컬 build를 다시 반복하지 않는다. 배포 서비스가 수행하는 운영 build와 결과를 확인한다. 임시 복사본의 코드가 검증한 커밋과 다르면 다시 검사한다.

GND 프로젝트는 별도 프로젝트 규칙에 따라 GitHub가 아니라 검증한 로컬 `main`과 Vercel CLI를 사용한다.

## 8. 보고 형식 간소화

빠른 작업 완료 보고:

- 결론
- 바뀐 것
- 실행한 검증과 결과
- 남은 일 또는 미검증

표준·고위험 작업만 현재의 상세 완료 보고 형식을 사용한다.

사용자가 비개발자라는 원칙은 유지하되, 사용자가 요청하지 않은 긴 개념 설명과 비유는 생략한다. 전문용어가 실제 판단에 필요할 때만 한 문장으로 풀어 쓴다.

## 9. 적용 범위와 예외

- 이 규칙은 앞으로의 모든 Codex 작업에 적용한다.
- 시스템 안전 규칙, 사용자가 명시한 스킬 절차, 외부 서비스의 필수 확인 단계는 생략할 수 없다.
- 프로젝트가 더 엄격한 안전 규칙을 가지면 프로젝트 규칙을 따른다.
- 테스트 실패, 예상 밖 변경, 보안 위험, 데이터 손상 가능성이 생기면 즉시 표준 또는 고위험 절차로 승격한다.

## 10. 적용과 되돌리기

구현 단계에서는 다음 순서를 따른다.

1. 기존 전역 `AGENTS.md`를 날짜가 포함된 백업 파일로 보존한다.
2. 전역 `AGENTS.md`를 안전 규칙을 유지한 간결한 구조로 다시 작성한다.
3. GND의 `AGENTS.md`와 `CLAUDE.md`에서 전역 규칙과 중복되는 문장을 줄이고 프로젝트 전용 규칙만 남긴다.
4. 전역 파일 크기, 핵심 안전 문구, 작업 등급, 반복 제한이 모두 존재하는지 확인한다.
5. GND 프로젝트 변경은 정확한 파일만 커밋한다.

문제가 생기면 전역 백업 파일을 원래 `AGENTS.md`로 복원하고, 프로젝트 변경은 해당 커밋을 되돌린다.

## 11. 기대 효과

[추정] 빠른 작업 기준으로 도구 호출과 토큰을 약 30~50% 줄이고, 전체 테스트·빌드 반복을 2~3회에서 0~1회로 줄일 수 있다. 실제 절감률은 다음 작업 3건에서 작업 시간, 전체 검사 횟수, 도구 호출 횟수를 비교해 확인한다.

# 버그 신고 파이프라인 — 설계 (First Principles)

작성 2026-07-31. 사용자가 앱에서 오류를 신고하면 **발생 지점이 기록에 남고**, 에이전트가 그것을 읽어 고치고, 고쳤다는 사실이 신고자에게 되돌아가는 한 바퀴를 만든다.

---

## 0. 현황 — 지금은 파이프라인이 하나도 없다

실측으로 확인한 것:

| 항목 | 현재 상태 |
|---|---|
| 신고 메뉴 | **없음** (`src` 전체에 신고/피드백 폼 0건) |
| 에러 경계 | **없음** (`error.tsx`·`global-error.tsx` 0개 → 앱이 죽으면 Next 기본 화면) |
| 에러 추적 도구 | **없음** (Sentry 등 0건) |
| 클라이언트 로그 수집 | **없음** |
| 실패 처리 | `catch`·`console.error` **33곳 / 15파일** — 전부 조용히 삼킨다 |

**현재의 진짜 신고 경로는 "사용자가 말로 알려주면 내가 코드 주석에 날짜를 박는 것"이다.** 저장소에 그 흔적이 그대로 남아 있다:

- `src/lib/domain/streak-messages.ts:16` — `2026-07-23 사용자 신고: 어제 운동했는데 "어제 쉬셨다?"가 떴다`
- `src/app/(tabs)/challenge/page.tsx:287` — `2026-07-31 사용자 신고`
- `src/lib/rest-countdown-audio.ts:5` — `2026-07-21, 음악에 여전히 가려진다는 사용자 신고`

주석은 **고친 뒤에 남는 기록**이지, 신고를 받는 장치가 아니다. 신고 시점의 맥락(어느 화면, 어떤 기기, 어떤 번들)은 그때 이미 사라져 있다.

### 재사용할 수 있는 기존 자산

새로 만들 것이 생각보다 적다. 필요한 조각이 대부분 이미 있다.

| 필요한 것 | 이미 있는 것 |
|---|---|
| 데이터 저장 + 권한 | Supabase + RLS + `SECURITY DEFINER` RPC 관행 (마이그레이션 51개) |
| 신고자에게 알림 | `notifications` INSERT 트리거 → `/api/push/notify` → web-push |
| **에이전트가 DB를 읽는 경로** | `scripts/*.mjs` + `SUPABASE_SERVICE_ROLE_KEY` (34개 스크립트가 이미 이 방식) |
| 고친 뒤 사용자에게 알리기 | `release-notes.data.json` + `scripts/broadcast-release.mjs` |
| 파일 업로드 | storage 버킷 패턴 (`workout-images`, `avatars` — 0005) |
| 계측 지점 한 곳 | `getSupabaseBrowserClient()` **싱글턴 팩토리 하나** (`src/lib/supabase/client.ts`) |

마지막 항목이 특히 크다. 앱 전체가 이 팩토리 하나를 통해 DB에 접근하므로, **여기서 `fetch`를 감싸면 33곳의 `catch`를 건드리지 않고 모든 DB 실패를 한 곳에서 잡는다.**

## 1. 문제의 본질

**핵심 문제:** 사용자가 "안 되는데요"라고 말한다. 그 문장만으로 나는 **재현할 수 없다.**

이건 추측이 아니라 이 저장소에서 반복된 사고다.

- **0044 배포** — lint·typecheck·단위 683건·build·번들 grep이 전부 초록이었는데 폰에서 챌린지가 3개로 중복되고 추가 버튼이 없었다
- **배포 누락 (7/29~7/30)** — 이틀간 옛 번들이 돌았다. 사용자는 "기능이 적용 안 됐다"고만 느꼈고 서버 DB는 정상이라 원인 찾는 데 오래 걸렸다
- **초대 링크 (7/31)** — 폰에서만 재현되는 순서 싸움

세 건 모두 **예외가 하나도 안 났다.** 화면이 틀렸을 뿐이다.

**성공 기준 (측정 가능):**

1. 신고 1건을 받았을 때 **사용자에게 되묻지 않고** 원인 후보를 좁힐 수 있다
2. "어느 화면에서"가 사람의 기억이 아니라 **기록**에서 나온다
3. 신고자의 폰이 **어느 배포본을 돌고 있었는지** 알 수 있다 (배포 누락 사고의 재발 차단)
4. 고친 뒤 그 신고가 닫혔다는 것과 신고자가 확인했다는 것이 남는다

## 2. 도전한 가정

| 가정 | 도전 | 판정 |
|---|---|---|
| Sentry 같은 에러 추적을 붙여야 한다 | Sentry는 **예외가 던져진 곳**을 잡는다. 그런데 위 실제 사고 3건은 예외가 안 났다 — Sentry였어도 **하나도 못 잡았다** | **버림.** 자동 예외 수집이 주가 되면 안 된다. 사람의 신고가 주다 |
| 신고 폼에 문제를 잘 적게 해야 한다 | 사용자는 비개발자다. 잘 적으라고 요구하면 신고 자체를 안 한다. 게다가 브라우저가 이미 아는 것(경로·계정·시각·기기)을 사람에게 묻는 건 낭비다 | **뒤집음.** 사람은 한 줄만, 나머지는 전부 자동 |
| `/admin` 대시보드에서 신고를 본다 | 화면을 보는 사람은 사용자(비개발자)다. **고치는 주체는 에이전트고, 에이전트는 화면을 못 본다.** DB를 `.mjs` 스크립트로 읽는다 | **수정.** 1차 소비자는 **스크립트**. `/admin` 패널은 2단계 |
| 신고가 들어오면 즉시 알림이 가야 한다 | ~~에이전트는 푸시를 못 받으니 실시간은 포기한다~~ ← **이 추론은 틀렸다. 다리를 하나 빼먹었다.** 에이전트는 못 받지만 **관리자(사용자)의 폰은 이미 푸시를 받고 있고, 에이전트 세션을 여는 사람도 그 사용자다.** 사용자가 다리다 | **유지 (가정이 옳다).** 실시간 알림은 필요하고 가능하다 → §5.4 |
| 발생 지점 = 스택 트레이스 | 프로덕션은 minify라 스택이 `chunk-abc.js:1:24580`이다. 소스맵 없이 못 읽는다. **"어느 라우트에서 무엇을 하다가"가 훨씬 유용하다** | **수정.** 라우트 + 직전 동작 흔적 > 스택 |
| 로컬 CLI 배포라 버전을 못 붙인다 | 빌드 시각을 빌드 타임에 주입하면 된다. `.git` 없는 복사본에서 배포하므로 커밋 해시는 못 쓰지만 **빌드 시각은 확실하다** | **버림 (제약 아님).** 그리고 이게 배포 누락 사고를 구조적으로 잡는다 |

## 3. 환원 불가능한 사실 (Ground Truths)

1. **신고 순간, 브라우저만이 그 시점 맥락을 갖고 있다.** 경로·계정·기기·직전 동작·최근 실패·번들 버전. 나중에는 영영 복원 불가다.
2. **고치는 주체는 에이전트이고, 에이전트는 DB를 스크립트로만 읽는다.** 화면으로 보는 건 사용자다.
3. **규모가 작다.** 인증 계정 5~6개, 프로필 4개. 신고는 하루 0~수 건. 대용량 파이프라인은 필요 없다.
4. **RLS가 진실이다.** 신고자는 자기 것만 읽는다. 관리자 읽기는 `service_role`로 한다 — 8개 테이블에 관리자 정책을 뿌리지 않는다는 `/admin`의 기존 원칙과 같다.
5. **버그가 고쳐졌다는 것은 사용자가 실기기에서 확인해야 완결된다.** 이 저장소의 모든 완료 규칙이 그렇다.
6. **실제 실패 모드는 "예외"가 아니라 "화면이 틀림"이 압도적이다.**

## 4. 최소에서 쌓아올리기

**최소 해:** `bug_reports` 테이블 1개 + 신고 시트 1개 + 읽기 스크립트 1개. 이것으로 GT 1·2·3이 충족된다.

여기서 **각각 근거가 있는 것만** 얹는다.

| 추가 | 근거 |
|---|---|
| 자동 맥락 (경로·계정·기기·화면크기·시각) | GT1 — 신고 순간에만 존재한다. 사람에게 안 묻는다 |
| **동작 흔적(trail)** 최근 30개 | GT6 — 예외가 안 나는 실패가 다수다. "무엇을 하다가"를 남겨야 좁힐 수 있다 |
| Supabase `fetch` 래핑 | 팩토리가 하나뿐이라 **한 곳에서 전 DB 실패를 잡는다.** 33개 `catch`를 안 건드린다 |
| **배포 식별자(빌드 시각)** | 배포 누락 사고를 잡는다. "이 폰이 3일 묵은 번들을 돌고 있다"가 즉시 보인다 |
| `error.tsx` / `global-error.tsx` | 앱이 하얗게 죽었을 때 **신고 버튼이 거기 있어야** 한다. 지금은 Next 기본 화면이라 신고 경로 자체가 없다 |
| 상태 + `fixed_release` | GT5 — 릴리스 id와 묶으면 "이 신고는 이 배포로 닫혔다"가 남는다 |
| 신고자에게 되돌아가는 알림 | 신고했는데 아무 반응이 없으면 **다음부터 신고를 안 한다.** 파이프라인이 계속 돌게 하는 연료다 |

### 일부러 뺀 것 (복잡도의 함정 차단)

- **Sentry / 세션 리플레이** — 4명 규모에 과잉이고, 위 사고를 못 잡고, 개인정보를 크게 늘린다
- **자동 예외 전송** — 무한 루프·노이즈. 예외는 trail에 **적어두기만** 하고 신고할 때 같이 간다
- **신고 카테고리 분류** — 비개발자가 카테고리를 고르면 틀린다. 자유 한 줄 + 자동 맥락이 낫다
- **오프라인 큐잉** — DB가 죽었을 때 신고도 실패한다. 1단계에서는 "카톡으로 알려주세요" 안내로 대신한다. 정직하고 실제로 작동한다
- **`/admin` 신고 패널** — 있으면 좋지만 1차 소비자가 아니다 (2단계)

## 5. 설계

### 5.1 DB — 마이그레이션 `0052_bug_reports.sql`

> 현재 **0051까지 적용**됨. 새 번호는 **0052**.

```
bug_reports
  id             uuid pk
  user_id        uuid not null → auth.users on delete cascade
  created_at     timestamptz default now()
  message        text not null          -- 사람이 쓴 한 줄 (2~1000자)
  route          text                   -- 신고 버튼을 누른 시점의 경로
  context        jsonb default '{}'     -- build, ua, viewport, tz, online
  trail          jsonb default '[]'     -- 최근 동작·실패 (최대 30)
  status         text default 'new'     -- new | triaged | fixed | wontfix
  triage_note    text                   -- 에이전트가 남기는 원인·판단
  fixed_release  text                   -- release-notes.data.json의 id
  resolved_at    timestamptz
  notified_at    timestamptz            -- 신고자에게 "고쳤어요" 보낸 시각
```

인덱스 `(status, created_at desc)`, `(user_id, created_at desc)`.

**RLS**
- `bug_reports_select_own` — `user_id = auth.uid()` (신고자가 자기 신고 상태를 본다)
- **INSERT 정책 없음** → RPC를 통해서만 들어온다. 레이트 리밋과 크기 제한을 우회할 수 없게 하기 위해서다

**RPC `submit_bug_report(p_message, p_route, p_context, p_trail) returns uuid`** — `SECURITY DEFINER`
- `auth.uid()` 없으면 `not_authenticated`
- `message` trim 후 2~1000자 검사
- **레이트 리밋** — 최근 10분 3건 초과면 `rate_limited` (스팸보다 버튼 연타 방어)
- **중복 흡수** — 최근 2분 내 같은 사용자·같은 메시지면 **기존 id를 그대로 반환**. 연타가 무해해진다
- **클라이언트를 믿지 않는다** — `trail`은 서버에서 30개로 자르고, `context`는 `pg_column_size` 8KB 초과 시 거부

**알림 타입 `bug_fixed` 추가** — `notifications` type CHECK 제약에 추가 (0034가 `app_update`를 넣은 것과 같은 방식).

> ⚠️ 앱 코드에서 `NotificationRow`의 유니온에 `bug_fixed`를 넣으면 `notification-bell.tsx`의 `TYPE_ICON`(exhaustive Record)이 **컴파일 타임에 깨진다 — 그게 의도한 게이트다.** 반면 `src/lib/domain/push.ts`의 `PUSH_URL_BY_TYPE`은 `Record<string, string>`이라 **exhaustive가 아니다.** 빠뜨리면 조용히 `/home`으로 떨어지므로 **손으로 챙긴다** (PROGRESS 0044 항목의 기록된 함정).

### 5.2 클라이언트

**`src/lib/domain/bug-trail.ts`** — 순수 링버퍼 (테스트 가능, DOM 무관)
- `noteTrail(kind, label, detail?)` — `kind: 'nav' | 'action' | 'fail'`
- 최대 30개, 항목은 `{ t, kind, label, detail? }`, `detail`은 200자 컷
- **값이 아니라 이름만 담는다.** 닉네임·본문·토큰은 넣지 않는다
- 메모리에만 산다. 신고할 때만 전송된다

**`src/lib/supabase/client.ts`** — `global.fetch` 래핑. 실패와 동작을 **같은 한 곳**에서 잡는다.
- `status >= 400` → `noteTrail('fail', 'db', '<method> <경로> <status>')`
- 성공 + `isUserAction(method, url)` → `noteTrail('action', '<경로>')`
- **쿼리스트링은 버린다** (닉네임·uuid가 들어간다). 인증 헤더·요청 본문은 절대 안 담는다

**동작 계측은 자동이다 — 손으로 안 넣는다.** `isUserAction`이 세 겹으로 거른다: ① 쓰기 메서드(POST·PATCH·PUT·DELETE)만 ② **이름이 `get_`·`list_`·`search_`·`autostart_`·`autofinalize_`·`admin_`·`pending_`·`schema_`로 시작하는 RPC 제외** ③ 서명 URL 발급(`/object/sign/`) 제외. auth도 뺀다.

> **②가 왜 필요한지는 실물로 배웠다.** 첫 판 규칙은 "쓰기 메서드면 동작"이었는데, **PostgREST는 읽기 전용 함수도 `POST /rest/v1/rpc/…`로 부른다.** 배포 후 실제 신고의 흔적 30칸이 `get_my_badge_metrics`·`get_incoming_crew_requests`·`autostart_due_challenges`·서명 URL로 **1분 만에 꽉 찼고 사용자가 누른 것은 하나도 안 남았다.** 노이즈가 신호를 덮으면 흔적은 없느니만 못하다. 그 신고에 실제로 찍혔던 경로 8개가 지금은 회귀 테스트로 고정돼 있다.

> **왜 설계를 바꿨나 — 실패해 봤기 때문이다.** 처음 설계는 "운동 시작/종료·사진 업로드·챌린지 참가·초대 수락·크루 요청·로그인에 손으로 `noteTrail('action', …)`을 넣는다"였다. **구현할 때 한 곳도 안 넣었고**, 배포 후 들어온 첫 신고의 흔적이 `nav` 한 줄뿐인 것으로 그게 드러났다. 이 저장소에는 같은 실패가 이미 있다 — `PUSH_URL_BY_TYPE`은 exhaustive가 아니라서 "손으로 챙겨야 한다"고 주석까지 달아 뒀지만 그런 것은 결국 빠진다. 팩토리 한 곳에서 자동으로 잡으면 빠질 자리가 없다.
>
> 대신 **"버튼을 눌렀는데 요청이 아예 안 나간" 경우는 못 잡는다.** 그때는 `nav`만 남는다 — 그 자체가 "탭이 아무것도 안 했다"는 신호로 읽힌다.

**`src/lib/build-info.ts` + `next.config.ts`의 `env`** — 빌드 시각을 `NEXT_PUBLIC_BUILD_TIME`으로 주입. `.git` 없는 복사본에서 배포하므로 커밋 해시가 아니라 **빌드 시각**을 쓴다.

**`src/components/bug-report-sheet.tsx`**
- 입력 한 칸: `어떤 게 이상했나요? 편하게 적어주세요`
- 현재 경로를 **읽기 전용으로 보여준다** (수정 불가 — 자동이라는 걸 사용자가 알게)
- 함께 전송되는 것을 한 줄로 정직하게 밝힌다: `화면 위치·기기 정보·최근 동작이 함께 전송돼요`
- 성공: `접수됐어요. 확인하고 고칠게요 🙏` / `rate_limited`: `잠시 후 다시 시도해주세요`

**진입점 2곳**
1. `/profile` 톱니 안, 계정 아래 — *"톱니 안이 사용자가 설정을 찾는 유일한 곳"* (기존 주석 근거)
2. **`error.tsx` / `global-error.tsx` 신설** — 앱이 죽은 화면에서 신고할 수 있어야 한다. 던져진 에러 메시지가 자동으로 신고에 실린다

### 5.3 에이전트 확인 절차 ← 사용자 질문의 핵심

**`scripts/bug-reports.mjs`** (`service_role`, 기존 34개 스크립트와 같은 방식)

```bash
node scripts/bug-reports.mjs                      # new 상태 전량 (기본)
node scripts/bug-reports.mjs --all
node scripts/bug-reports.mjs --id <uuid>          # 1건 상세 — trail 전량
node scripts/bug-reports.mjs --triage <id> --note "원인: ..."
node scripts/bug-reports.mjs --fix <id> --release <release-id>          # DRY RUN
node scripts/bug-reports.mjs --fix <id> --release <release-id> --send   # 상태 fixed + 신고자 알림
node scripts/bug-reports.mjs --wontfix <id> --note "..."
```

`--send`가 없으면 **알림은 안 나간다.** `broadcast-release.mjs`와 같은 규약이고, "발송은 사용자가 Run"이라는 기존 원칙과 맞다.

출력 예:

```
[new] 2026-08-02 21:14 KST · 스칼레또 · /challenge
  "챌린지 참가 눌렀는데 아무 반응이 없어요"
  build 2026-07-31T09:22Z (3일 전)   iPhone/Safari 17.4   390×844
  trail:
    21:14:02  fail  db    POST /rpc/accept_challenge_invite 400
    21:13:58  action      challenge:accept-tap
    21:13:41  nav         /challenge
    21:13:39  nav         /home
```

**한 바퀴:**

```
사용자 신고 → bug_reports (RPC)
   → node scripts/bug-reports.mjs           (에이전트가 읽는다)
   → 재현 → 수정 → pnpm dev로 화면 확인      (CLAUDE.md 필수 절차)
   → vercel --prod → 프로덕션 실물 확인
   → --fix <id> --release <id> --send        (신고자 폰에 알림)
   → 사용자가 실기기 확인 → 닫힘
```

**새 세션이 자동으로 알게 하기** — `CLAUDE.md`에 한 줄 추가한다. `SessionStart` hook으로 자동 실행할 수도 있지만 매 세션 프로덕션 DB에 붙으므로 **선택 사항으로 남긴다.**

### 5.4 알림 — 신고가 들어온 걸 어떻게 아는가

**제약:** 에이전트에게는 받는 함이 없다. Claude Code는 사용자가 세션을 열 때만 돈다. 그래서 "신고 도착 순간 에이전트에게 알림"은 **구조적으로 불가능하다.**

**해법:** 알릴 대상은 에이전트가 아니라 **관리자(사용자)**다. 그 사람의 폰은 이미 푸시를 받고 있고, 에이전트 세션을 여는 것도 그 사람이다. **사용자가 다리다.**

실패 모드가 서로 다른 3층을 겹친다.

| 층 | 무엇 | 잡는 것 | 놓치는 것 |
|---|---|---|---|
| **1** | 관리자 폰 즉시 푸시 | 실시간 | 푸시 구독 만료·알림 끔 → **조용히** 실패 |
| **2** | 매일 09:00 브리핑에 한 줄 | 1층이 죽어도 매일 | 하루 지연 |
| **3** | 에이전트 `SessionStart` 훅 | 사용자가 잊어도 에이전트가 먼저 말한다 | 세션을 안 열면 안 뜸 |

#### 1층 — 관리자 폰 푸시 (기존 배관 재사용, 새로 만들 것 없음)

```
bug_reports INSERT
   → 트리거가 관리자 user_id로 notifications 행 INSERT
   → (0016 트리거 → /api/push/notify → web-push)   ← 한 줄도 안 고친다
   → 폰 푸시
```

```
🐞 새 신고 · 스칼레또
"챌린지 참가 눌렀는데 아무 반응이 없어요" (/challenge)
```

**본문에 신고 내용을 통째로 싣는다.** 관리자가 알림만 읽고 에이전트에게 넘길 수 있어야 하고, 1단계에는 아직 `/admin` 신고 패널이 없기 때문이다. 푸시 탭 목적지는 `/admin` (2단계에 패널이 생기면 `/admin/reports`).

세부 규칙:
- **본인 신고는 본인에게 안 간다** — 관리자도 4명 중 한 명이다. 자기 신고에 자기가 알림받는 건 소음이다
- **알림 설정 톱니에 이 토글을 넣지 않는다** — 끄면 신고를 영영 못 본다. 관리자 1명 전용이라 남에게 새지도 않는다
- **DB 트리거는 Vercel 환경변수를 못 읽는다.** `ADMIN_USER_IDS`는 env라 트리거에서 접근 불가 → 받는 사람 uid를 담는 작은 테이블(`bug_report_watchers`)을 0052에 만들고 관리자 폰 계정 uid를 넣는다.
- **받는 계정 (2026-07-31 확정)** — `4fa751c8-8ee6-4e74-bcac-68f963ff032f` = **오뎅끼데스까**, 사용자 본인 확인 완료.
  - 익명 인증이라 **한 사람이 기기마다 다른 계정을 갖는다.** 그래서 "관리자"가 아니라 **"푸시가 실제로 닿는 폰 계정"**이어야 한다
  - **`/admin/whoami`로는 못 찾는다** — 실제로 시도했고 `세션 없음 (익명 로그인 전)`이 떴다. 홈 화면에 설치한 PWA는 주소창이 없어 그 경로로 갈 수 없고, 사파리 탭에서 열면 저장소가 분리돼 있어 앱 계정이 안 보인다
  - **찾는 법은 DB다** — `push_subscriptions ⋈ profiles`로 "푸시 구독이 살아 있는 계정"을 뽑고 `ADMIN_USER_IDS`와 교집합을 낸다. 실측 결과 교집합이 정확히 1개였다(구독 보유 3계정 중 관리자 목록에 있는 것은 오뎅끼데스까뿐). 나머지 관리자 uid 4개는 프로필도 구독도 없는 PC·사파리 계정이다
- 알림 타입 `bug_reported` 추가 — `bug_fixed`와 함께 CHECK 제약·`TYPE_ICON`·`PUSH_URL_BY_TYPE`에 반영 (§5.1의 경고 동일 적용)

#### 2층 — 09:00 브리핑에 얹기

`vercel.json`의 크론은 **하나뿐**이다: `{"path": "/api/briefing?hour=9", "schedule": "0 0 * * *"}` (UTC 0시 = KST 09시). 0044가 `autostart_due_challenges`·`autofinalize_due_challenges`를 여기에 얹은 전례가 있다. **같은 자리에** 미처리 신고 수를 얹는다.

- **`new` + `triaged`** 개수를 세어 1건 이상이면 관리자에게 알림 1건. `new`만 세면 **원인을 적어 둔 순간 알림이 끊겨** 손대다 만 신고가 조용히 묻힌다 — 2층의 존재 이유가 정확히 그걸 막는 것이다. `--brief`(3층)도 같은 기준을 쓴다
- dedupe 키에 **uid를 반드시 넣는다.** `notifications.dedupe_key` 유니크 인덱스는 컬럼 하나뿐(전역 유니크)이라, uid가 빠지면 감시자가 둘 이상일 때 첫 사람만 받고 나머지는 조용히 삼켜진다
- **왜 필요한가** — 1층은 조용히 실패한다. `/api/push/notify`는 404·410을 받으면 만료 구독을 **삭제한다**(`route.ts:117`). 그러면 아무 소리 없이 푸시가 끊긴다. 2층이 매일 그걸 다시 잡는다
- 브리핑 본체와 마찬가지로 **실패해도 브리핑을 죽이지 않는다** (0044가 챌린지 전환에 적용한 규칙과 동일)

#### 3층 — 에이전트 `SessionStart` 훅

`.claude/settings.json`에 훅을 걸어 `node scripts/bug-reports.mjs --brief`를 실행하면 결과가 세션 맥락에 자동 주입된다. 사용자가 *"신고 확인해줘"*라고 말할 필요조차 없어진다.

```
미처리 신고 2건 — ① 스칼레또 · /challenge · 참가 버튼 무반응 (3일 묵은 번들) ② …
```

비용은 세션당 select 1회. `--brief`는 **한 줄 요약만** 뱉는다(전문은 인자 없이 실행). 실패해도 exit 0으로 조용히 넘어간다 — 신고 조회가 안 된다고 세션 시작을 막으면 안 된다.

#### 채택하지 않은 경로

- **이메일** — Supabase에 SMTP 설정이 없어 외부 발송 서비스를 하나 더 붙여야 한다. 폰 푸시가 이미 되므로 불필요
- **카카오톡** — 사업자 등록이 필요한 API
- **크론 주기 단축(매시간)** — 1층이 이미 즉시라 의미 없다

## 6. 단계

| 단계 | 내용 | 마이그레이션 |
|---|---|---|
| **1** | 테이블·RPC·trail·시트·`error.tsx`·읽기 스크립트·검증 **+ 알림 1층(폰 푸시)·2층(09시 브리핑)·3층(SessionStart 훅)** | **0052** |
| **2** | 스크린샷 첨부 (`bug-shots` 버킷), `/admin` 신고 패널 | 0053 |
| **3** (선택) | 오프라인 큐잉 | 없음 |

**알림 3층은 1단계에 포함한다.** 신고가 쌓이는데 아무도 모르면 파이프라인이 아니라 그냥 테이블이다. 1층·2층은 기존 배관(`notifications` 트리거, 09시 크론) 위에 행 하나·한 줄을 얹는 것이라 추가 비용이 거의 없다.

1단계만으로 한 바퀴가 완결된다. 2단계는 1단계가 실제로 쓰이는 걸 본 뒤에 판단한다.

## 7. 감수하는 것

- **자동 예외 수집이 없다.** 사용자가 신고하지 않은 오류는 안 잡힌다. 대신 예외는 trail에 쌓여 있다가 다음 신고에 실려 온다 — GT6이 근거다
- **trail은 명시 계측이라 빠진 지점이 있을 수 있다.** 전 버튼 자동 수집보다 신호 대 잡음이 낫다고 판단했다
- **기기 정보(UA·해상도)가 저장된다.** 시트에서 무엇이 전송되는지 사용자에게 밝힌다. 4명 규모라 위험은 작지만 명시한다
- **신고 자체가 실패하면 (DB 다운) 아무것도 안 남는다.** 1단계 범위 밖 — 안내 문구로 대신한다

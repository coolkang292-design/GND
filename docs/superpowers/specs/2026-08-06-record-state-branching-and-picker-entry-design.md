# 기록 화면 상태 분기 + 운동 추가 진입 개편 (2026-08-06)

사용자 지시 6건. 두 화면(`기록` 탭 · `운동 추가` 시트)을 **등록된 운동 수**와
**사용자 이력 유무**에 따라 분기한다.

> 이 문서는 착수 전 **실측**을 먼저 적는다. 아래 §2의 8건은 코드를 읽고 확인한
> 사실이고, 그중 3건은 그냥 만들었으면 조용히 깨지거나 이미 있는 결정을
> 되돌리는 자리다.

---

## 1. 문제의 본질

**핵심 문제:** 기록 화면이 **상태와 무관하게 같은 도구를 그린다.**

등록된 운동이 0개일 때 화면에 있는 것 — 완료 볼륨 `0kg` · 이전 대비 · 세트 사이
휴식 · 운동 시작 · 타바타 · "완료 체크한 세트만 볼륨에 반영돼요" 복구 안내.
**여섯 개 전부 "지금 할 일"과 무관하다.** 아직 잴 볼륨도, 쉴 세트도, 시작할
운동도 없다. 화면의 모양이 다음에 뭘 해야 하는지에 대한 정보를 전혀 담지 않는다.

같은 문제의 다른 얼굴이 운동 추가 시트다. 열면 곧바로 **검색창과 100여 종의
카탈로그 목록**이 나온다 — 이건 *찾는 종목의 이름을 이미 아는 사람*을 위한
화면이다. 초보자는 그 이름을 모른다.

**성공 기준 (측정 가능하게)**

| | 지금 | 목표 |
|---|---|---|
| 등록 0개 화면의 상호작용 요소 | 8개 (휴식 ±, 추가, 시작, 타바타, 서브탭 2, 취소) | **2개 이하** (첫 운동 추가 + 조건부 최근 불러오기) |
| 이름을 모르는 사람이 첫 운동을 담기까지 | 도달 경로 없음 (검색어를 알아야 한다) | 부위 선택 → 추천 목록 → 추가, **3탭** |
| 운동 추가 후 | 시트가 닫히고 같은 화면 | 오늘 목록이 최상단 핵심 콘텐츠 |
| 마이그레이션 | — | **0건** (§5 결정 ①·②) |

## 3. 도전한 가정

| 가정 | 왜 의심하는가 | 판정 |
|---|---|---|
| ① 추천 운동의 "초보자용 한 줄 설명"은 `exercise_catalog` 컬럼이어야 한다 | 그 설명은 **사용자 데이터가 아니라 편집 카피**다. 사용자마다 다르지 않고, 서버에서 필터·정렬에 쓰지 않고, 바뀌는 계기가 "문구를 다듬었다"이지 "스키마가 변했다"가 아니다. 컬럼으로 만들면 마이그레이션 1건 + 100여 행 중 20행만 쓰는 nullable 컬럼 + 문구 고칠 때마다 사용자가 SQL Run | **폐기.** 코드 상수로 둔다 (§5 ①) |
| ② 빈 상태 화면은 새 컴포넌트가 필요하다 | 필요한 건 "무엇을 **안 그릴지**"의 판정 하나다. 그릴 것은 안내문 + 버튼 2개뿐 | **수정.** 새 파일 1개(빈 상태)만 만들고 나머지는 기존 JSX에 조건을 건다 |
| ③ 피커를 다시 만들어야 한다 | 검색·부위 필터·자주 한 운동 칩·다중 선택·지난 기록·루틴 목록은 **전부 이미 있고 잘 동작한다.** 없는 것은 그 앞의 **진입 허브**와 **추천 목록**뿐 | **폐기.** 594줄을 갈아엎지 않고 **허브 한 겹을 앞에 얹는다** |
| ④ 3세트·10회 기본값은 `defaultSets`를 고치면 된다 | `defaultSets`는 검색으로 담는 경로도 쓴다. 거기까지 3세트로 바뀌면 요구에 없는 변경이다 | **수정.** `recommendedSets()`를 따로 만들고 설정 시트가 그 결과를 낸다 |
| ⑤ `routines=[]`에도 탭을 띄우는 2026-08-02 결정은 지켜야 한다 | 그 결정의 목적은 "**조회 실패**(`undefined`)와 **루틴 0개**(`[]`)를 구별해서, 0056 미적용 상태에 기능이 멀쩡한 척하지 않는 것"이었다. 그 구별은 **기록 페이지의 저장 버튼**(`routines !== null`, [page.tsx:1666](src/app/(tabs)/record/page.tsx#L1666))이 그대로 지킨다. 진입 지점에서는 둘 다 "보여줄 루틴이 없다"로 같다 | **되돌려도 안전.** 단 저장 버튼 조건은 **건드리지 않는다** |
| ⑥ 부위 그리드가 기존 필터 칩 줄을 대체한다 | 칩 줄에는 부위 7개 말고 **`맨몸` 모달리티 칩**이 있다. 이건 2026-08-03 신고 0783ca35(맨몸 실적이 100회 내내 0) 대응으로 넣은 것이다. 그리드로 갈아치우면 그 수정이 회귀한다 | **수정.** 요구 3은 *추천* 흐름의 **부위** 선택만 규정한다 → 그리드는 추천에만, `맨몸` 칩은 **검색 모드에 그대로 남긴다** |

| ⑧ | 썸네일이 부담이면 부위 공통 이미지로 대체한다 (제안 방법 B) | 한 화면에 가슴 운동 카드가 3장 뜨면 **셋 다 같은 그림**이다. 목록에서 항목을 **구별하지 못하는 이미지는 없는 것보다 나쁘다** — 세로 공간만 먹고 스캔을 느리게 한다 | **폐기.** 썸네일 없는 항목은 카드에 이미 있는 **부위 텍스트 태그**로 충분하다 (요구 3이 이미 요구한 요소다) |

## 4. 근본 사실 (ground truths)

- **`draft.exercises.length`가 화면 분기의 단일 진실이다.** 새 상태를 만들지 않는다.
- **"이력이 있는 사용자"는 완료 세션이 1건 이상인 사용자다.** 필요한 정보는 목록이 아니라 **불리언 하나**다.
- **한 시점에 사용자가 할 일은 하나다.** 0개면 "담기", 1개 이상이면 "시작하기".
- **초보자는 종목 이름을 모른다.** 검색은 이름을 아는 사람의 도구이므로 **기본 진입로가 될 수 없다.**
- **무게 미입력은 이미 표현 가능하다** (`weightKg === 0`), 그리고 그 모호함을 완료 시점에 사람에게 확인하는 장치가 이미 있다.

## 5. 설계 결정 3건

### ① 추천 데이터는 DB가 아니라 **코드 상수 × 카탈로그 교집합**

`src/lib/domain/recommended-exercises.ts` (신규):

```ts
/** 부위별 초보자 추천 — 편집 카피다. DB 컬럼이 아닌 이유는 설계 §3 가정 ①. */
export const RECOMMENDED: Record<BodyPart, readonly { name: string; note: string }[]>
```

- **런타임에 카탈로그와 교집합을 낸다.** `resolveRecommended(part, catalog)`가
  카탈로그에 실제로 있는 이름만 돌려준다. 시드 이름이 바뀌면 그 항목이
  **조용히 빠질 뿐 화면이 깨지지 않는다.**
- ⚠️ **그 대가**: 이름 오타를 타입이 못 잡는다. 그래서 개발 서버 확인에서
  **부위별 개수를 센다**(§8). 단위 테스트는 "카탈로그에 없는 이름은 빠진다" ·
  "부위가 다른 항목은 안 섞인다"를 고정한다.
- 마이그레이션 **0건**. 문구 수정이 배포로 나간다.

### ② 무게 '운동 중 입력' = `weightKg: 0` — 새 필드 없음 (실측 ④)

세트 모델·DB·직렬화 어디도 손대지 않는다. 표시만 `0`일 때 `"운동 중 입력"`으로 읽는다.

### ③ 이력 유무는 **목록이 아니라 개수 질의**로 (실측 ①·②)

`hasCompletedHistory(userId)` — `head: true, count: "exact"`로 행을 하나도
받지 않고 개수만 받는다. 새 RPC도 마이그레이션도 없다.
사용자가 실제로 '최근 운동 불러오기'를 누르면 그때 기존 `loadPastSessions()`가
평소대로 돈다. **1비트를 위해 전량을 받지 않는다.**

---

### ④ 썸네일은 **추천 12개 전용**, `RECOMMENDED` 상수에 얹는다 (목업 2026-08-06)

목업의 결론에 동의한다 — **전 종목 썸네일은 하지 않는다.** 다만 구현은 더 싸게 된다.

```ts
// src/lib/domain/recommended-exercises.ts
type Recommendation = {
  name: string;   // ⚠️ 카탈로그 시드 이름과 글자까지 같아야 한다 (실측 ⑩)
  note: string;   // 초보자용 한 줄
  thumb?: string; // public/exercise-thumbs/{slug}.png — 없으면 부위 태그만
};
```

- **`isBeginnerRecommended` 플래그가 필요 없다** — 이 상수에 있으면 추천이다 (가정 ⑦)
- **`thumb`는 선택 필드다.** 없으면 카드가 텍스트만으로 성립한다 → 12장을 한 번에
  다 못 만들어도 **부분 배포가 된다.** 이미지 제작이 코드 일정을 막지 않는다
- 자산 규약은 배지를 그대로 베낀다 (실측 ⑨): `public/exercise-thumbs/{slug}.png`,
  `next/image`에 `width={72} height={72} sizes="72px"` 명시, 개당 **50KB 이하** 목표
- **검색 결과·지난 기록·내 루틴에는 썸네일을 안 넣는다** (목업 분석과 같은 결론,
  §3 가정 ⑥에서 독립적으로 도달한 자리다)

⚠️ **이미지 제작이 이 작업의 유일한 비-코드 의존이다.** 12장의 톤이 안 맞으면
안 넣느니만 못하다 (목업 분석의 리스크 2). 코드는 `thumb` 없이 먼저 완성하고,
이미지는 준비되는 대로 상수에 경로만 채운다.

### ⑤ 추천 흐름은 **다중 선택 → 다음 → 설정** (목업이 요구 3-7과 갈리는 자리)

⚠️ **원래 지시와 새 목업이 여기서 다르다.**

| | 원래 지시 (요구 3) | 새 목업 (2026-08-06) |
|---|---|---|
| 선택 | "운동 선택 시 세트·횟수·무게 바텀시트를 표시" — **한 개씩** | 카드 다중 선택 + 하단 `운동 0개` · `다음` — **여러 개** |
| 힌트 문구 | — | "처음엔 **3개만** 골라도 충분해요" |

**목업 쪽을 택한다.** 그 힌트 문구가 3개를 권하는데 3개를 담으려면 시트를 세 번
열고 세 번 닫아야 한다 — 화면이 스스로와 모순된다. 대신 요구 3-7·3-8의 실체
(세트·목표·무게를 정한다 · 끝나면 오늘 목록으로 복귀)는 그대로 지킨다:

```
부위 그리드 → 추천 카드 다중 선택(골드 테두리 + '추가됨')
   → 하단 고정 바 '운동 N개' · [다음]
   → 설정 화면: 고른 N개가 행으로, 각 행이 '3세트 · 10회 · 무게 운동 중 입력'
                (행을 누르면 그 자리에서 조절 · 기본값 그대로 두면 안 눌러도 된다)
   → [추가하기] → 시트 전체 닫힘 → 오늘 운동 목록
```

- **N개를 위해 시트를 N번 열지 않는다.** 기본값이 3세트·10회·운동 중 입력이므로
  대부분은 설정 화면을 **읽고 지나간다** — 조절은 예외 경로다
- 카드 **전체가 탭 영역**이다 (`＋ 추가` 버튼만이 아니라)
- ⚠️ **부위 선택은 목업이 아니라 지시를 따른다.** 새 목업의 부위 줄은 다시
  **가로 스크롤**로 보이는데, 요구 3은 "가로 스크롤이 아니라 **버튼 그리드**"라고
  명시했고 첫 목업도 4×2 그리드였다 → **그리드로 간다**

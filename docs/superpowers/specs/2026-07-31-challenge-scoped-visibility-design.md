# 챌린지 참가자와 크루 분리 설계

**작성일:** 2026-07-31

**대상 작업:** 마이그레이션 0051

**출발점:** `docs/superpowers/HANDOFF-2026-07-31-challenge-rooms.md`

**현재 코드 기준:** 커밋 `4e18781`

## 1. 한 줄 결론

챌린지에 참가한 사람은 그 챌린지의 이름과 점수만 볼 수 있고, 서로 친구(크루)가 되지는 않게 한다.

## 2. 왜 필요한가

현재는 초대 링크로 챌린지에 참가하면 서버가 참가자끼리 `crew_links`를 만든다. `crew_links`는 친구 관계를 저장하는 표다. 이 표에는 어느 챌린지에서 생긴 관계인지 적는 칸이 없어서, 챌린지가 끝난 뒤에도 친구 관계가 계속 남는다.

그 결과 다른 챌린지 참가자가 실제 크루 목록과 홈 크루 카드에 나타났다. 사용자는 “챌린지에 잠깐 참가했다”가 아니라 “내 크루에 들어왔다”고 보게 된다.

이번 작업은 두 관계를 다음처럼 분리한다.

| 관계 | 맺는 방법 | 볼 수 있는 것 | 종료 후 |
|---|---|---|---|
| 크루(친구) | 닉네임 요청 후 상대가 수락 | 피드, 운동 알림, 응원, 반응, 콕 | 계속 유지 |
| 챌린지 참가자 | 초대 또는 링크 참가 | 해당 챌린지의 참가자 이름과 랭킹 | 해당 챌린지 결과만 계속 열람 |

## 3. 핵심 원칙

### 3.1 RLS는 넓히지 않는다

RLS(데이터베이스 출입문 규칙): 사용자별로 어떤 자료를 읽을 수 있는지 정하는 문지기다.

기존 RLS에 “같은 챌린지 참가자” 조건을 추가하면 구현은 짧다. 하지만 참가자가 다른 참가자의 운동 세션, 세트, 사진 같은 원본 자료를 직접 읽을 수 있게 된다. 피드·반응처럼 같은 문지기를 이용하는 기능까지 관계가 새어 나갈 수 있다.

따라서 기존 RLS는 그대로 두고, 챌린지 화면에 꼭 필요한 정보만 전용 RPC로 돌려준다.

RPC(서버의 전용 주문 창구): 사용자가 서버에 정해진 일을 요청하면 서버가 권한을 확인하고 필요한 결과만 돌려주는 함수다.

### 3.2 점수 계산은 복제하지 않는다

RPC는 운동 자료를 기존 앱이 먹을 수 있는 모양으로만 돌려준다. 점수는 현재 사용 중인 `foldPeriodStats`가 계속 계산한다.

SQL과 TypeScript 양쪽에 점수 계산을 두 벌로 만들면 시간이 지나면서 계산 결과가 달라질 수 있다. 이번 작업은 자료를 가져오는 길만 바꾸고, 계산기는 바꾸지 않는다.

### 3.3 기존 크루 관계는 자동 삭제하지 않는다

기존 `crew_links`에는 관계가 챌린지 때문에 생겼는지, 사용자가 직접 수락해서 생겼는지 표시가 없다. 추측으로 삭제하면 진짜 친구 관계가 사라질 수 있다.

0051은 새로운 자동 크루 연결만 막는다. 기존 연결을 삭제해야 한다면 현재 연결 목록과 요청 기록을 먼저 확인하고 사용자 승인을 별도로 받는다.

## 4. 선택한 접근법

브라우저 화면과 관리자 화면이 같은 챌린지 전용 RPC를 사용한다.

- 일반 사용자: 해당 챌린지에서 `joined` 또는 `dropped` 상태일 때만 허용한다.
- `invited`: 초대만 받고 아직 참가하지 않았으므로 차단한다.
- 외부인: 해당 챌린지 참가자가 아니므로 차단한다.
- `cancelled`: 취소된 챌린지로 다른 사람 자료를 계속 읽지 못하게 차단한다.
- `ended`: 본인이 참가했던 대결 결과이므로 계속 허용한다.
- `service_role`: 관리자 화면이 사용하는 서버 전용 열쇠다. 관리자 집계에만 명시적으로 허용한다.

브라우저만 RPC를 쓰고 관리자는 기존 직접 조회를 유지하는 방법도 가능하지만, 자료를 가져오는 길이 두 벌이 된다. 화면별 숫자가 달라지는 일을 줄이기 위해 한 경로로 통일한다.

## 5. 데이터베이스 설계

### 5.1 같은 챌린지 관계 판정

0051 초안의 `shares_challenge_with(p_other)`는 어느 챌린지에서 만난 관계인지 인자로 받지 않는다. 특정 챌린지 안에서만 관계를 판정하도록 `challenge_id`를 함께 받게 보강한다.

판정 조건:

1. 요청한 사용자와 상대가 같은 `challenge_id`에 있다.
2. 두 사람 모두 `joined` 또는 `dropped`다.
3. 챌린지 상태가 `cancelled`가 아니다.

RPC가 “요청한 사용자가 이 챌린지를 볼 수 있는가”를 검사할 때도 같은 조건을 사용한다. 현재 `is_challenge_participant()`는 상태를 보지 않아서 `invited`도 참으로 판정하므로, 0051 조회 권한의 최종 문지기로 그대로 사용하지 않는다.

### 5.2 참가자 프로필 RPC

`get_challenge_participant_profiles(challenge_id)`는 다음 세 칸만 반환한다.

- `id`
- `nickname`
- `avatar_url`

참가자 이름을 보여주는 데 필요하지 않은 프로필 정보는 반환하지 않는다.

### 5.3 챌린지 기간 운동 RPC

`get_challenge_period_sessions(challenge_id)`는 다음 자료만 반환한다.

- 참가자 ID
- 운동 완료 시각
- 타바타 시간
- 운동 종목 종류·이름·부위
- 세트의 중량·횟수·거리·시간과 완료 여부

기간은 기존 앱과 같은 넉넉한 검색 범위를 사용하고, 최종 날짜 판정은 `foldPeriodStats`가 한국 시간 기준으로 한다. 사진 필수 챌린지는 사진이 있는 세션만 포함한다.

일반 사용자는 참가 권한 검사를 통과해야 한다. 관리자 서버에서 호출할 때만 `service_role`을 허용한다.

### 5.4 참가 RPC에서 자동 친구 연결 제거

다음 두 함수에서 `crew_links`를 만드는 반복문만 제거한다.

- `accept_challenge_invite`
- `join_challenge_with_code`

동시 참가 충돌을 막는 잠금, 상태 검사, 오류 코드, 참가자 행 생성은 현재 운영 정의와 동일하게 유지한다. 오래된 앱이 응답 필드를 기대할 수 있으므로 `crewLinked`는 제거하지 않고 `0`을 반환한다.

## 6. 앱 설계

### 6.1 공용 자료 변환

`src/lib/challenge.ts`에 다음 역할을 둔다.

- `getChallengeParticipantProfiles(challengeId)`: 참가자 이름·아바타 RPC 호출
- `getChallengePeriodSessions(challengeId, client?)`: 운동 RPC 호출 후 기존 `PeriodSessionRow[]` 모양으로 변환
- `getPeriodStatsByUser(...)`: 변환된 행을 `foldPeriodStats`에 전달

자료 모양을 바꾸는 코드는 한 곳에만 둔다. 챌린지 탭, 홈, 소셜, 관리자가 각자 변환 코드를 갖지 않는다.

### 6.2 호출부 전수 변경

다음 경로를 함께 바꾼다.

1. `src/app/(tabs)/challenge/page.tsx`
   - 참가자 프로필을 새 RPC에서 받는다.
   - 점수를 챌린지 ID 기준 RPC에서 받는다.

2. `src/lib/challenge.ts`의 `getActiveChallengeRanking`
   - 새 기간 운동 RPC를 사용한다.
   - 이 함수를 쓰는 홈·소셜·관리자 경로가 함께 전환된다.

3. `src/components/home/challenge-performance-card.tsx`
   - `getGroupMemberProfiles(group_id)`를 제거하고 챌린지 참가자 프로필 RPC를 사용한다.

4. `src/lib/admin/queries.ts`
   - 관리자용 `service_role` 호출이 실제로 새 RPC를 통과하는지 확인한다.
   - 참가 인원 수가 그룹 인원이 아니라 챌린지 참가 인원인지 함께 확인한다. 잘못돼 있으면 같은 범위 안에서 고친다.

### 6.3 화면 문구 정리

챌린지 참가를 친구 가입으로 오해하게 만드는 문구를 바꾼다.

- `크루 초대` → `챌린지 초대`
- `챌린지 크루 성과` → `챌린지 참가자 성과`
- 챌린지 랭킹 안의 `크루원` → `참가자`
- `링크로 참가하면 서로 크루가 돼요` → `링크로 참가해도 서로 크루가 되지는 않아요`

진짜 친구 기능인 크루 탭·피드·응원 화면의 “크루” 문구는 바꾸지 않는다. 변경 전 전체 검색으로 챌린지 문맥인지 실제 친구 문맥인지 나눠 확인한다.

## 7. 사용자 화면의 작동 순서

```text
사용자가 초대 링크를 엶
→ 서버가 챌린지 참가자 행만 만듦
→ 친구 관계인 crew_links는 만들지 않음
→ 챌린지 화면이 참가자 전용 RPC로 이름과 운동 자료를 요청
→ 서버가 같은 챌린지의 정식 참가자인지 검사
→ 앱이 기존 foldPeriodStats로 점수 계산
→ 해당 챌린지 랭킹에만 참가자가 표시됨
```

크루 목록, 피드, 운동 알림, 응원, 반응 화면에는 새 참가자가 나타나지 않는다.

## 8. 오류가 생겼을 때 보이는 현상

| 문제 | 사용자에게 보이는 현상 | 잡는 검증 |
|---|---|---|
| 앱보다 0051을 먼저 적용 | 새 비크루 참가자의 랭킹이 잠시 0으로 보임 | 적용 순서 고정 |
| 참가 상태 검사가 느슨함 | 초대만 받은 사람이 랭킹을 볼 수 있음 | `invited` 차단 검사 |
| 관리자 예외 누락 | 관리자 챌린지 달성률이 비거나 오류 | 관리자 RPC 검사 |
| 호출부 일부 누락 | 챌린지 탭은 정상인데 홈 카드 이름이 비어 있음 | 호출부 전체 검색·화면 확인 |
| 옛 D5 단언 유지 | 정상 변경인데 검증 스크립트가 실패 | 두 검증 스크립트 동시 수정 |
| 점수 자료 모양 불일치 | 기존 점수와 새 점수가 다름 | 집계 동등성 검사 |

## 9. 검증 설계

### 9.1 단위 검증

- RPC JSON 자료가 `PeriodSessionRow`로 정확히 바뀐다.
- `foldPeriodStats` 기존 테스트는 그대로 통과한다.
- 초대 화면에 “크루가 되지 않는다”는 문구가 보인다.
- 옛 “서로 크루가 돼요” 문구는 보이지 않는다.

### 9.2 실제 데이터베이스 검증

`challenge-invite-link-check.mjs`와 `challenge-room-check.mjs`를 함께 수정한다.

반드시 확인할 내용:

1. 링크 참가 전후 `crew_links` 개수가 같다.
2. 닉네임 초대 수락 전후 `crew_links` 개수가 같다.
3. `joined`·`dropped` 참가자는 같은 챌린지 프로필과 점수를 읽는다.
4. `invited`·외부인·취소된 챌린지는 읽지 못한다.
5. 종료된 챌린지는 결과를 읽는다.
6. 챌린지 참가만으로 피드·응원·반응 권한이 생기지 않는다.
7. 관리자 `service_role`은 챌린지 집계를 읽는다.
8. 기존 `7월 GND 챌린지`의 세션 집합과 점수가 전후 동일하다.
9. 실행 후 실사용 계정 수와 기존 크루 연결 수가 원래대로다.

실제 데이터베이스 검증은 운영 Supabase에 붙으므로 계정 삭제는 `_safe-delete.mjs` 보호 장치를 반드시 거친다. 익명 계정 가입 제한을 피하도록 스크립트 사이에 필요한 간격을 둔다.

### 9.3 전체 검증

- `pnpm lint`
- `pnpm typecheck`
- `pnpm test`
- `pnpm build`
- `challenge-invite-link-check.mjs`
- `challenge-room-check.mjs`
- `challenge-consent-test.mjs`
- `challenge-subset-start-check.mjs`
- `challenge-aggregation-parity.mjs`
- `rls-test.mjs`
- 기존 기준선에 포함된 나머지 챌린지·소셜 검증

실패가 하나라도 있으면 적용 또는 배포를 중단한다.

## 10. 적용 순서

1. 앱 코드와 검증 코드를 먼저 작성한다.
2. 데이터베이스 없이 가능한 lint·typecheck·unit·build를 통과시킨다.
3. 사용자에게 0051 적용 내용을 보여주고 SQL Editor에서 Run을 요청한다.
4. `pnpm db:snapshot`으로 `docs/db-current-schema.sql`을 갱신한다.
5. 실제 데이터베이스 검증을 실행한다.
6. `pnpm dev`로 `localhost:3000`을 열어 챌린지 탭·홈 카드·관리자 화면을 직접 확인한다.
7. 초대 링크 전 과정을 새 시크릿 창 또는 폰에서 확인한다.
8. 검증된 코드와 문서만 골라 커밋한다.
9. 운영 배포 내용을 사용자에게 보여주고 승인을 받는다.
10. `main` 전용 워크트리에서 Vercel 운영 배포를 실행한다.
11. 프로덕션 주소와 사용자 폰에서 최종 확인한다.

앱 코드가 준비된 뒤 0051 적용과 배포를 가깝게 이어서, 운영 중인 옛 앱과 새 데이터베이스가 서로 다른 규칙을 사용하는 시간을 최소화한다.

## 11. 성공 기준

- 챌린지 참가가 `crew_links`를 새로 만들지 않는다.
- 다른 챌린지 참가자가 크루 목록과 홈 크루 카드에 나타나지 않는다.
- 같은 챌린지의 정식 참가자는 닉네임과 랭킹을 본다.
- 초대만 받은 사람과 외부인은 남의 랭킹 자료를 보지 못한다.
- 종료된 챌린지 결과는 참가자에게 계속 보인다.
- 친구 전용 피드·응원·반응 권한은 넓어지지 않는다.
- 관리자 챌린지 집계가 기존처럼 표시된다.
- 기존 진행 중 챌린지의 점수가 바뀌지 않는다.
- 모든 자동 검증과 로컬 화면 확인이 통과한다.
- 사용자 승인 전에는 운영 배포하지 않는다.

## 12. 이번 작업에서 하지 않는 것

- 기존 크루 관계 자동 삭제
- 그룹·그룹 멤버 테이블 제거
- 완료 보너스 변경
- 새로운 관리자 기능 추가
- 챌린지 중도 참가 허용
- 결제·알림·다국어 같은 별도 기능 추가
- 운영 배포 자동 실행

# 설계 — 챌린지 방 (다중 크루·다중 챌린지)

- 작성: 2026-07-29
- 선행: `2026-07-28-crew-link-graph-design.md` (0038·0039 적용 완료)
- 인수인계서 §7이 "다음 스펙"으로 미뤄 둔 **챌린지 개편**이 이 문서다.

## 1. 문제

한 사람이 여러 챌린지를 동시에 뛸 수 없다. 막고 있는 것은 두 가지다.

1. **`challenges_one_live`** — `group_id`당 `setup`/`active` 챌린지 1개 (`0006:23`). 그룹이 하나면 챌린지도 하나다.
2. **화면의 단일 그룹 가정** — `getMyGroups()[0]`이 네 곳에 박혀 있다 (`challenge-performance-card.tsx:47`, `king-card.tsx:66`, `record/page.tsx:187`, `challenge/page.tsx:131`).

더 깊은 곳에 세 번째가 있다. **`workout_sessions.group_id`가 단수**라 운동 한 번은 한 그룹에만 집계된다 (`getPeriodStatsByUser`가 `.eq("group_id", groupId)`). 챌린지 두 개를 뛰어도 오늘 운동은 한쪽에만 잡힌다.

DB는 이미 한 사람이 여러 그룹에 속하는 것을 허용한다 (`group_members`는 `unique(group_id, user_id)`뿐). 막고 있는 것은 위 세 가지다.

## 2. 결정 사항

| # | 결정 | 근거 |
|---|---|---|
| D1 | **챌린지가 곧 방.** 그룹 개념을 없앤다 | 0039로 "크루 = 상호 수락"이 이미 됐다. 그룹은 그 위에 남은 중복 개념이다 |
| D2 | 운동은 **기간이 겹치는 모든 챌린지에 자동 반영** | 사용자가 고를 게 없어 "운동했는데 왜 안 올라가지" 사고가 구조적으로 사라진다 |
| D3 | **시작일이 되면 자동 시작** | 전원 게이트는 챌린지가 늘수록 자주 막힌다 |
| D4 | **전원 동의(0025) 제거** | 자동 시작이면 동의가 진행을 막을 수 없어 장치로서 기능하지 않는다 |
| D5 | 초대 수락 = **참가자 전원과 자동 크루 맺기**(완전 연결) | 새 판정 함수 없이 랭킹판 닉네임 노출이 해결된다 |
| D6 | **중도 합류 불가** — 시작 전까지만 | 같은 기간·같은 조건이라야 순위가 의미를 갖는다. 놓쳤으면 새 챌린지를 만들면 된다 |
| D7 | 너무 쉬운 목표는 **자동 하한선**으로 차단 | D4로 사람이 거르는 장치가 사라진 자리를 규칙이 대신한다 |
| D8 | 홈은 **대표 챌린지 1개** + 나머지는 탭 | 홈 길이를 지금과 같게 유지 |
| D9 | 완료 목표 보너스 **개당 +3 → +9**, 최대 3개(+27) | 현재는 목표를 적게 거는 쪽이 유리하다 (§5.1) |
| D10 | **추가 → 전환 → 정리** 3단계 마이그레이션 | 0038→0039에서 검증된 이 저장소의 패턴 |
| D11 | **동일 KPI 유형 중복 설정 금지** | D9의 개당 보너스를 목표 쪼개기로 뽑아내는 것을 막는다 (§5.2) |
| D12 | 크루 관계는 **기존 크루 해제 기능으로 직접 끊는다** | 챌린지가 관계를 자동으로 회수하지 않는다. 끊는 주체는 사용자다 |
| D13 | 실적 없는 유형의 목표는 **보너스 대상 1개까지만** | 하한선을 검증할 수 없는 목표로 +27을 뽑는 구멍을 막는다. 새 상수를 만들지 않는다 (§5.3) |

**D9를 "목표 개수와 무관한 고정 최대 보너스"로 바꾸지 않는다.** 고정 최대치로 바꾸면 `목표 1개 중 1개 완료 = 목표 3개 중 3개 완료 = 같은 보너스`가 되어, 목표를 1개만 거는 것이 다시 가장 안전해진다. 여러 목표를 걸고 실제로 달성하도록 유도하려는 설계 목적과 정면으로 어긋난다.

**현재 제품 범위는 공개 챌린지가 아니라 지인 중심의 소규모 챌린지다.** D5(참가자 전원 자동 크루 연결)는 이 전제 위에서만 성립한다 — §9 참조.

## 3. 데이터 모델

### 3.1 신설 — `challenge_participants`

```
challenge_id  uuid    → challenges(id) on delete cascade
user_id       uuid    → profiles(id) on delete cascade
role          text    'host' | 'member'
status        text    'invited' | 'joined' | 'dropped'   -- dropped: §4.2
invited_by    uuid    → profiles(id)
joined_at     timestamptz
primary key (challenge_id, user_id)
```

`groups`가 하던 "명단" 역할을 챌린지가 직접 한다. 초대는 `status='invited'` 행으로 남고, 수락하면 `'joined'`이 된다.

RLS는 0038의 방식을 따른다 — `revoke all` + `grant select`만 주고 **쓰기는 전부 RPC로만**. SELECT는 "내가 참가자인 챌린지의 행"으로 좁힌다.

### 3.2 변경·제거

| 대상 | 처리 | 시점 |
|---|---|---|
| `challenges_one_live` 인덱스 | **드롭** — 챌린지 개수 제한이 풀리는 지점 | 0043 |
| `challenges.group_id` | 드롭 | 0044 |
| `user_goals.group_id` | 드롭 (`challenge_id`로 충분) | 0044 |
| `workout_sessions.group_id` | 읽지 않음 → 드롭 | 0043 읽기 중단 / 0044 드롭 |
| `challenge_goal_approvals` (0025) | 테이블·RPC·UI 전부 제거 | 0043 |
| `groups` · `group_members` | 드롭 | 0044 |
| `is_group_member` · `shares_group_with` | 드롭 | 0044 |

마이그레이션 번호는 **응원 포인트 스펙이 0041을 쓰는 것을 전제로** 0042부터 잡았다. 순서가 바뀌면 하나씩 당긴다.

**세션 `group_id`를 버리는 것이 이 설계의 핵심이다.** 운동이 어느 방에도 속하지 않게 되면서 D2("기간 겹치는 모든 챌린지에 반영")가 계산 규칙 하나로 성립한다. 세션↔챌린지 연결 테이블이 필요 없다.

### 3.3 `visibility='group'`의 의미 재정의

DB 값은 기존 데이터 호환을 위해 `'group'`으로 유지한다. 값을 바꾸면 기존 행 전체를 건드려야 하는데 이득이 없다. 대신 **의미를 명시적으로 재정의한다.**

> `visibility='group'` = **지금 `crew_links`로 연결된 상호 크루에게 공개**

화면 문구를 "크루 공개"로 바꾸는 것으로 끝내지 않는다. 관련 RLS·조회 함수가 전부 `is_crew_with` 기준이어야 한다.

**현황 조사 결과 — 대부분은 0039에서 이미 전환됐다.**

| 지점 | 현행 | 필요 조치 |
|---|---|---|
| `workout_session_crew_visible` (`0039:458`) | `is_crew_with` + 자기접근 | ✅ 없음 |
| `session_crew_shared` (`0039:480`) | `is_crew_with` + 자기접근 | ✅ 없음 |
| `sessions_select_own_or_crew` (`0039:494`) | `is_crew_with` + 자기접근 | ✅ 없음 |
| `send_cheer` (`0039:509`) | `is_crew_with` | ✅ 없음 |
| Storage `workout_images_read_own_or_crew` (`0005:60`) | `workout_session_crew_visible` 경유 | ✅ 없음 (간접 의존) |
| **`sessions_insert_own_draft` (`0004:226`)** | `group_id is null or is_group_member(group_id, auth.uid())` | ⚠ **0043에서 제거** |

마지막 줄이 남은 유일한 직접 참조다. 0039가 "그룹은 챌린지 몫으로 남는다"며 의도적으로 남긴 것인데(`0039:492` 주석), 그룹이 사라지면 이 정책이 없는 테이블을 참조하게 된다. **0043에서 `group_id` 조건을 통째로 들어낸다.**

**자기 세션 접근 — 회귀 방지 대상.** 0004→0039 전환 때 `is_group_member`가 세션 주인 본인에게도 true였던 탓에 자기접근이 암묵적으로 성립하고 있었고, `is_crew_with`는 자기 자신에게 항상 false라 0039가 세 함수에 `s.user_id = auth.uid()` 분기를 명시적으로 복원했다. **이번 전환에서 같은 함정이 재발하지 않도록 검증 ㉜에 고정한다** — 세션 작성자는 크루 여부와 무관하게 항상 자기 세션을 읽을 수 있어야 한다.

## 4. 참가 · 시작 흐름

```
[방장] 챌린지 만들기 (이름·기간·내 KPI)  →  status='setup', 방장 joined
   ↓
[방장] 초대 — 내 크루 목록에서 고르거나 닉네임 검색
   ↓  (0038의 search_profile_by_nickname 재사용)
   ↓  challenge_participants status='invited' + 알림 challenge_invite
[초대받은 사람] 수락  →  status='joined'
   ↓  이 순간 기존 joined 참가자 전원과 crew_links 생성 (D5, 완전 연결)
[초대받은 사람] 내 KPI 설정  →  참가 확정
   ↓
시작일 00:00 KST  →  자동 active, 명단 잠김
```

### 4.1 자동 시작 — 정각 전환이 아니다

정확한 동작은 이렇다.

> **시작일 00:00 KST가 지난 뒤, 첫 챌린지 화면 진입(지연 전환)과 09:00 KST 크론 중 먼저 실행되는 경로에서 `active`로 전환된다.**

- **크론** — `vercel.json`의 09:00 KST 브리핑에 얹는다
- **지연 전환** — 챌린지 화면 진입 시 시작일이 지난 `setup`이 있으면 RPC 호출

크론만 두면 자정~9시 사이에 앱을 연 사람이 "시작일인데 아직 setup"을 본다. 지연 전환만 두면 아무도 안 열 때 영영 안 넘어간다. **RPC를 멱등하게 만들어 둘 다 안전하게 부른다.**

**자정 크론을 새로 만들지 않는다.** 제품상 00:00 정각 전환이 필요하지 않다 — 전환이 몇 시간 늦어도 집계는 `start_date` 기준이라 그날 운동이 누락되지 않는다. 크론을 하나 더 두는 비용이 이득보다 크다.

이 표현이 중요한 이유는 화면 문구 때문이다. "자정에 시작돼요"라고 써 두면 새벽에 들어온 사용자가 버그로 인식한다. **"시작일이 되면 자동으로 시작돼요" 정도로 적는다.**

### 4.2 시작 시점의 명단 확정

| 상태 | 처리 |
|---|---|
| `joined` + 목표 1개 이상 | 참가 확정 |
| `joined` + 목표 0개 | 명단에서 제외 + 알림 통지 |
| `invited` 미응답 | 초대 만료 (행 삭제) |

**"제외"는 행 삭제가 아니라 `status='dropped'` 전환이다.** 삭제하면 이미 맺어진 `crew_links`의 근거가 사라져 "왜 이 사람이 내 크루지"를 설명할 수 없게 된다. `dropped` 행은 랭킹·집계에서 빠지지만 이력으로 남는다. 따라서 `status`의 값은 `'invited' | 'joined' | 'dropped'` 셋이다.

**이미 맺어진 `crew_links`는 남긴다.** 크루 관계는 챌린지보다 오래 사는 개념이고, 되돌리면 "어제 보이던 사람이 오늘 사라지는" 현상이 생긴다.

### 4.3 시작 후

명단·목표 모두 잠긴다. 중도 합류 불가(D6), 목표 수정 불가(기존 `challenge_in_setup` RLS 그대로). 방장 취소만 가능하다.

종료도 크론이 자동 처리한다. 지금은 누군가 "🏆 결과 발표하기"를 눌러야 `ended`가 되는데, 챌린지가 여러 개면 아무도 안 누른 채 방치되는 게 확실하다.

## 5. 점수 규칙

### 5.1 완료 목표 보너스 — 개당 +3 → +9

현재 규칙에서는 **목표를 적게 거는 쪽이 유리하다.** 두 힘이 반대로 작용한다.

- 개수가 많을수록 유리 — 완료 목표 보너스 (개당 +3, 최대 3개, `goal-score.ts:66`)
- 개수가 적을수록 유리 — 달성률이 **평균**이고 목표마다 100%에서 잘린다 (`goal-score.ts:35`). 한 목표를 200% 해도 다른 목표의 부진을 못 메운다

두 번째가 훨씬 세다. 참여율 100% 가정, 현행(+3):

| 참가자 | 평균 달성률 | 보너스 | 종합 |
|---|---|---|---|
| 목표 1개, 100% | 100 | +3 | **103** |
| 목표 3개, 평균 90% (2개 완료) | 90 | +6 | **98** |

목표 1개를 확실히 달성하는 게 3개를 평균 90% 하는 것보다 5점 앞선다. 합리적인 참가자라면 자신 있는 목표 하나만 건다.

역전시키려면 개당 보너스가 **8점을 넘어야 한다** (92 + 2B > 100 + B → B > 8). `COMPLETED_GOAL_BONUS_PER`를 **9**로 올린다 (`COMPLETED_GOAL_BONUS_MAX`는 3 유지, 최대 +27).

변경 후:

| 참가자 | 평균 달성률 | 보너스 | 종합 |
|---|---|---|---|
| 목표 3개, 전부 100% | 100 | +27 | **127** |
| 목표 3개, 평균 90% (2개 완료) | 90 | +18 | **110** |
| 목표 1개, 100% | 100 | +9 | **109** |
| 목표 3개, 평균 80% (1개 완료) | 80 | +9 | **93** |

"많이 걸고 **실제로 해낸** 사람이 이긴다"가 성립한다. 3개를 걸고 2개만 완료하면 1개 완주자를 1점 앞설 뿐이라, 많이 거는 것은 여전히 리스크다 — 의도한 바다.

⚠ **화면 문구도 같이 고쳐야 한다.** `setup-sheet.tsx:337`에 "완료 1개당 +3점, 최대 3개"가 하드코딩돼 있다. 상수만 바꾸고 문구를 두면 화면과 실제 계산이 어긋난다.

### 5.2 동일 KPI 유형 중복 금지 (D11)

D9의 개당 +9는 **목표를 쪼개서 뽑아낼 수 있다.** 같은 운동일 목표를 "가슴 운동일", "등 운동일", "하체 운동일"처럼 세 개로 나누면 실질적으로 한 종류의 노력으로 완료 목표 3개(+27)를 받는다.

규칙:

- 같은 챌린지에서 **동일 KPI 유형은 중복 설정할 수 없다**
- 목표는 현행 시스템이 지원하는 **서로 다른 KPI 유형으로만 최대 3개**
- 서버 RPC와 화면 **양쪽**에서 차단한다

**화면에는 이미 차단이 있다** — `setup-sheet.tsx:234`의 `new Set(types).size !== types.length` 검사가 "같은 지표의 목표가 두 개 있어요"로 막는다. **없는 것은 서버 쪽이다.** `saveMyGoals`는 그대로 insert하므로 RPC를 우회하면 뚫린다. `validate_goal_floor`에 같은 검사를 넣는다.

여기서 "KPI 유형"은 `GoalType` 열거값이다 (`goal-score.ts:8`). `weight_days`의 `qualifier`(하루 최소 부위 수)가 달라도 **같은 유형이므로 중복이다** — 부위별로 쪼개는 것이 바로 막으려는 행동이다.

### 5.3 목표 자동 하한선 (D7)

```
하한 = (직전 28일 해당 유형 실적) × (챌린지 기간 ÷ 28)
```

**28일의 기준점은 "목표를 저장하는 시점"이다** — 챌린지 시작일이 아니다. 시작일 기준으로 잡으면 미래 구간이 섞여 설정 시점에 계산할 수 없다.

예: 지난 28일 웨이트 운동일 14일 → 28일 챌린지에서 12일 입력 시 *"지난 4주에 14일 하셨어요. 최소 14일부터 가능해요"* 로 차단.

- 검증은 **화면과 RPC 양쪽**에 둔다 — 화면만 두면 우회된다
- 순수 계산은 `src/lib/domain/goal-floor.ts`로 빼서 TDD 대상으로 삼는다 (RPC와 같은 규칙을 공유)

#### 반올림 — 항상 올림, 단위는 KPI 유형별

기간이 28일이 아니면 결과가 거의 항상 소수가 된다. **모든 유형에서 올림**한다 — 내림하면 하한선이 실적보다 낮아져 장치가 무력해진다.

올림 단위는 **현행 앱이 실제로 저장·표시하는 최소 단위**를 그대로 쓴다. 새 단위를 만들지 않는다. 근거는 두 가지다 — `user_goals.target_value`가 `numeric(10,1)`이고(`0006:35`), 입력 UI가 `round1`(소수 첫째 자리)로 값을 다듬는다(`setup-sheet.tsx:77`).

| KPI 유형 | 단위 | 올림 단위 |
|---|---|---|
| `weight_reps` · `bodyweight_reps` · `tabata_count` | 회 | **1** (정수) |
| `weight_days` · `bodyweight_days` | 일 | **1** (정수) |
| `cardio_distance` | km | **0.1** |
| `cardio_time` · `bodyweight_time` | 분 | **0.1** |

`volume`(kg)은 레거시 표시 전용이라 신규 설정 대상이 아니다 (`setup-sheet.tsx:19`의 `CATEGORY_TYPES`에 없음). 하한선 계산에서도 제외한다.

```
직전 28일 운동일 13일
챌린지 기간 21일
13 × 21 ÷ 28 = 9.75
최소 목표 = 10일        (정수 올림)

직전 28일 유산소 42.3km
챌린지 기간 21일
42.3 × 21 ÷ 28 = 31.725
최소 목표 = 31.8km      (0.1 올림)
```

#### 실적 없는 목표 — 보너스 대상에서 1개까지만 (D13)

"직전 실적이 없으면 통과"만 두면 실적 없는 KPI로 매우 쉬운 목표 3개를 걸어 `+27`을 가져간다. D9를 올린 만큼 이 구멍이 커졌다. 신규 계정만의 문제가 아니다 — **기존 사용자도 자기가 안 해본 유형만 골라 걸면 하한선이 0이라 똑같이 뚫린다.**

**절대 하한값을 새로 만들지 않는다.** 현행 앱에 KPI 유형별 절대 하한값은 존재하지 않고(검증은 `setup-sheet.tsx:243`과 `0006:35`의 "0보다 크다" 둘뿐), 있는 것은 `GOAL_TYPE_META.defaultTarget`·`PER_DAY_DEFAULT`인데 둘 다 하한이 아니라 입력 편의용 초기값이다. 여기서 새 숫자를 만들면 근거 없는 상수가 9개 생긴다.

대신 **보너스 대상 개수를 제한한다.**

```
보너스 대상 완료 목표 수
  = (직전 28일 실적이 있는 유형의 완료 목표 수)
  + min(1, 직전 28일 실적이 없는 유형의 완료 목표 수)
```

즉 **하한선 검증을 실제로 거친 목표만 보너스를 온전히 받고, 검증할 수 없었던 목표는 몇 개를 걸든 1개로 셈한다.** `COMPLETED_GOAL_BONUS_MAX = 3` 상한은 그 위에 그대로 적용된다.

| 상황 | 보너스 대상 | 보너스 |
|---|---|---|
| 완전 신규가 쉬운 목표 3개 전부 완료 | 0 + 1 = 1 | **+9** |
| 실적 있는 유형 2개 + 새 유형 1개, 전부 완료 | 2 + 1 = 3 | **+27** |
| 안 해본 유형 3개만 걸고 전부 완료 | 0 + 1 = 1 | **+9** |
| 실적 있는 유형 3개 전부 완료 | 3 + 0 = 3 | **+27** |

**감수하는 것** — 처음 도전하는 종목은 보너스를 온전히 못 받는다. 새 종목을 억제하는 방향이라 이상적이지 않다. 다만 목표 자체는 그대로 설정되고 **달성률 평균에는 100% 반영**되므로 도전이 막히지는 않으며, 한 챌린지를 돌면 실적이 쌓여 다음부터 풀린다. 검증할 수 없는 목표에 최대 보너스를 주는 것보다 이쪽이 낫다.

계산은 `src/lib/domain/goal-floor.ts`가 아니라 **`goal-score.ts`에 둔다** — `completedGoalCountOf`가 이미 완료 목표를 세는 곳이고, 보너스 규칙이 두 파일로 갈라지면 서버 RPC와 어긋난다.

### 5.4 집계

`user_id` + 기간으로만 집계한다 (세션 `group_id` 안 봄). 사진 인증 필수 여부는 챌린지마다 다를 수 있으므로 지금처럼 챌린지별 필터로 처리한다 — **같은 운동이 A 챌린지엔 잡히고 B엔 안 잡힐 수 있다.**

랭킹 계산을 클라이언트(`getActiveChallengeRanking`)에서 `get_challenge_ranking` 정의자 RPC로 옮긴다. 0040이 "챌린지 개편 몫"이라고 미뤄 둔 부분이다 (`0040:9`).

지금은 열람권 잠금이 화면 규칙일 뿐이라 브라우저에서 `user_goals`를 직접 읽으면 뚫린다. RPC로 옮기면 진짜 데이터 경계가 된다.

## 7. 마이그레이션 (D10)

### 0042 — 추가만 (앱 동작 변화 없음)

`challenge_participants` + RLS, §3.3의 RPC 8종, **기존 챌린지의 `group_members`를 참가자로 백필**(`created_by`→`host`, 나머지 `member`, 전부 `joined`).

앱이 아직 이걸 읽지 않으므로 적용해도 지금과 똑같이 돈다. **되돌릴 지점이 여기다.**

#### 백필 — 챌린지 단위 가드를 쓰지 않는다

0038은 `where not exists (select 1 from crew_links)`라는 **테이블 단위** 가드를 썼다. 여기에 같은 방식(챌린지 단위 `where not exists`)을 쓰면 안 된다. **부분 실패 후 복구를 막기 때문이다** — 챌린지의 참가자 3명 중 1명만 들어간 상태에서 재실행하면 "이미 행이 있으니 통째로 건너뜀"이 되어 나머지 2명이 영영 안 들어온다.

**행 단위 충돌 처리로 간다.**

1. 모든 기존 챌린지의 `created_by`를 `host` · `joined`로 삽입
2. 해당 챌린지의 나머지 `group_members`를 `member` · `joined`로 삽입
3. 같은 사용자가 1·2 양쪽에 걸리면 **`host` 역할을 유지**
4. 재실행 시 기존 참가자의 `status`·`role`을 덮어쓰지 않음
5. 재실행으로 `dropped` 사용자가 다시 `joined`가 되지 않음

`(challenge_id, user_id)`가 PK이므로 `on conflict (challenge_id, user_id) do nothing`이 3·4·5를 한꺼번에 만족시킨다. **`do update`를 쓰면 안 된다** — `dropped`를 되살린다.

순서도 중요하다. **`created_by`를 먼저 넣어야** 3이 성립한다. 반대로 넣으면 방장이 `member`로 먼저 들어가고 `do nothing`에 막혀 `host`가 못 된다.

#### `created_by`가 `group_members`에 없는 경우

방장이 그룹을 나갔거나 데이터가 어긋난 챌린지가 있을 수 있다. **`created_by`는 `group_members` 소속 여부와 무관하게 반드시 `host` · `joined`로 들어간다** — 1단계를 `group_members` 조인이 아니라 `challenges.created_by`에서 직접 뽑는 이유다. 방장 없는 챌린지가 생기면 취소할 사람이 없어진다.

### 8.1 함정 — 함수 현행 정의는 "가장 나중에 덮어쓴 것"

이 저장소는 마이그레이션마다 `create or replace function`으로 같은 함수를 덮어쓴다. **옛 번호 파일을 고치면 아무 일도 안 일어난다.** 0043에서 기존 함수를 손댈 때는 파일에서 베끼지 말고 DB에서 `pg_get_functiondef`로 현행 정의를 뽑는다. (인수인계서 §5.1)

## 9. 범위 밖

- **응원·코멘트 포인트 지급** — 별도 스펙 (`2026-07-29-cheer-points-design.md`). 챌린지 개편과 독립적이며 더 작아서 먼저 진행한다.
- 챌린지 개수 상한, 초대 남용 방지(pending 상한)
- **공개 챌린지·누구나 참가** — 도입한다면 **D5(참가자 전원 자동 크루 연결)를 반드시 재검토해야 한다.** D5는 "지인 중심 소규모"라는 현재 범위 위에서만 성립한다. 모르는 사람 50명이 참가하는 챌린지에서 전원 자동 연결이 일어나면 크루 목록이 무의미해지고, 피드·응원·프로필이 사실상 공개된다. 공개 챌린지에서는 "참가자 전용 판정 함수(`is_challenge_peer`)를 따로 두고 크루는 맺지 않는" 쪽이 맞다 — 이번에 D5를 골라 피한 복잡도를 그때는 치러야 한다
- KPI 유형별 절대 하한값 — D13으로 대체했다. 실적이 쌓이지 않은 유형에 근거 없는 상수 9개를 만드는 대신 보너스 대상에서 제한한다
- 챌린지별 열람권 분리 (지금은 대표 챌린지 하나만)
- 팀전·2:2 대결

## 1. 왜 이 작업이 시작됐나 — "개발서버에 조인이 안되는데?"

사용자가 챌린지 초대 링크로 가입을 시도했더니 **`챌린지에 참가하지 못했어요.
초대 링크를 다시 확인해 주세요.`** 가 떴다.

**근본 원인은 코드가 아니라 데이터였다. 참가 가능한 링크가 DB에 하나도 없었다.**

| 챌린지 | 상태 | `invite_code` |
|---|---|---|
| `test` · `개발 확인용 챌린지` · `7월 GND 챌린지` | **active** | **null** |
| `개노답 챌린지` 외 3개 | cancelled | `GND-WMXHK` 등 |

익명 계정으로 **앱과 같은 경로**를 재현해 확인한 실제 오류:

```
취소된 챌린지의 코드 (GND-WMXHK) → invalid_status:cancelled
존재하지 않는 코드               → invalid_invite_code
active 챌린지 (코드가 없다)       → invalid_invite_code
셋 다 isNotNewcomer=false → 폴백도 안 타고 바깥 catch로 간다
```

**왜 코드가 없었나:** 초대 코드는 방장이 **`setup` 단계에서 `링크 만들기`를 눌러야만**
생긴다(`issue_challenge_invite_code`가 `status <> 'setup'`이면 거절). 그 버튼을 누르기
전에 챌린지를 시작하면 **코드를 영영 만들 수 없다.** 참가도 `setup`에서만 되므로
그 방은 아무도 부를 수 없게 된다.

## 2. 한 것 — 커밋 `21103bd` (미배포)

### 2.1 ⚠️ 마이그레이션 0064 — **먼저 Run해야 한다**

`supabase/migrations/0064_challenge_invite_code_at_creation.sql`

`create_challenge_room`이 챌린지를 만들 때 `invite_code`도 같이 넣는다.

- **공정성 정책은 그대로다.** 시작하면 `join_challenge_with_code`가 여전히
  `invalid_status`로 막는다. 사라지는 것은 "링크 만들기를 깜빡해서 영영 못 부르는"
  함정뿐이다.
- `issue_challenge_invite_code`는 **그대로 둔다.** 이미 멱등이라
  (`if c.invite_code is not null then return c.invite_code`) 코드가 미리 있으면
  그걸 돌려준다. 발급 규칙이 두 곳으로 갈리지 않는다.
- 기존 active 챌린지에 **소급 적용하지 않는다.** `setup`이 아니라 어차피 참가가
  안 되므로 죽은 링크만 늘어난다.
- **지금 돌려도 안전하다** — 새로 만드는 챌린지에 값이 하나 더 채워질 뿐이고,
  운영에 떠 있는 앱은 동작이 같다.

⚠️ 이 함수의 현행 정의는 **0062**였다(0042 → 0043 → 0044 → 0062 → 0064).
**파일에서 베끼지 마라** — `docs/db-current-schema.sql`이 단일 답이다.

### 2.2 흐름 통일 (사용자 지시)

> *"모든 유저는 카카오/구글 회원 가입 > 닉네임 세팅하기 > 홈 or 챌린지"*
> *"챌린지 링크로 초대되어도 GND에 계정이 있으면 바로 챌린지 메뉴로,
> 아니면 처음 가입 온보딩부터"*

| 진입 | 계정 있음 | 계정 없음 |
|---|---|---|
| `/onboarding` | — | 히어로 → 카카오·구글 → 닉네임 → **홈** |
| `/invite/<코드>` (친구) | 바로 친구 맺고 홈 | 히어로 → 카카오·구글 → 닉네임 → 친구 완료 → 홈 |
| `/challenge?join=<코드>` | **바로 그 챌린지** (원래 됐다) | 히어로 → 카카오·구글 → 닉네임 → **그 챌린지** |

**⚠️⚠️ `mustAskNickname`에 `invited`를 다시 넣지 마라.**
옛 코드는 `invited || providers.length === 0`이라, 초대로 온 사람은 카카오·구글을
건너뛰고 닉네임만 받았다. 그러면 그 사람은 **소셜 신원 0개짜리 브라우저 전용 계정**을
쥔다 — 브라우저를 지우면 기록·XP·배지가 사라지는, **배치 3이 통째로 없애려던 그
상태**다. 친구가 부른 사람이야말로 오래 남는데 가장 약한 계정을 주고 있었다.

**⚠️ `providers.length === 0`은 남겨 뒀다.** 카카오·구글이 동시에 죽으면 이게 없을 때
**신규 가입이 0이 된다.** 2026-08-08에 카카오가 KOE205로 실제로 죽었다 — 가정이 아니다.

**⚠️ `?open=`과 `?join=`을 헷갈리지 마라.**
`join`은 "이 코드로 참가시켜라", `open`은 "참가는 끝났으니 이 방을 열어라"다.
온보딩이 참가를 마친 뒤 `?join=`을 다시 넘기면 챌린지 화면이 참가를 한 번 더 시도해
`already_joined`가 뜬다. 챌린지를 여러 개 만들 수 있게 된 뒤로 `/challenge`만 열면
`pickPrimaryRow`가 대표 방을 골라 **초대받은 사람이 엉뚱한 방**을 본다.

**⚠️ 로그인 문을 챌린지 초대에서 숨기지 마라** (옛 코드는 `!challengeCode`로 가렸다).
초대로 온 사람도 제공자 버튼을 보게 된 뒤로 그게 막다른 길이 됐다 — 기존 사용자가
새 기기에서 챌린지 링크를 타면 카카오를 눌러도 `identity_already_exists`로 막히고
(그 카카오는 본인 계정에 이미 붙어 있다) 나갈 문이 없다. `/login`이 보관된 코드를
보고 챌린지로 데려간다.

### 2.4 D1·D2·D3 — 온보딩의 세 결함

| | 무엇이었나 | 어떻게 고쳤나 |
|---|---|---|
| **D1** | `catch {}`가 서버 오류 셋을 `초대 링크를 다시 확인해 주세요` 한 줄로 뭉갰다. **링크가 멀쩡한데 링크를 의심하게** 만들었다 | `challengeJoinError(e)` — 원인별 문구 + `recoverable` 판정 |
| **D2** | 실패하면 온보딩에 **갇혔다.** 프로필은 이미 생겼는데 `return`으로 붙잡고, `/onboarding`은 `(tabs)` 밖이라 `OnboardingGate`가 없어 새로고침해도 못 나간다 | 되돌릴 수 없는 실패면 안내를 남기고 홈으로 |
| **D3** | 실패한 코드가 localStorage에 **영구히** 남아 다음 가입까지 오염시켰다 | 되돌릴 수 없는 실패면 코드도 지운다 |

⚠️ **D1은 §2.3(앞 문서)의 `/auth/callback`이 오류를 삼켰던 것과 같은 부류다.**
같은 날 그걸 고쳐 문서에 적어 놓고 **바로 옆 파일에서 같은 짓을 하고 있었다.**
`catch {}`를 보면 멈춰라.

⚠️ **친구 코드는 마운트가 아니라 다 쓴 뒤에 지운다.** 옛 코드는
`useEffect(() => clearPendingInvite(), [])`였는데, 초대 사용자가 제공자로 떠났다
돌아오면 화면이 **다시 마운트**되고 그때는 코드가 이미 없어서 **친구 초대 링크가
통째로 증발한다.** 이 흐름 변경이 아니었으면 안 드러났을 함정이다.

소셜 계정**(다른 구글 등)이 필요하다.

**⚠️ 붙어 있는 것을 떼서 시험하지 마라.** 얻는 것보다 잃는 것이 크다.

경로(비상구)가 열려 4·5번과 참가 로직을 확인할 수 있다. **확인 뒤 반드시 되돌린다.**

## 8. 절대 하지 말 것

1. **`signInWithOAuth`와 `linkIdentity`를 뒤바꾸지 마라.** 기록이 갈린다
2. **`mustAskNickname`에 `invited`를 되살리지 마라** (§2.2). 초대로 온 사람이 가장 약한 계정을 쥔다
3. **`providers.length === 0` 비상구를 지우지 마라** (§2.2). 신규 가입이 0이 된다
4. **`catch {}`로 오류를 삼키지 마라** (§2.4). 이 저장소에서 두 번 났다
5. **친구 코드를 마운트에서 지우지 마라** (§2.4). 제공자 왕복에서 링크가 증발한다
6. **`?join=`과 `?open=`을 섞지 마라** (§2.2). 참가를 두 번 시도한다
7. **주간 목표 `null`에 기본값을 붙이지 마라.** 아무도 못 바꾸는 숫자로 달성률을 매기게 된다
8. **적용된 마이그레이션(0001~0063)을 수정하지 마라.** 0064도 Run한 뒤엔 마찬가지
9. **붙어 있는 소셜 신원을 시험용으로 떼지 마라** (§4.3)
10. **화면 확인 없이 배포하지 마라.** 이번 버그는 테스트·빌드가 전부 초록인데 났다

## 9. 이번에 배운 것

**"안 된다"는 신고를 받으면 코드보다 데이터를 먼저 봐라.**
챌린지 조인 실패는 조인 코드의 버그가 아니라 **참가 가능한 링크가 DB에 하나도
없었던 것**이었다. `challenges.invite_code`를 한 번 조회하는 데 명령 한 줄이면
됐는데, 그 전까지 RPC 정의를 읽고 있었다. 앞 문서 §8의 *"여백처럼 보이면 CSS보다
자산을 먼저 재라"* 와 같은 교훈이다 — **증상이 가리키는 층을 의심하기 전에 그
아래 층의 사실을 먼저 확인해라.**

**`catch {}`는 그 자체로 버그다.** 원인을 버리면 화면이 거짓말을 하고, 사용자는
멀쩡한 것을 의심하며 시간을 쓴다. 같은 날 `/auth/callback`에서 고쳐 놓고 옆
파일에서 반복했다. 오류를 잡되 **버리지는 마라.**

**흐름을 바꾸면 "한 번만 실행된다"는 가정이 깨진다.** 마운트에서 코드를 지우던
로직은 초대 사용자가 제공자로 떠났다 돌아오는 순간 링크를 증발시킨다.
화면을 떠났다 돌아오는 경로를 만들면 **마운트에서 하는 일을 전부 다시 세어라.**

# GND 학습 커리큘럼 — AI를 지휘하기 위한 용어와 구조

> **목적:** 코드를 직접 쓰기 위해서가 아니다. **다음 앱·홈페이지를 만들기 전에 기본 개념·구조·용어를 제대로 갖춰서, AI가 하는 말을 정확히 알아듣고 AI가 나 대신 정한 것을 알아채고 뒤집기 위해서**다.
>
> **교재:** GND 저장소 그 자체. 일반론이나 튜토리얼을 쓰지 않는다 — 이미 의도를 아는 시스템이 가장 빠른 교재다.
>
> **방식:** 회차마다 ① 용어를 받고 ② GND의 실제 파일을 열어 확인하고 ③ 스스로 답해 본다. AI와 함께 뜯는다.
>
> ---
>
> ⚠️ **교재를 쓰기 전에 반드시 알아야 할 것 — GND는 표본이지 표준이 아니다.**
>
> GND는 **AI가 제안하는 방향으로 만들어졌다.** 그래서 이 저장소의 구조에는 두 종류가 섞여 있다:
>
> - **법칙** — 그렇게 안 하면 실제로 망가지는 것 (예: DB가 권한을 판정해야 한다)
> - **선택** — 그때 AI가 고른 하나의 길. 다른 길도 있었다 (예: 화면 조각 82개 중 77개를 클라이언트로 만든 것)
>
> 교재로 읽기만 하면 **이 둘이 구별되지 않는다.** 그러면 다음 앱에 GND의 우연한 선택까지 그대로 베낀다.
> 그래서 **11회차에서 둘을 가른다.** 그게 이 커리큘럼의 진짜 종착점이다.

## 0. 이 문서를 쓰는 법

### 한 회차 = 40~60분

| 순서 | 하는 것 |
|---|---|
| 1 | 아래 회차의 **용어 목록**을 본다 (아직 모르는 게 정상) |
| 2 | **AI 프롬프트**를 복사해 붙여넣는다 |
| 3 | AI가 GND 파일을 열어 보여주면 **그 파일을 직접 열어 본다** ← 건너뛰지 말 것 |
| 4 | **손으로 확인**을 한다 (터미널·브라우저·Supabase) |
| 5 | **졸업 시험**에 답한다. 못 하면 그 회차를 다시 한다 |

### 매 회차 공통 프롬프트 (복사해서 씀)

```
GND 저장소를 교재로 [N회차: 주제]를 공부한다. 나는 비개발자다.

규칙:
1. 용어를 설명할 때 반드시 GND의 실제 파일과 줄을 열어서 보여줘. 일반론 금지.
2. 설명 도중에 내가 아직 안 배운 용어가 나오면 즉시 멈추고 그것부터 풀어줘.
   (내가 지금까지 배운 것: [지난 회차 용어들])
3. 비유는 하나만 쓰고, 곧바로 실제 코드로 되돌아와.
4. 마지막에 내가 답할 확인 질문 3개를 내줘. 답은 미리 주지 마.

이번 회차 용어: [용어 목록 붙여넣기]
```

> ⚠️ **규칙 2가 이 커리큘럼의 핵심이다.** "용어를 설명하려고 또 다른 모르는 용어를 쓰는 것" — 이게 지금 못 알아듣는 가장 큰 원인이다.

### 모르는 말 수집 노트

작업 중 AI가 못 알아들을 말을 하면, **단어만 적지 말고 문장을 통째로** 적어 둔다. 문맥이 빠지면 나중에 못 푼다.

```
2026-08-11 | "RLS 정책 때문에 anon 키로는 조회가 안 됩니다" | 6회차 관련
```

이 노트가 커리큘럼보다 우선한다. 아래 목록은 출발점일 뿐이다.

## 1회차 — 코드는 **어디서** 도는가 (가장 중요)

> 거의 모든 헷갈리는 AI 문장은 "이게 어디서 도는 얘기지?"만 풀리면 절반이 풀린다.

**용어:** 클라이언트 / 서버 / 데이터베이스 · 저장소(repo) · 커밋 · 브랜치 · 개발 서버 · 빌드 · 배포

**핵심 구분 — 이 셋은 전부 다른 것이다:**

| | 무엇 | GND에서 |
|---|---|---|
| **개발 서버** | 내 컴퓨터에서만 도는 앱 | `pnpm dev` → `localhost:3000` |
| **빌드** | 배포용으로 코드를 묶는 것 | `pnpm build` |
| **배포** | 사용자 폰에 실제로 반영 | `vercel --prod` ← **`git push`는 배포가 아니다** |

**GND 앵커:**
- `CLAUDE.md`의 「배포 — `git push`는 배포가 아니다」 절 — 이걸 몰라서 이틀간 옛 코드가 돌았던 사고 기록
- `vercel.json` — 3줄짜리 배포 설정

**손으로 확인:**
```bash
git log --oneline -5
```
```bash
node scripts/dev-fixture.mjs status
```

**졸업 시험:**
1. `pnpm dev`에서 잘 되던 게 사용자 폰에서 안 될 수 있다. 왜?
2. AI가 "푸시했습니다"라고 하면, 사용자 폰에 반영됐는가?
3. GND 코드가 도는 장소는 몇 군데인가? 각각 이름은?

## 8회차 — 데이터가 사는 곳 ②: 권한과 DB 함수 (가장 어려움)

> 6회차의 "anon 키가 노출돼도 되는 이유"가 여기서 풀린다.

**용어:** RLS 정책 · RPC / DB 함수 · SECURITY DEFINER · 트랜잭션 · 락 · 경쟁 상태(race condition)

**핵심 통찰:** GND는 **DB가 스스로를 지킨다.** 앱이 아니라 DB가 "이 사람이 이 줄을 볼 수 있나"를 판정한다(정책 70개). 그래서 화면에서 버튼을 숨기는 건 보안이 아니다.

**GND 앵커:**
- [`docs/db-current-schema.sql`](db-current-schema.sql) 2916줄부터 — RLS 정책 70개
- 같은 파일의 `accept_challenge_invite` 함수 — **한 함수 안에 다 있다:**
  - `SECURITY DEFINER` (정책을 건너뛰고 실행)
  - `pg_advisory_xact_lock` (둘이 동시에 눌러도 안 엉키게 = 락)
  - 상태 검사 → 갱신 (트랜잭션)

**졸업 시험:**
1. 남의 운동 기록이 안 보이는 건 앱이 막는 건가 DB가 막는 건가?
2. AI가 "SECURITY DEFINER로 만들었습니다"라고 하면 무엇을 건너뛴 건가? 왜 위험한가?
3. "경쟁 상태"는 어떤 상황에서 생기나?

## 졸업 과제 — 다음 앱의 구조를 한 장으로 그린다

> 코드를 쓰지 않는다. **그림 한 장과 문장 10개**면 된다.

다음에 만들 앱(홈페이지든 앱이든)에 대해 아래를 채운다. 이걸 AI에게 **처음에** 주면, AI가 나 대신 정하는 일이 크게 줄어든다.

```
1. 이 앱은 무엇을 저장하는가?        → 테이블 후보 5개
2. 누가 무엇을 볼 수 있나?           → 권한 규칙 3줄
3. 되돌릴 수 없는 동작은 무엇인가?    → 목록
4. 혼자 쓰는가, 상대가 있는가?       → (있으면 계정 2개로 검증해야 함)
5. 판단 규칙 중 반드시 테스트할 것 3개
6. 개발용 데이터와 실데이터를 어떻게 가르나?   ← GND가 실패한 지점
7. 배포는 무엇을 눌러야 되는가?               ← GND가 실패한 지점
8. 화면은 몇 개인가?                 → 주소 목록
9. 외부에 의존하는 것은?             → 로그인·결제·알림 등
10. 3개월 뒤 후회할 것 같은 결정은?
```

**이 10줄을 채울 수 있으면 커리큘럼은 끝난 것이다.** 용어를 외웠는지가 아니라, **결정을 내릴 수 있는지**가 기준이다.

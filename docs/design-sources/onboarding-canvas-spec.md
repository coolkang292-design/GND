# 통짜 화면 이미지 규격 — 온보딩·닉네임·로그인

**목적:** 세 화면(`/onboarding` 첫 화면 · `/onboarding` 닉네임 단계 · `/login`)의
상단 그림이 **잘려 보이는 것**을 없앤다. 한 장을 세 화면에 잘라 쓰는 대신,
**화면마다 그 화면의 레이아웃에 맞춘 통짜 이미지 한 장**을 뽑고 그 위에 텍스트를
정확한 자리에 얹는다.

사용자 지시 (2026-08-10):
> *"상단 이미지를 잘라서 사용하니까 뭔가 잘린 느낌이 나는데, 지금 레이아웃의
> 위치를 측정해서 통짜 이미지를 만들고 그 위에 텍스트를 정확한 위치에 렌더링하고
> 싶다"* · *"각각의 화면마다 꼭 같은 사이즈의 사진일 필요는 없어 어차피 텍스트
> 구성과 레이아웃이 다르니까"* · *"사진을 잘라 쓴 느낌이 아니라 자연스러운 사진
> 위에 텍스트를 추가해서 보이게 하기 위함"*

이 문서의 숫자는 **전부 실측이다** (2026-08-10, `pnpm dev` + 개발자 도구,
`public/onboarding/hero.webp` 1080×2252). 눈대중으로 고치지 마라 — §2에 다시 재는
방법이 있다.

## 1. 왜 잘려 보이는가 — 원인은 세 개다

### 1-1. 자산의 아트는 62.5%에서 끝나는데, 화면은 그보다 **위에서** 자른다

`hero.webp`(1080×2252)를 화소 단위로 재면:

| | 값 |
|---|---|
| 아트가 끝나는 세로 | **y = 1407** (전체의 62.5%). 이 아래는 순검정(밝기 0) |
| 아트의 가로 범위 | x = 11 ~ 1050 (1.0% ~ 97.2%) |
| `GND` 워드마크 오른쪽 획 | x ≈ 1035까지, 잔광 1050까지 |

그런데 화면에 **실제로 보이는** 범위는 이렇다 (컬럼 폭 390 기준):

| 화면 | 히어로 상자 높이 | 보이는 세로 | 아트(0~1407) 중 **잘린 양** |
|---|---|---|---|
| 온보딩 첫 화면 | 498.3px (1.278u) | y 0~1232 | 175px = 아트의 **12%** |
| 닉네임 단계 | 438.0px (1.123u) | y 0~1083 | 324px = **23%** |
| 로그인 | 313.4px (0.804u) | y 0~775 | 632px = **45%** |

로그인 화면에서는 **황금 문이 통째로 사라진다.** 불독 가슴 아래에서 그림이 가로선으로
뚝 끊긴다 — 이것이 "잘린 느낌"의 정체다.

### 1-2. 히어로 상자가 **화면마다·기기마다** 다른 높이로 눌린다

`hero-art.tsx`의 상자는 `aspect-[1080/1380]`(=1.278u)로 고정한 것처럼 보이지만,
부모 `main`이 `flex flex-col`이고 이 상자는 `flex-shrink: 1`인 **플렉스 아이템**이다.
아래 텍스트가 길수록 상자가 그만큼 **찌그러진다**. (실측: `/login`에서
`flex-shrink:0`을 주면 313.4px → 498.3px으로 되돌아온다.)

`/login`의 히어로 높이와 보이는 아트 (같은 화면, 기기만 다름):

| 기기 폭 | 히어로 높이 | 보이는 자산 세로 | 아트 잘림 |
|---|---|---|---|
| 360×800 | 241.9px (0.672u) | 0~648 | 54% |
| 390×844 | 313.4px (0.804u) | 0~775 | 45% |
| 430×932 | 401.4px (0.934u) | 0~900 | 36% |

**같은 그림이 기기마다 다른 데서 잘린다.** 그래서 "어디까지 보이는지"를 전제로
아트를 그릴 수가 없다 — 지금 구조로는 통짜 이미지를 만들어도 소용이 없다.
§5의 CSS 규칙이 이걸 먼저 없앤다.

### 1-3. 이미지를 112%로 키우고 왼쪽으로 밀어서 **좌우도** 잘린다

`hero-art.tsx`는 `w-[112%]` + `-ml-[6%]`다(사용자 지시 "그냥 사진을 키워"). 그 결과
가로로 **좌 58px · 우 58px(각 5.4%)** 이 상자 밖으로 나간다.

- 왼쪽: 불독 왼팔(x=11부터 시작)이 47px 잘린다
- 오른쪽: `GND` 워드마크 획(x≈1035)이 13px 잘린다

⚠️ 세로 잘림의 절반은 여기서도 온다. 112%로 키우면 아트 아래끝이 상자 바닥보다
**12% 더 내려가므로**, `aspect-[1080/1380]`을 맞춰 놨어도 y=1232에서 잘린다.

## 2. 다시 재는 방법 — 눈대중 금지

자산이나 레이아웃을 건드렸으면 **먼저 재고** 이 문서의 표를 갱신한다.

### 2-1. 자산 재기 (아트가 어디서 끝나는가)

```bash
python -c "
from PIL import Image
im=Image.open('public/onboarding/hero.webp').convert('L'); w,h=im.size; px=im.load()
rows=[y for y in range(h) if max(px[x,y] for x in range(w))>40]
cols=[x for x in range(w) if max(px[x,y] for y in range(h))>40]
print(f'{w}x{h}  아트 세로 {rows[0]}~{rows[-1]} ({rows[-1]/h:.1%})  가로 {cols[0]}~{cols[-1]}')
"
```

### 2-2. 화면 재기 (텍스트가 어디에 오는가)

`pnpm dev` → 확인할 화면을 열고 개발자 도구 콘솔에 붙여 넣는다.
**컬럼 폭(u) 단위**로 같이 찍어 주므로 기기 폭이 달라도 비교할 수 있다.

```js
(() => {
  const main = document.querySelector('main');
  const col = main.parentElement, cr = col.getBoundingClientRect();
  const hero = main.querySelector('div[aria-hidden]');
  const img = hero?.querySelector('img');
  const W = cr.width;
  const rows = [...main.querySelectorAll('p,h1,label,input,button,a')]
    .map(e => { const b = e.getBoundingClientRect(); return b.height ? {
      t: (e.innerText || e.placeholder || '').trim().replace(/\s+/g,' ').slice(0,26),
      y: +(b.top - cr.top).toFixed(1), h: +b.height.toFixed(1),
      u: +((b.top - cr.top) / W).toFixed(3) } : null; }).filter(Boolean);
  const hb = hero?.getBoundingClientRect(), ib = img?.getBoundingClientRect();
  console.table(rows);
  console.log({
    폭: W, 높이: cr.height, 기기비율: +(cr.height / W).toFixed(3),
    히어로높이: hb && +hb.height.toFixed(1),
    히어로비율u: hb && +(hb.height / W).toFixed(3),
    보이는자산세로: ib && Math.round((hb.bottom - ib.top) * 2252 / ib.height),
    텍스트블록높이: +(rows.at(-1).y + rows.at(-1).h - (hb ? hb.height : 0)).toFixed(1),
  });
})()
```

⚠️ **화면당 최소 세 폭(360 · 390 · 430)에서 재라.** 한 폭만 재면 §1-2의
기기별 편차를 놓친다. 폭에 따라 글줄이 접히면(로그인 첫 문장은 360에서 3줄,
390 이상에서 2줄) 텍스트 블록 높이가 통째로 달라진다.

## 3. 좌표 단위는 `u` — 픽셀이 아니다

**1u = 앱 컬럼의 폭** (`layout.tsx`의 `max-w-[430px]`, 좁은 폰에서는 기기 폭).
이미지도 컬럼 폭을 꽉 채우므로 **1u = 이미지의 가로폭 = 캔버스 1080px**이다.

| 왜 | |
|---|---|
| px로 적으면 | 390 폰에서 맞춘 좌표가 430 폰에서 어긋난다 |
| %(세로)로 적으면 | 기기 세로 비율이 2.16~2.22로 흔들려 같이 흔들린다 |
| u로 적으면 | 이미지와 텍스트가 **같은 자로 재진다** → 어느 폭에서도 같은 자리 |

환산: `캔버스 px = u × 1080`. 예) 1.52u → 캔버스 y 1642px.

지원 기기 비율 밴드 (세로/가로, 실측):

| 기기 | 비율 |
|---|---|
| 360×800 | 2.222 |
| 375×812 · 390×844 · 430×932 | 2.164 ~ 2.167 |
| 412×915 | 2.221 |

→ **설계 밴드 2.16 ~ 2.23.** iPhone SE(375×667 = 1.78)와 데스크톱 창은 이 밖이라
스크롤을 허용한다(§5-4).

## 5. 규격 — 프레임은 하나, 아트 배치는 화면마다

### 5-1. 계산 원리

```
아트에 쓸 수 있는 세로(u) = 기기 비율 − 텍스트 블록(u)
```

텍스트 블록은 px 고정이라 **폭이 넓을수록 u가 작아진다** → 아트 자리는 넓은 폰에서
더 커진다. 그 차이를 **여운 존**(완전히 균일한 검정)이 먹는다.

| 화면 | 텍스트 블록 u (360 / 390 / 430) | 아트 가용 u (360 / 390 / 430) |
|---|---|---|
| 온보딩 첫 | 0.700 / 0.646 / 0.586 | 1.522 / 1.518 / 1.581 |
| 닉네임 | 1.128 / 1.041 / 0.944 | 1.094 / 1.123 / 1.223 |
| 로그인 (문구 교체 뒤) | 1.474 / 1.360 / 1.234 | 0.748 / 0.804 / 0.933 |
| 로그인 (교체 전, 참고) | 1.550 / 1.362 / 1.235 | 0.672 / 0.802 / 0.932 |

→ **아트 존 = 최솟값** (제일 좁은 기기에서도 안 잘리게)
→ **여운 존 = 최댓값 − 최솟값** (남는 자리를 흡수)
→ **텍스트 존 = 여운 존 아래 전부** — 프레임 바닥까지 검정으로 둔다

⚠️ 여기서 나오는 것은 **아트 존 하나뿐이다.** 프레임 높이는 이 계산에 안 들어간다
(§5-2) — 텍스트가 이미지 안에 담기지 않기 때문이다.

### 5-2. 최종 캔버스 규격 — 프레임은 하나, 아트 끝나는 높이만 다르다

**프레임: 세 장 모두 `1080 × 2560` (비율 2.370).** 배경은 아트에서 뽑은 검정.

> ⚠️ 처음엔 화면마다 프레임을 다르게(2460·2540·2680) 잡았다가 사용자 지적으로
> 고쳤다 (2026-08-10 — *"3장의 이미지 전체 프레임 크기는 동일하되, 그 프레임 안에서
> 이미지 배치를 보정해야 하는 게 아닌가"*). 맞는 지적이다: **텍스트는 이미지 안에
> 담기지 않는다.** 화면 아래에 붙고(§5-4), 이미지는 `object-cover`로 아래가 잘린다.
> 그래서 프레임 높이가 하는 일은 "화면을 덮을 만큼 긴가" 하나뿐이고, 그건 화면마다
> 다를 이유가 없다. 2560은 제일 긴 폰(21:9 ≈ 2.33)보다 길어서 **가로가 잘리는 일이
> 없다** — 남는 아래쪽은 순검정이라 잘려도 티가 안 나고 용량도 거의 안 먹는다.

| | 온보딩 첫 화면 | 닉네임 단계 | 로그인 |
|---|---|---|---|
| **파일** | `screen-onboarding.webp` | `screen-nickname.webp` | `screen-login.webp` |
| **프레임** | 1080 × 2560 | 1080 × 2560 | 1080 × 2560 |
| **아트 존** | y 0 ~ **1642** (0~64.1%) | y 0 ~ **1182** (0~46.2%) | y 0 ~ **726** (0~28.4%) |
| **여운 존** | 1642 ~ 1707 (~66.7%) | 1182 ~ 1321 (~51.6%) | 726 ~ 1007 (~39.3%) |
| **텍스트 존** | 1707 ~ 2560 | 1321 ~ 2560 | 1007 ~ 2560 |
| **아트 비율(h/w)** | **1.52** | **1.09** | **0.67** (가로형) |

⚠️ **아트 존의 픽셀 값은 프레임 높이와 무관하다.** 화면 위에서 재는 값(§5-1의 u)이
정하기 때문이다 — 프레임을 더 늘려도 1642·1182·726은 그대로고 %만 바뀐다.
프레임을 바꿀 일이 생기면 **%가 아니라 px를 옮겨 적어라.**

⚠️ **이 프레임을 GPT에서 직접 만들려고 하지 마라.** §5-3이 이유와 대신 할 일이다.

#### 같은 아트를 배치만 바꿔 세 장을 만들 수 있나 — 두 장은 된다

프레임이 같아졌으니 자연스러운 다음 질문이다. 답은 **아트에 주어진 세로 자리에
달렸다.** 지금 아트의 비율은 h/w = 1.303이다.

| 화면 | 아트 존 | 같은 아트로 되나 |
|---|---|---|
| 온보딩 첫 | 1.52u | ✅ 아트(1.303)보다 **넓다.** 위아래 여백만 두면 그대로 들어간다 |
| 닉네임 | 1.09u | ⚠️ 16% 모자란다. 세로에 맞춰 줄이면 폭이 84%가 돼 **좌우에 검은 띠**가 생긴다 |
| 로그인 | 0.67u | ❌ 절반이다. 줄이면 폭이 52% — 검은 화면에 사진 한 장 뜬 꼴이 된다 |

그래서 **로그인은 아트를 다시 짜야 한다**(가로로 눕힌 구도 — §5-3 ③).
닉네임은 발판만 어둠 속으로 빼면 되므로 편집이 가볍다.

⚠️ 대안: **로그인 화면의 이메일 폼을 접으면**(§5-6) 아트 자리가 1.44u로 늘어
**같은 아트를 그대로 쓸 수 있다.** 그림을 다시 뽑기 전에 이쪽을 먼저 결정하라 —
순서를 거꾸로 하면 안 써도 될 그림을 만들게 된다.

### 5-3. GPT에서 기존 이미지를 편집해 받는 방법

사용자 작업 방식 (2026-08-10): *"이미지는 내가 GPT 채팅창에서 기존에 생성된
이미지에 편집을 통해서 생성을 할 거야."*

**ChatGPT의 이미지 출력은 세 가지 크기뿐이다** — `1024×1024` · `1024×1536`(세로) ·
`1536×1024`(가로). 제일 긴 것이 비율 1.5라, 프레임(2.370)은 **애초에 나올 수 없다.**

그럴 필요도 없다. 프레임의 아래쪽은 **아무것도 없는 순검정**이라 생성할 이유가
없다. 그래서 이렇게 나눈다:

| 누가 | 무엇을 |
|---|---|
| **GPT** | **아트만.** 세 화면의 아트 비율이 마침 GPT의 세 크기와 거의 맞는다 |
| **스크립트** | 검정 확장 · 아래끝 페이드 · 텍스트 존 검정 강제 · webp 변환 |

아트 비율과 GPT 크기가 맞아떨어지는 정도:

| 화면 | 필요한 h/w | **GPT에서 고를 크기** | 오차 |
|---|---|---|---|
| 온보딩 첫 화면 | 1.52 | **1024 × 1536** (세로, 1.50) | 1.5% — 그대로 쓴다 |
| 닉네임 | 1.09 | **1024 × 1024** (정사각, 1.00) | 스크립트가 아래에 검정 9%를 덧댄다 |
| 로그인 | 0.67 | **1536 × 1024** (가로, 0.667) | 0.7% — 그대로 쓴다 |

⚠️ **페이드(아래끝을 검정으로 녹이는 것)를 GPT에 시키지 마라.** 생성기는 거의
항상 희미한 가로 띠를 남기는데, 그 띠가 이 작업이 없애려는 "잘린 느낌"의 정체다.
스크립트가 계산으로 만들면 경계선이 생길 수가 없다.

#### 채팅창에 붙여 넣을 편집 지시문

`어플 UI 이미지/온보딩 히어로.png`)를 **첨부하고** 아래를 그대로 붙인다.

#### 받은 뒤 — 이 다섯 가지를 먼저 본다

GPT 편집은 **원본을 보존하지 않고 다시 그린다.** 그래서 매번 확인해야 한다.

1. **`GND` 세 글자가 맞는가** — `GNO`·`CND`·`GNND`로 자주 틀린다. 틀리면 다시.
2. **불독 얼굴이 그대로인가** — 다른 개가 되어 돌아오면 세 화면이 딴 앱이 된다.
3. **잘린 요소가 없는가** — 그 화면이 보여주기로 한 것(§5-2)이 온전한가.
4. **아래쪽이 비어 있는가** — 불티·글로우가 남아도 된다(스크립트가 덮는다).
   다만 **형태가 있는 것**(발판 조각·문틀)이 남으면 다시 요청한다.
5. **좌우 끝이 검정으로 막혀 있지 않은가** — 생성기가 좌우에 검은 띠를 넣어
   오는 일이 잦다. 그러면 화면에서 그림이 좁아 보인다(2026-08-08에 세 번 당했다,
   `make-onboarding-assets.py` 헤더 참조).

#### 캔버스로 만들기

```bash
python scripts/make-screen-canvas.py onboarding "어플 UI 이미지/아트-온보딩.png"
python scripts/make-screen-canvas.py nickname   "어플 UI 이미지/아트-닉네임.png"
python scripts/make-screen-canvas.py login      "어플 UI 이미지/아트-로그인.png"
```

스크립트가 하는 일과 그 이유는 `scripts/make-screen-canvas.py` 헤더에 있다.
숫자(아트 존·캔버스 높이)는 §5-2 표와 **같은 값을 들고 있다** — 한쪽만 고치지 마라.

출력에서 **두 줄을 확인한다**:

- `텍스트 존 최대 밝기 N  OK` — 12를 넘으면 글자 밑이 안 비었다는 뜻이다
- `여유 Npx` — 음수면 스크립트가 멈춘다(아트가 아트 존보다 길다). 그때는
  "위아래 여백을 더 두고 같은 구도로 다시"를 GPT에 요청한다
- `이음색 rgb(r,g,b)` — 아트 아래쪽에서 뽑은 검정. **캔버스를 이 색으로 채운다.**
  ⚠️ 고정값으로 채우면 아트가 끝나는 자리에서 배경이 갑자기 밝아져 **가로 경계선이
  생긴다** — 2026-08-10 첫 시험에서 실제로 났다(아트 (0,0,0) vs 캔버스 (10,10,12)).
  실측으로 확인한 뒤 값: 이음매 전후 평균 밝기 1.12 → 1.00, 단차 없음

### 5-4. 붙이는 방법 — 이 구조여야 좌표가 맞는다

```tsx
<main className="relative flex flex-1 flex-col overflow-y-auto">
  {/* 배경: 화면을 덮는다. 캔버스가 어느 기기보다 세로로 길어서
      잘리는 것은 **아래쪽 빈 검정뿐**이다 — 가로는 절대 안 잘린다 */}
  <Image
    src="/onboarding/screen-login.webp"
    alt=""
    fill
    priority
    className="pointer-events-none -z-10 object-cover object-top"
  />

  {/* 텍스트: 화면 **아래에** 붙인다 (mt-auto). 그래야 텍스트 블록의 위끝이
      기기와 무관하게 아트 아래끝과 만난다 — §5-1의 계산이 이 전제 위에 있다 */}
  <div className="mt-auto w-full px-6 pb-8 text-center">…</div>
</main>
```

⚠️ **`mt-auto`(아래 붙이기)를 빼지 마라.** 지금처럼 히어로 뒤에 텍스트를 이어
붙이면 텍스트 위치를 *이미지 높이*가 정하고, 그 이미지 높이는 §1-2처럼 flex-shrink로
흔들린다 — 통짜 이미지를 만들어도 다시 어긋난다.

⚠️ **히어로를 문서 흐름의 블록으로 되돌리지 마라.** `absolute`(=`fill`)로 흐름에서
빼야 flex-shrink에 눌리지 않는다. `hero-art.tsx`의 `aspect-[…]`·`w-[112%]`·
`-ml-[6%]`는 **전부 지운다** — 그 세 개가 §1-1·1-3의 잘림을 만든 장본인이다.

⚠️ `object-top`이어야 한다. `object-center`면 아트 위가 잘리고 아래 검정이 남는다.

### 5-5. 이 밴드 밖의 기기

| 기기 | 비율 | 무슨 일이 나나 |
|---|---|---|
| 360~430 폰 (2.16~2.23) | 설계 대상 | 여운 존이 흡수, 스크롤 없음 |
| 21:9 폰 (≈2.33) | 프레임(2.370) 안 | 아래 검정이 거의 다 보인다. 가로는 안 잘린다 |
| iPhone SE (1.78) | 밴드 밖 | 이미지 아래쪽이 더 잘린다(검정이라 안 보인다) + 세로 스크롤. **지금도 그렇다** |
| 데스크톱 (컬럼 430, 창 높이 자유) | 밴드 밖 | 창이 낮으면 스크롤. 컬럼이 430으로 묶여 있어 가로는 안 깨진다 |

⚠️ **프레임 비율(2.370)이 기기 비율보다 항상 커야 한다.** 작아지는 순간
`object-cover`가 폭을 잘라 불독 팔과 `GND`가 화면 밖으로 나간다 — §1-3에서
고친 그 실패가 그대로 돌아온다. 프레임을 줄이려거든 이 조건을 먼저 확인하라.

스크롤 없이 1.78(SE)까지 덮는 것은 **산술적으로 불가능하다**(로그인 기준 텍스트
블록이 SE 화면 높이의 80%를 먹어 아트에 0.23u밖에 안 남는다). 스크롤을 허용하는
쪽이 맞다.

### 5-6. 로그인 화면에 아트가 0.67u뿐인 이유 — 줄이고 싶으면 이걸 바꿔라

로그인은 소셜 버튼 2개 + 이메일 폼 전체(라벨·입력 2쌍)가 항상 펼쳐져 있어
텍스트 블록이 **531px**을 먹는다. 그래서 아트에 0.67u밖에 안 남는다.

이메일 폼을 `이메일로 로그인` 한 줄 뒤로 접으면 텍스트 블록이 **≈281px**로 줄고
아트 자리가 **1.44u**까지 늘어난다 — 온보딩 첫 화면과 거의 같은 그림을 쓸 수 있다.
⚠️ 다만 **이메일 폼을 없애지는 마라.** 카카오·구글이 둘 다 없는 사용자의 탈출구고,
이미 이메일로 붙은 계정이 있다(설계 §5.6).

## 6. 만든 뒤 확인 — 이걸 통과해야 반영이다

`pnpm dev`로 띄우고 **세 화면 × 세 폭(360·390·430)** 을 직접 본다.
자동 테스트·빌드·번들 grep은 이 중 아무것도 검증하지 않는다.

1. **가로선이 보이는가** — 아트가 검정으로 녹지 않고 선으로 끊기면 실패. 세 폭 모두.
2. **핵심이 다 보이는가** — 각 화면에서 그 그림이 보여주기로 한 것(포털·발판 등)이
   **잘리지 않고** 전부 있는가. 화면을 세로로 늘였다 줄여도 유지되는가.
3. **글자가 아트를 침범하지 않는가** — 첫 글줄 위에 그림 요소가 걸치면 여운 존이
   부족한 것이다. 캔버스를 다시 뽑는다(아트 존을 줄인다).
4. **글자 밑이 균일한 검정인가** — 글자 뒤로 불티·그라데이션이 비치면 실패.
5. **좌우가 잘리지 않는가** — 불독 팔·`GND` 마지막 획이 화면 밖으로 나가지 않는가.
   §1-3이 딱 이 실패였다.
6. **§2-2 스니펫을 다시 돌려** 텍스트 블록 위끝(u)이 §5-2의 아트 존 아래끝과
   ±0.02u 안에서 만나는지 숫자로 확인한다. 눈으로만 보면 20~30px 어긋난 것을 놓친다.
7. **기존 자산을 지우지 마라.** `hero.webp`는 되돌릴 자리다.

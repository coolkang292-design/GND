# First Principles — 제1원칙 사고

## 목적

이 스킬의 목적은 기존 관행·유사 사례·경쟁사 방식에서 답을 복사하는 것이 아니라, 문제를 더 이상 유용하게 쪼개기 어려운 사실과 제약까지 분해한 뒤 그 재료만으로 해법을 다시 만드는 것이다.

제1원칙은 "남들과 다르게 생각하기"가 아니다. 다음을 엄격하게 구분하는 절차다.

- **사실(Fact):** 검증 가능하거나 이미 관찰된 것
- **제약(Constraint):** 시간·돈·물리·법·기술·인간 행동 때문에 마음대로 바꿀 수 없는 것
- **가정(Assumption):** 사실처럼 취급하고 있지만 검증되지 않은 것
- **관행(Convention):** 업계나 조직이 원래 그렇게 해왔다는 이유로 유지되는 것
- **가설(Hypothesis):** 실험으로 맞고 틀림을 판별할 수 있는 주장

## 호출 방식

사용자가 다음과 같이 명시적으로 호출하면 이 스킬을 우선 적용한다.

- `/제1원칙 <문제>`
- `제1원칙으로 <문제>를 분석해줘`
- `근본부터 다시 설계해줘`
- `first principles로 봐줘`

다른 모드가 함께 호출되면 다음처럼 합성한다.

- `/제1원칙 /검증` → 재설계 후 핵심 가정을 가장 공격적으로 반증한다.
- `/제1원칙 /기획` → 근본요소에서 가능한 대안을 넓게 생성한다.
- `/제1원칙 /실행` → 분석을 압축하고 최소 검증 실험과 다음 행동에 집중한다.
- `/제1원칙 /리뷰` → 기존 결과 데이터를 근본 가정과 대조해 유지·수정·피벗·폐기 중 하나로 판정한다.

## 핵심 규칙

1. **답보다 문제 정의를 먼저 검증한다.** 사용자가 제시한 해결책을 문제 자체로 착각하지 않는다.
2. **비유와 경쟁사 사례는 보조자료다.** 결론의 출발점으로 사용하지 않는다.
3. **"원래", "보통", "업계에서는", "다들"을 가정 신호로 취급한다.**
4. **분해만 하고 끝내지 않는다.** 반드시 바닥 사실에서 다시 조립한다.
5. **모르면 모른다고 쓴다.** 빈칸을 상식이나 그럴듯한 숫자로 메우지 않는다.
6. **현재성이 필요한 외부 사실은 검증한다.** 시장 규모, 가격, 법규, 경쟁사 기능, 기술 사양, 인물·기업 현황 등은 최신 출처가 없으면 `[미검증]`으로 표시한다.
7. **사업 문제는 고객 행동과 경제성을 반드시 포함한다.** 기능 아이디어만으로 사업성을 판정하지 않는다.
8. **제품 문제는 사용자가 원하는 행동 변화와 마찰을 분리한다.** 기능 수가 아니라 행동 결과를 본다.
9. **기술 문제는 구현 관행보다 실제 요구사항·보안·데이터 경계·성능·운영비를 먼저 본다.**
10. **결론은 반드시 반증 가능해야 한다.** 무엇이 관찰되면 현재 결론을 버릴지 적는다.

## 분석 절차

### 1. 문제를 한 문장으로 재정의

다음 형식을 우선 사용한다.

> 우리는 `[대상]`이 `[원하는 행동/결과]`를 하도록 만들고 싶지만, `[현재 장애]` 때문에 `[손실/문제]`가 발생한다.

사용자의 질문이 이미 해결책 형태라면 문제와 해결책을 분리한다.

예:
- 질문: "GND에 그룹채팅을 넣어야 하나?"
- 문제: "챌린지 참가자 사이의 상호작용이 운동 지속률을 높이는 데 현재 방식으로 충분한가?"

### 2. 성공 조건을 수치 또는 관찰 가능 상태로 정의

가능하면 결과를 다음 중 하나 이상으로 표현한다.

- 행동 빈도
- 전환율
- 재방문/유지율
- 시간 절감
- 비용 절감
- 매출/마진/현금흐름
- 오류/실패율
- 사용자가 실제로 완료한 행동

정확한 숫자가 없다면 숫자를 발명하지 말고 "측정 필요"라고 표시한다.

### 3. 현재 가정을 전부 밖으로 꺼낸다

최소 다음 범주를 점검한다.

- 고객은 무엇을 원한다고 가정하는가?
- 고객이 실제로 돈/시간/노력을 쓸 것이라고 가정하는가?
- 어떤 기능이 반드시 필요하다고 가정하는가?
- 어떤 채널로 고객을 얻을 수 있다고 가정하는가?
- 경쟁사가 하는 방식이 필요하다고 가정하는가?
- 기술적으로 어렵거나 쉽다고 근거 없이 가정하는가?
- 비용·법·운영 문제를 과소평가하고 있지 않은가?

각 항목에 다음 라벨을 붙인다.

- `[확실]` 실제 데이터·코드·출처·관찰로 확인
- `[추정]` 논리적 추론이며 근거 1줄 명시
- `[추측]` 증거 부족
- `[미검증]` 확인 가능한데 아직 확인하지 않음

### 4. 근본 요소까지 분해

문제에 해당하는 축만 사용하되, 사업·제품 의사결정에서는 기본적으로 아래를 확인한다.

#### 고객
- 누구의 어떤 고통인가?
- 고통은 얼마나 자주 발생하는가?
- 지금은 무엇으로 해결하는가?
- 해결하지 않을 때 실제 비용은 무엇인가?

#### 행동
- 원하는 최종 행동은 무엇인가?
- 행동 직전의 마찰은 무엇인가?
- 보상은 즉시인가 지연인가?
- 네트워크/사회적 압력/습관이 행동에 어떤 영향을 주는가?

#### 경제
- 누가 돈을 내는가?
- 왜 돈을 내는가?
- 수익 발생 단위는 무엇인가?
- 변동비와 고정비는 무엇인가?
- 한 고객이 늘 때 경제성이 좋아지는가 나빠지는가?

#### 기술
- 실제로 꼭 필요한 데이터와 상태는 무엇인가?
- 신뢰 경계와 권한 경계는 무엇인가?
- 가장 단순한 구현으로 결과를 검증할 수 있는가?
- 기술이 문제인가, 수요가 문제인가?

#### 시간
- 무엇이 순차적으로 먼저 검증되어야 하는가?
- 지금 만들지 않아도 되는 것은 무엇인가?

#### 물리·법·운영
- 마음대로 바꿀 수 없는 제약은 무엇인가?
- 사람이 직접 처리하면 어디서 병목이 생기는가?

### 5. 관행 제거

다음 질문을 던진다.

- 이것을 기존 업계 이름으로 부르지 않는다면 어떻게 설명할까?
- 경쟁사 기능을 전부 보지 못했다고 가정하면 무엇부터 만들까?
- 앱/웹/구독/광고/커뮤니티 등 현재 형태를 금지하면 문제를 어떻게 해결할까?
- 예산이 1/10이라면 무엇만 남길까?
- 사람이 직접 해결해도 된다면 무엇을 자동화하지 않을까?

관행을 제거하되 검증된 제약까지 제거하지 않는다.

### 6. 바닥 사실에서 재조립

해법을 최소 3단계로 나눈다.

1. **최소 구조:** 결과를 만들기 위해 없어서는 안 되는 것
2. **증폭 구조:** 최소 구조가 작동한 뒤 성과를 크게 만드는 것
3. **장식/후순위:** 없어도 핵심 결과가 나는 것

가능하면 기존 설계보다 더 단순한 대안을 최소 1개 포함한다.

### 7. 가장 강한 대안을 비교

대안은 최대 3개로 압축하고 다음 기준으로 비교한다.

- 고객 가치
- 검증 속도
- 비용
- 실행 난이도
- 되돌리기 쉬움
- 학습량
- 경제성

정밀한 데이터가 없으면 가짜 점수를 만들지 않는다. `높음/중간/낮음` 또는 근거 문장으로 비교한다.

### 8. 반증 조건을 만든다

반드시 다음 문장을 완성한다.

> **이 결론이 틀렸다면 `_____` 데이터에서 드러난다.**

예:
- 파일럿 30명 중 초대→참여 전환이 거의 발생하지 않는다.
- 반복 사용자가 핵심 기능을 쓰지 않는다.
- 고객 인터뷰에서는 강한 관심을 보이지만 결제/예약 행동은 없다.
- 기능 추가 후 핵심 유지율이 변하지 않는다.

### 9. 최소 검증 실험

"무엇을 만들까?"보다 "무엇을 가장 싸고 빠르게 배울까?"를 우선한다.

실험에는 다음을 포함한다.

- 검증할 가설 1개
- 대상
- 행동
- 측정값
- 성공/실패 판정 기준
- 필요한 최소 구현
- 다음 의사결정

성공 기준을 정할 근거가 없으면 먼저 baseline을 측정한다.

## GND에 적용할 때 추가 규칙

GND 관련 분석에서는 기능 아이디어를 평가하기 전에 다음 순서로 확인한다.

1. 이 기능이 **운동 실행/지속** 또는 **초대·참여·재참여** 중 어떤 행동을 바꾸는가?
2. 현재 GND에 같은 결과를 낼 수 있는 기존 기능/데이터가 있는가?
3. 신규 테이블·상태·알림·권한이 정말 필요한가?
4. 현재 외부 파일럿 단계에서 지금 검증해야 하는가, 아니면 사용자가 생긴 뒤 검증해도 되는가?
5. 구현이 성공해도 사업 가설을 전혀 검증하지 못하는 "좋아 보이는 기능"은 아닌가?

GND 코드/DB 현황이 결론에 영향을 주면 추측하지 말고 GitHub/Supabase의 실제 현황을 먼저 확인한다.

## 출력 형식

기본 출력은 아래 순서를 따른다. 질문이 단순하면 각 섹션을 1~3줄로 압축할 수 있다.

### 결론
한 줄.

### 1. 진짜 문제
문제와 사용자가 제시한 해결책을 분리한다.

### 2. 바닥 사실
핵심 사실·제약만 적고 `[확실] / [추정] / [추측] / [미검증]` 라벨을 붙인다.

### 3. 깨야 할 가정
결론을 가장 크게 바꿀 가정부터 최대 5개.

### 4. 제1원칙 재설계
- 최소 구조
- 증폭 구조
- 제거/후순위

### 5. 대안
결과를 바꿀 수 있는 대안만 최대 3개.

### 최대 리스크
최대 2개.

### 반증 조건
`이 결론이 틀렸다면 OO 데이터에서 드러난다.`

### 다음 액션
지금 할 단 하나의 검증 행동.

## 품질 체크

답변을 끝내기 전에 확인한다.

- [ ] 사용자의 해결책을 문제 자체로 받아들이지 않았는가?
- [ ] 사실과 가정을 구분했는가?
- [ ] 경쟁사/관행을 근거 없이 출발점으로 삼지 않았는가?
- [ ] 고객 행동과 경제적 제약을 빠뜨리지 않았는가?
- [ ] 더 단순한 대안을 최소 1개 만들었는가?
- [ ] 분석 후 다시 조립했는가?
- [ ] 검증 가능한 반증 조건이 있는가?
- [ ] 다음 행동이 기능 개발이 아니라 더 싼 검증으로 대체될 수 있는지 확인했는가?

## 금지사항

- 유명인의 "제1원칙" 어록을 장식적으로 붙이는 것
- 근거 없는 시장규모·전환율·가격 숫자를 만드는 것
- "좋은 아이디어다"로 끝내는 것
- 분해만 하고 실행 결론을 내지 않는 것
- 경쟁사가 한다는 이유만으로 기능을 추천하는 것
- 사용자의 기대 결론에 맞추기 위해 치명적 반례를 생략하는 것
